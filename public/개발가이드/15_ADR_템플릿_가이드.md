## 1. ADR 개요

### 1.1 ADR이란

Architecture Decision Record(ADR)는 소프트웨어 아키텍처에서 내린 중요한 결정을 문서화하는 방법이다. **"왜 이렇게 설계했는가?"** 에 대한 답을 제공하여 미래의 개발자들이 맥락을 이해할 수 있게 한다.

### 1.2 ADR의 핵심 가치

- **투명성**: 모든 아키텍처 결정의 이유가 명확하게 기록됨
- **연속성**: 담당자가 바뀌어도 결정의 맥락이 유지됨
- **학습**: 과거의 실수와 성공 경험을 조직 자산으로 축적
- **검증**: 결정의 타당성을 사후에 검증 가능

### 1.3 ADR 작성이 필요한 경우

| 구분 | 예시 | ADR 필요 여부 |
|------|------|:---:|
| 프레임워크/라이브러리 선택 | React vs Vue, Next.js 도입 | 필수 |
| 데이터베이스 선택 | PostgreSQL vs MongoDB | 필수 |
| 인증/보안 전략 | JWT vs Session, OAuth 구현 | 필수 |
| 아키텍처 패턴 | 모놀리스 vs 마이크로서비스 | 필수 |
| 인프라 결정 | 클라우드 공급자, 컨테이너 전략 | 필수 |
| 코딩 컨벤션 | 린팅 규칙, 포맷터 설정 | 불필요 (별도 가이드) |
| 단순 라이브러리 추가 | 유틸 라이브러리 하나 추가 | 불필요 |

### 1.4 ADR 상태 관리

| 상태 | 설명 | 전환 |
|------|------|------|
| **Proposed** | 초안 작성, 검토 중 | -> Accepted / Rejected |
| **Accepted** | 팀 승인, 구현 예정 또는 진행 중 | -> Deprecated / Superseded |
| **Rejected** | 검토 후 채택하지 않기로 결정 | (종료) |
| **Deprecated** | 더 이상 유효하지 않음 | (종료) |
| **Superseded** | 새로운 ADR로 대체됨 (대체 ADR 번호 명시) | (종료) |

## 2. AI 기반 ADR 초안 자동 생성

AI를 활용하면 ADR 초안 작성 시간을 대폭 단축할 수 있다. 아래 3가지 프롬프트는 가장 빈번하게 발생하는 아키텍처 결정 시나리오를 다룬다.

### 2.1 AI 활용 원칙

1. **맥락은 사람이 제공**: 팀의 고유한 상황, 제약 조건, 히스토리는 사람이 입력
2. **대안 분석은 AI가 보조**: 기술 비교, 벤치마크 데이터, 업계 동향 조사를 AI에 위임
3. **최종 판단은 사람이 수행**: AI가 제시한 분석을 팀이 검증하고 결정

### 2.2 프롬프트 1: 프레임워크 선택 ADR 자동 생성

```text
당신은 시니어 소프트웨어 아키텍트입니다. 아래 조건으로 ADR 초안을 MADR 포맷으로 작성해주세요.

[결정 주제]
신규 프로젝트의 프론트엔드 프레임워크 선택

[배경]
- 현재 상태: jQuery 기반 레거시 시스템
- 문제점: 유지보수 어려움, 신규 채용 어려움, 성능 저하
- 제약 조건: 팀 6명, 3개월 내 MVP, React 경험자 4명

[고려할 대안]
- Next.js (App Router)
- Remix
- Vite + React (SPA)

[평가 기준]
성능, 학습 곡선, SEO 대응, 생태계 성숙도, 장기 유지보수

[출력 요구사항]
- MADR 포맷(상태, 컨텍스트, 결정, 고려한 대안, 결과, 구현 계획, 검증) 준수
- 각 대안의 장단점을 정량적 지표(번들 사이즈, 빌드 시간, 커뮤니티 크기 등)로 비교하는 표 포함
- 마이그레이션 비용 분석(인력, 기간, 리스크) 포함
- 롤백 계획 포함
```

### 2.3 프롬프트 2: 데이터베이스 선택 ADR 자동 생성

```text
당신은 데이터 아키텍트입니다. 아래 조건으로 ADR 초안을 MADR 포맷으로 작성해주세요.

[결정 주제]
주문 서비스의 데이터베이스 선택

[배경]
- 일일 주문량: 약 50,000건
- 복잡한 조회 쿼리 (주문-상품-결제-배송 조인)
- 트랜잭션 무결성 필수
- 향후 분석용 쿼리 지원 필요

[제약 조건]
- 월 인프라 비용: $1,000 이내
- DBA 없이 개발자가 직접 운영
- 클라우드 관리형 서비스 사용 가능

[고려할 대안]
- PostgreSQL (관리형)
- MySQL 8
- MongoDB

[평가 기준]
트랜잭션 안정성, 복잡 쿼리 성능, 운영 비용, 학습 곡선, 확장성

[출력 요구사항]
- MADR 포맷 준수
- 각 대안의 TPS 벤치마크, 조인 쿼리 성능, 관리형 서비스 월 비용을 비교하는 표 포함
- 데이터 마이그레이션 전략 포함
- 장애 시 롤백 방안 포함
```

### 2.4 프롬프트 3: 인증 전략 ADR 자동 생성

```text
당신은 보안 아키텍트입니다. 아래 조건으로 ADR 초안을 MADR 포맷으로 작성해주세요.

[결정 주제]
서비스 인증/인가 전략 선택

[배경]
- 웹 + 모바일 앱 동시 지원
- 소셜 로그인(Google, Apple, Kakao) 지원 필요
- 마이크로서비스 간 인증 전파 필요
- 사용자 수: 초기 10만, 1년 내 100만 예상

[제약 조건]
- 자체 인증 서버 운영 가능
- 기존 세션 기반 인증에서 전환
- 보안 감사 통과 필수

[고려할 대안]
- OAuth 2.0 + JWT (자체 구현)
- 세션 기반 인증 유지 (Redis 클러스터)
- Auth0 / Firebase Auth (외부 서비스)

[평가 기준]
보안 수준, 확장성, 운영 비용, 소셜 로그인 통합 용이성, 마이크로서비스 호환성

[출력 요구사항]
- MADR 포맷 준수
- 보안 체크리스트(PKCE, Token Rotation, CORS 등) 포함
- 100만 사용자 기준 월 비용 비교표 포함
- 보안 감사 항목별 대응 방안 포함
```

### 2.5 AI 생성 ADR 검증 체크리스트

AI가 생성한 ADR 초안은 반드시 다음 항목으로 검증한다:

- [ ] 팀의 실제 맥락(레거시, 인력, 문화)이 정확히 반영되었는가
- [ ] AI가 제시한 벤치마크/통계 데이터의 출처가 확인 가능한가
- [ ] 대안 분석이 공정하고 편향되지 않았는가
- [ ] 우리 팀에 맞지 않는 대안이 포함되어 있지는 않은가
- [ ] 리스크 분석이 현실적인가
- [ ] 구현 계획이 실행 가능한가
- [ ] 비용 데이터가 최신 가격 기준인가

## 3. AI 기반 의사결정 매트릭스 자동 생성

ADR에서 대안을 비교할 때, AI에게 의사결정 매트릭스를 자동으로 생성하도록 요청하면 객관적인 비교 분석이 가능하다.

### 3.1 의사결정 매트릭스 생성 프롬프트

```text
아래 대안들을 의사결정 매트릭스로 비교 분석해주세요.

[대안]
1. {대안 A}
2. {대안 B}
3. {대안 C}

[평가 기준 및 가중치]
- 성능 (25%)
- 비용 (20%)
- 학습 곡선 (15%)
- 생태계 성숙도 (15%)
- 확장성 (15%)
- 운영 복잡도 (10%)

[출력 형식]
1. 각 기준별 1~5점 점수표 (근거 포함)
2. 가중치 적용 총점 계산
3. 민감도 분석: 가중치 변동 시 결과가 바뀌는 임계점
4. 최종 추천과 그 근거 (2~3문장)
```

### 3.2 의사결정 매트릭스 예시

AI가 생성한 매트릭스 결과물 형태:

| 평가 기준 | 가중치 | Next.js | Remix | Vite + React |
|----------|:------:|:-------:|:-----:|:------------:|
| 성능 | 25% | 5 | 4 | 3 |
| 비용 | 20% | 4 | 4 | 5 |
| 학습 곡선 | 15% | 4 | 3 | 5 |
| 생태계 성숙도 | 15% | 5 | 3 | 4 |
| 확장성 | 15% | 5 | 4 | 3 |
| 운영 복잡도 | 10% | 3 | 4 | 5 |
| **가중치 총점** | **100%** | **4.40** | **3.65** | **3.95** |

### 3.3 민감도 분석 요청 프롬프트

```text
위 의사결정 매트릭스에서 다음을 추가 분석해주세요:

1. 가중치를 변경했을 때 1위 대안이 바뀌는 시나리오는?
2. "비용 최우선" 시나리오(비용 40%)에서의 순위 변화
3. "성능 최우선" 시나리오(성능 40%)에서의 순위 변화
4. 결과의 신뢰도를 낮추는 불확실한 요소는 무엇인가?
```

## 4. ADR 작성법 (MADR 포맷)

MADR(Markdown Any Decision Records)은 ADR의 표준 포맷 중 하나로, 간결하면서도 필요한 정보를 모두 담을 수 있다.

### 4.1 MADR 템플릿

```markdown
# ADR-[번호]: [간결한 제목]

## 상태

[Proposed | Accepted | Rejected | Deprecated | Superseded by ADR-XXX]

## 컨텍스트

### 배경
{무엇이 문제이며, 어떤 상황에서 이 결정이 필요한가}

### 제약 조건
- {기술적 제약}
- {비즈니스 제약}
- {팀 역량 제약}
- {시간/비용 제약}

### 요구사항
- {기능적 요구사항}
- {비기능적 요구사항 (성능, 보안, 확장성 등)}

## 결정

### 선택한 방안
{구체적으로 무엇을 결정했는가}

### 선택 이유
{왜 이 방안을 선택했는가}

## 의사결정 매트릭스

| 평가 기준 | 가중치 | 대안 A | 대안 B | 대안 C |
|----------|:------:|:------:|:------:|:------:|
| {기준 1} | {N}% | {점수} | {점수} | {점수} |
| {기준 2} | {N}% | {점수} | {점수} | {점수} |
| **총점** | **100%** | **{총점}** | **{총점}** | **{총점}** |

## 고려한 대안

### 대안 1: [대안명]
- **장점**: {장점}
- **단점**: {단점}
- **선택하지 않은 이유**: {이유}

### 대안 2: [대안명]
- **장점**: {장점}
- **단점**: {단점}
- **선택하지 않은 이유**: {이유}

## 결과

### 긍정적 결과
- {예상되는 긍정적 영향}

### 부정적 결과 (Trade-offs)
- {감수해야 하는 단점}

### 중립적 결과
- {긍정도 부정도 아닌 영향}

## 구현 계획

### 마이그레이션 전략
{기존 시스템에서 전환하는 방법}

### 롤백 계획
{문제 발생 시 이전 상태로 복원하는 방법}

### 예상 작업량
{필요한 인력, 기간, 비용}

## 검증

### 성공 지표
{어떤 지표로 이 결정의 성공을 측정할 것인가}

### 모니터링 방법
{어떻게 지속적으로 추적할 것인가}

## 참고 자료
- {관련 문서, 벤치마크, 외부 사례 등}

## 이력
| 날짜 | 변경 내용 | 작성자 |
|------|----------|--------|
| YYYY-MM-DD | 초안 작성 (AI 생성 + 수동 검토) | 홍길동 |
| YYYY-MM-DD | 리뷰 반영 | 홍길동 |
| YYYY-MM-DD | 승인 | 김영희 |
```

### 4.2 ADR 작성 베스트 프랙티스

#### 제목

- 간결하고 결정 내용이 드러나야 한다
- 잘못된 예: "데이터베이스 관련 개선"
- 올바른 예: "읽기 성능 개선을 위한 읽기 전용 Replica 도입"

#### 컨텍스트

- 이 결정의 배경을 모르는 사람도 이해할 수 있게 작성
- 숫자와 데이터로 문제를 구체화
- "왜 지금 이 결정이 필요한가"를 명확히

#### 대안 분석

- 진지하게 고려한 대안만 작성 (허수 대안 금지)
- 각 대안의 장단점을 공정하게 평가
- "왜 선택하지 않았는가"를 명확히
- AI에게 의사결정 매트릭스를 생성하도록 요청하여 객관성 확보

#### 결과

- 긍정적 결과만 나열하지 않는다
- Trade-off를 솔직하게 인정
- 예상되는 문제점도 사전에 명시

## 5. 실전 ADR 예시 3가지

### 5.1 프레임워크 선택 ADR

```markdown
# ADR-015: 신규 프로젝트 프레임워크로 Next.js 15 선택

## 상태
Accepted

## 컨텍스트

### 배경
신규 서비스의 프론트엔드 프레임워크를 선정해야 한다.
- SEO가 중요한 퍼블릭 페이지 존재
- 인증 후 사용하는 대시보드 페이지 존재
- 초기 로딩 성능 목표: LCP 2.5초 이내
- 팀원 6명 중 4명이 React 경험 보유

### 제약 조건
- 개발 기간: 3개월 이내 MVP 출시
- React 생태계 내에서 선택 (팀 역량 고려)

## 결정

### 선택한 방안
Next.js 15 (App Router + Server Components)

### 선택 이유
1. SEO 필요 페이지는 서버 사이드 렌더링, 대시보드는 클라이언트 렌더링으로 유연한 전략
2. React 서버 컴포넌트로 번들 사이즈 최적화
3. 팀의 React 경험을 활용 가능
```

### 5.3 인증 전략 ADR

```markdown
# ADR-022: 인증 전략으로 OAuth 2.0 + JWT 채택

## 상태
Accepted

## 컨텍스트

### 배경
서비스의 인증/인가 시스템을 설계해야 한다.
- 웹 + 모바일 앱 동시 지원
- 소셜 로그인(Google, Apple, Kakao) 지원 필요
- 마이크로서비스 간 인증 전파 필요
- 사용자 수: 초기 10만, 1년 내 100만 예상

### 제약 조건
- 자체 인증 서버 운영 가능
- 기존 세션 기반 인증에서 전환
- 보안 감사 통과 필수

## 결정

### 선택한 방안
OAuth 2.0 (Authorization Code Flow with PKCE) + JWT (Access/Refresh Token)

### 선택 이유
1. 소셜 로그인 통합이 OAuth 2.0 표준으로 자연스러움
2. JWT로 마이크로서비스 간 인증 전파가 간단
3. Refresh Token Rotation으로 보안 강화
4. 무상태(Stateless) 인증으로 수평 확장 용이

## 의사결정 매트릭스 (AI 생성)

| 평가 기준 | 가중치 | OAuth 2.0 + JWT | 세션 기반 (Redis) | Auth0/Firebase |
|----------|:------:|:---------------:|:----------------:|:--------------:|
| 보안 수준 | 25% | 4 | 4 | 5 |
| 확장성 | 20% | 5 | 3 | 5 |
| 운영 비용 (100만 기준) | 20% | 4 | 4 | 2 |
| 소셜 로그인 통합 | 20% | 5 | 2 | 5 |
| MSA 호환성 | 15% | 5 | 2 | 4 |
| **총점** | **100%** | **4.55** | **3.10** | **4.15** |

## 고려한 대안

### 대안 1: 세션 기반 인증 유지
- **장점**: 구현 간단, 즉시 세션 무효화 가능
- **단점**: 서버 확장 시 세션 공유 필요(Redis), 모바일 대응 불편
- **선택하지 않은 이유**: 마이크로서비스 구조에서 세션 공유 복잡도 높음

### 대안 2: Auth0 / Firebase Auth (외부 서비스)
- **장점**: 운영 부담 최소, 다양한 소셜 로그인 즉시 지원
- **단점**: 사용자 수 증가 시 비용 급증, 커스터마이징 제한
- **선택하지 않은 이유**: 100만 사용자 기준 월 비용 $3,000+ 예상

## 결과

### 긍정적 결과
- 서비스 간 인증 전파를 위한 별도 호출 불필요
- 소셜 로그인 표준 프로토콜로 통합
- Access Token 짧은 만료(15분)로 탈취 리스크 최소화

### 부정적 결과
- JWT 즉시 무효화 불가 (블랙리스트 별도 관리 필요)
- 토큰 관리 로직 복잡도 증가
- 보안 감사 항목 증가 (토큰 저장, 전달 방식)

## 보안 체크리스트
- [x] PKCE 적용 (Authorization Code 탈취 방지)
- [x] Refresh Token Rotation (재사용 탐지)
- [x] Access Token 만료 15분
- [x] Refresh Token 만료 7일 (슬라이딩 윈도우)
- [x] HttpOnly + Secure + SameSite Cookie 저장
- [x] CORS 정책 엄격 설정
```

## 6. ADR 관리 도구 비교: adr-tools vs log4brains

### 6.1 adr-tools

CLI 기반 ADR 관리 도구로, 터미널에서 ADR을 생성/관리할 수 있다.

```bash
# 설치
brew install adr-tools

# ADR 저장소 초기화
adr init docs/adr

# 새 ADR 생성
adr new "주문 서비스 데이터베이스로 PostgreSQL 선택"

# ADR 대체 (기존 ADR을 새 ADR로 대체)
adr new -s 3 "Redis에서 Valkey로 전환"

# ADR 목록 보기
adr list

# ADR 목차 생성
adr generate toc > docs/adr/README.md
```

### 6.2 log4brains

웹 기반 ADR 브라우저로, ADR을 검색하고 탐색할 수 있는 정적 사이트를 생성한다.

```bash
# 설치
npm install -g log4brains

# 초기화
log4brains init

# 새 ADR 생성
log4brains adr new

# 로컬 미리보기
log4brains preview

# 정적 사이트 빌드
log4brains build
```

### 6.3 도구 비교표

| 비교 항목 | adr-tools | log4brains |
|----------|-----------|------------|
| **유형** | CLI 전용 | 웹 + CLI |
| **설치** | `brew install` | `npm install` |
| **웹 UI** | 없음 | 정적 사이트 자동 생성 |
| **검색** | `grep` 등 수동 | 내장 검색 기능 |
| **타임라인 뷰** | 없음 | 지원 |
| **Git 친화성** | 우수 (마크다운 파일) | 우수 (마크다운 기반) |
| **ADR 상호 참조** | 수동 링크 | 자동 링크 |
| **설정 복잡도** | 낮음 | 중간 |
| **추천 상황** | 소규모 팀, CLI 선호, 빠른 도입 | 중대규모 팀, ADR이 많을 때, 비개발자 열람 필요 시 |

### 6.4 AI + 도구 연동 워크플로우

## 7. ADR과 RFC의 관계

### 7.1 RFC와 ADR의 차이

| 구분 | RFC | ADR |
|------|-----|-----|
| **목적** | 의사결정을 위한 논의 프로세스 | 내려진 결정의 기록 |
| **시점** | 결정 전 | 결정 후 |
| **내용** | 문제 정의, 대안 분석, 논의 과정 | 최종 결정, 근거, 결과 |
| **길이** | 상세 (5-20페이지) | 간결 (1-5페이지) |
| **변경** | 논의 중 수정 가능 | 원본 불변 (새 ADR로 대체) |
| **AI 활용** | 초안 생성, 리뷰 보조 | 초안 생성, 의사결정 매트릭스 자동 생성 |

### 7.2 연동 워크플로우

```
문제 인식
  │
  ▼
RFC 작성 (논의 프로세스) -- AI로 초안 생성 가능
  │
  ├─ 대안 분석 (AI 의사결정 매트릭스 자동 생성)
  ├─ 팀 논의 (비동기 + 동기)
  └─ 의사결정
  │
  ▼
ADR 작성 (결정 기록) -- AI로 RFC 내용을 ADR 포맷으로 변환
  │
  ├─ RFC의 핵심 내용을 요약
  ├─ 최종 결정과 근거 기록
  └─ 성공 지표 명시
  │
  ▼
구현 & 검증
  │
  └─ 성공 지표 달성 여부 ADR에 업데이트
```

### 7.3 AI를 활용한 RFC -> ADR 변환 프롬프트

```text
아래 RFC 문서의 내용을 MADR 포맷 ADR로 변환해주세요.

[RFC 원문]
{RFC 내용 붙여넣기}

[변환 규칙]
- RFC의 동기/문제점 -> ADR 컨텍스트 (핵심 문제만 요약)
- RFC의 대안 분석 -> ADR 고려한 대안 (최종 비교 결과만)
- RFC의 제안 -> ADR 결정 (승인된 제안만)
- RFC의 영향 분석 -> ADR 결과 (긍정/부정/중립 분류)
- RFC의 구현 계획 -> ADR 구현 계획 (승인된 계획만)
- RFC의 성공 지표 -> ADR 검증 (측정 방법 구체화)

[출력]
MADR 포맷 마크다운
```

## 자주 묻는 질문

### Q: 모든 기술 결정을 ADR로 작성해야 하는가?

아니다. 다음과 같은 **중요한 결정만** 작성한다:
- 프로젝트 전체에 영향을 미치는 결정
- 변경하기 어려운 결정 (데이터베이스, 아키텍처)
- 비용이 많이 드는 결정
- Trade-off가 명확한 결정

### Q: AI로 생성한 ADR을 그대로 사용해도 되는가?

절대 그대로 사용하지 않는다. AI는 초안 생성과 대안 분석을 보조하는 도구이다. 반드시 2.5절의 검증 체크리스트를 통과시키고, 팀의 실제 맥락과 경험을 반영하여 수정한다.

### Q: 과거 결정을 수정해도 되는가?

원본 ADR는 수정하지 않는다. 대신:
1. 새로운 ADR을 작성한다 (ADR-XXX: {변경 내용})
2. 기존 ADR 상태를 "Superseded by ADR-XXX"로 변경한다
3. 왜 변경했는지를 새 ADR에 명시한다

### Q: ADR과 RFC 중 어떤 것을 먼저 도입해야 하는가?

ADR을 먼저 도입하는 것을 권장한다. ADR은 가벼운 형식으로 시작할 수 있으며, 문서화 습관이 자리잡은 후에 RFC 프로세스를 추가하면 자연스럽게 확장된다.
