## ADR이란?

Architecture Decision Record(ADR)는 소프트웨어 아키텍처에서 내린 중요한 결정을 문서화하는 방법입니다. **"왜 이렇게 설계했는가?"** 에 대한 답을 제공하여 미래의 개발자들이 맥락을 이해할 수 있게 합니다.

### ADR을 사용해야 하는 이유

**문제 상황:**
> 개발자 A: "왜 Redis를 쓰고 있죠? MySQL로 하면 안 되나요?"  
> 개발자 B: "음... 예전 선임이 그렇게 했는데..."

**ADR을 사용하면:**
> 개발자 A: "왜 Redis를 쓰고 있죠?"  
> 개발자 B: "ADR-007을 보시면, 세션 동시성 문제로 Redis 선택했고, 성능 테스트 결과도 있습니다."

### 핵심 가치
- **투명성**: 모든 아키텍처 결정의 이유가 명확
- **연속성**: 담당자가 바뀌어도 맥락 유지
- **학습**: 과거 실수를 반복하지 않음
- **리뷰**: 결정의 타당성을 검증 가능

## 실전 예시 1: 캐시 솔루션 선택

```markdown
# ADR-007: 세션 스토리지로 Redis 도입

날짜: 2024-11-15
상태: 승인됨
의사결정자: 김철수(Tech Lead), 박영희(Backend Lead)
관련 문서: [성능 테스트 결과](link), [보안 검토](link)

## 컨텍스트

### 배경
현재 세션을 MySQL에 저장하고 있어 다음 문제가 발생:
- 피크 시간대 세션 조회 레이턴시 300ms
- 동시 접속자 1만명 시 데이터베이스 부하 급증
- 로그인/로그아웃 시 응답 시간 2초 이상

### 제약 조건
- 예산: 월 $500 이하
- 마이그레이션 기간: 2주
- 기존 세션 데이터 무손실 이전 필요
- 팀 내 Redis 경험자 2명

### 고려한 요구사항
- 세션 조회 응답시간 < 50ms
- 동시 접속자 10만명 지원
- 고가용성 (99.9% 이상)
- 데이터 영속성 (세션 만료 전까지)

## 의사결정

### 선택한 방안
**Redis Cluster (3 Master + 3 Replica)를 세션 스토리지로 도입**

### 이유
1. **성능**: In-memory 기반으로 평균 5ms 응답시간
2. **확장성**: 샤딩으로 수평 확장 가능
3. **안정성**: Replica를 통한 자동 페일오버
4. **경험**: 팀 내 Redis 운영 경험 보유

## 대안

### 대안 1: Memcached
**장점**: 단순한 아키텍처, Redis보다 약간 빠른 순수 캐싱 성능
**단점**: 데이터 영속성 미지원, 복제 기능 없음, 데이터 구조 제한적
**왜 선택하지 않았는가**: 서버 재시작 시 모든 세션 유실 위험이 너무 큼

### 대안 2: MySQL 인덱싱 최적화
**장점**: 추가 인프라 불필요, 기존 코드 변경 최소화
**단점**: 50ms 목표 달성 어려움, 동시 접속자 10만명 지원 불가능
**왜 선택하지 않았는가**: 성능 목표를 달성할 수 없음

### 대안 3: AWS ElastiCache (관리형 Redis)
**장점**: 운영 부담 최소화, 자동 백업 및 패치
**단점**: 월 비용 $800 (예산 초과), 벤더 종속성
**왜 선택하지 않았는가**: 현재 예산으로는 불가능, 향후 재검토

## 결과

### 긍정적 결과
- 세션 조회 응답시간 300ms → 5ms (98% 개선)
- 피크 시간대 DB CPU 사용률 80% → 20%
- 동시 접속자 처리 용량 10배 증가

### 부정적 결과 (Trade-offs)
- Redis 클러스터 운영 복잡도 증가
- 메모리 용량 제한 (64GB)
- 팀원 Redis 운영 교육 필요

### 중립적 결과
- 월 인프라 비용 $400 증가 (예산 내)
- 모니터링 대상 증가 (Redis 6대 추가)

## 구현 계획

### 마이그레이션 전략
- **Phase 1: 준비 (1주)** — Redis 클러스터 구축, 마이그레이션 스크립트, 모니터링 설정
- **Phase 2: 이중 쓰기 (3일)** — MySQL + Redis 동시 쓰기, 데이터 정합성 검증
- **Phase 3: 읽기 전환 (2일)** — Redis에서 읽기, MySQL에서 폴백
- **Phase 4: 완전 전환 (2일)** — Redis에서만 읽기/쓰기

### 롤백 계획
- Phase 3까지는 즉시 MySQL 전환 가능
- Phase 4에서도 24시간 내 MySQL 복구 가능

## 검증 방법

### 성공 지표
- P95 응답시간 < 50ms ✓
- 에러율 < 0.1% ✓
- 동시 접속자 10만명 부하 테스트 통과 ✓
- 1주일 동안 세션 유실 0건 ✓

## 업데이트 이력
- 2024-11-01: 초안 작성 (김철수)
- 2024-11-08: 팀 리뷰 및 피드백 반영
- 2024-11-15: 최종 승인 (CTO)
- 2024-12-01: 구현 완료 및 검증 결과 업데이트
```

## 실전 예시 2: 프론트엔드 상태 관리 라이브러리

```markdown
# ADR-012: 전역 상태 관리로 Zustand 도입

날짜: 2024-12-10
상태: 승인됨
의사결정자: 이민수(Frontend Lead), 팀 전체

## 컨텍스트

### 배경
현재 Context API + useReducer로 전역 상태 관리 중:
- 상태 업데이트 시 불필요한 리렌더링 발생
- 중첩된 Context Provider 가독성 저하
- 비동기 로직 처리 복잡함
- DevTools 지원 부족

### 제약 조건
- 번들 사이즈 증가 < 10KB
- 학습 곡선 낮아야 함
- TypeScript 타입 안전성 보장

## 의사결정

### 선택한 방안
**Zustand를 전역 상태 관리 라이브러리로 도입**

### 이유
1. **성능**: Selector 기반 자동 최적화
2. **단순성**: Boilerplate 최소화
3. **경량**: 2.9KB (gzipped)
4. **유연성**: 미들웨어로 확장 가능

## 대안

### 대안 1: Redux Toolkit
**장점**: 업계 표준, 풍부한 생태계, Redux DevTools
**단점**: 번들 사이즈 큼 (11KB), Boilerplate 여전히 많음
**왜 선택하지 않았는가**: 단순한 전역 상태에는 과도한 복잡도

### 대안 2: Jotai
**장점**: 경량 (3.4KB), Atom 기반 유연성
**단점**: 상대적으로 적은 생태계, 팀 내 경험자 없음
**왜 선택하지 않았는가**: Zustand의 단순함이 더 적합

## 결과

### 긍정적 결과
- 리렌더링 횟수 60% 감소
- 번들 사이즈 영향 최소 (2.9KB)
- 코드 가독성 향상

### 부정적 결과
- Redux보다 작은 커뮤니티
- 팀원 학습 시간 필요 (1주)

## 구현 계획
- **Phase 1 (1개월)**: 신규 기능에 Zustand 적용
- **Phase 2 (2개월)**: 기존 코드 점진적 전환
- **Phase 3 (1개월)**: Context API 완전 제거

## 업데이트 이력
- 2024-12-01: 초안 작성 (이민수)
- 2024-12-10: 최종 승인 (Tech Lead)
- 2025-01-15: Phase 1 완료
```

## ADR 작성 베스트 프랙티스

### 1. 제목은 간결하고 명확하게
- ❌ "데이터베이스 관련 개선"
- ✅ "읽기 성능 개선을 위한 읽기 전용 Replica 도입"

### 2. 컨텍스트는 충분히 자세히
- 현재 문제를 모르는 사람도 이해할 수 있게
- 숫자와 데이터로 문제를 구체화
- "왜 지금 이 결정이 필요한가?" 명확히

### 3. 대안은 정직하게
- 진지하게 고려한 대안만 작성
- 대안의 장단점을 공정하게 평가
- "왜 선택하지 않았는가"를 명확히

### 4. 결과는 솔직하게
- 긍정적 결과만 나열하지 않기
- Trade-off를 명확히 인정
- 예상되는 문제점도 사전 명시

### 5. 구체적인 실행 계획
- "누가, 언제, 무엇을" 명확히
- 마일스톤과 체크포인트 설정
- 롤백 계획 필수 포함

## ADR 상태 관리

### 상태 종류
- **제안됨 (Proposed)**: 초안 작성, 검토 중
- **승인됨 (Accepted)**: 팀 승인, 구현 예정/진행 중
- **기각됨 (Rejected)**: 검토 후 채택하지 않기로 결정
- **폐기됨 (Deprecated)**: 더 이상 유효하지 않음
- **대체됨 (Superseded by ADR-XXX)**: 새로운 ADR로 대체

### 상태 전환 예시
```
제안됨 → 승인됨 → 구현 → (시간 경과) → 대체됨 (ADR-025로)
       ↓
     기각됨
```

## ADR 리뷰 프로세스

### 1. 작성 단계
1. 작성자가 초안 작성
2. Draft PR 생성
3. 관련 팀원들에게 리뷰 요청

### 2. 리뷰 단계
1. 컨텍스트 충분한가?
2. 대안 검토가 충분한가?
3. 결과(Trade-off) 평가가 현실적인가?
4. 구현 계획이 실현 가능한가?

### 3. 승인 단계
1. 모든 리뷰어 승인 (최소 2명)
2. Tech Lead 최종 승인
3. PR Merge
4. 팀 공유 (Slack, 위클리 미팅)

## 자주 묻는 질문

### Q1: 모든 기술 결정을 ADR로 작성해야 하나요?
**A**: 아니오. 다음과 같은 **중요한 결정만** 작성합니다:
- 프로젝트 전체에 영향을 미치는 결정
- 변경하기 어려운 결정 (데이터베이스, 아키텍처)
- 많은 비용이 드는 결정
- Trade-off가 명확한 결정

간단한 라이브러리 선택이나 코딩 컨벤션은 ADR 불필요.

### Q2: ADR이 너무 길어지는데 괜찮나요?
**A**: 괜찮습니다. 충분한 컨텍스트가 중요합니다. 간결함보다 명확함 우선.

### Q3: 과거 결정을 수정해도 되나요?
**A**: 원본 ADR는 수정하지 않습니다.
- 새로운 ADR 작성 (ADR-XXX: yyy 대체)
- 기존 ADR 상태를 "대체됨"으로 변경
- 왜 변경했는지를 새 ADR에 명시

### Q4: ADR를 팀에 어떻게 도입하나요?
**A**: 점진적으로 시작하세요:
1. 템플릿 공유 및 설명
2. 다음 중요한 결정부터 ADR 작성
3. 팀 리뷰 문화 정착
4. 주요 결정 시 ADR 작성 습관화

## 정리

ADR은 단순한 문서가 아니라:
- **소통 도구**: 팀의 합의를 명확히
- **지식 자산**: 조직의 기술 히스토리
- **의사결정 프레임워크**: 체계적인 평가 방법
