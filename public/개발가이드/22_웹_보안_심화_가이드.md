> **"보안은 기능이 아니라 제품의 전제 조건이다. 보이지 않는 곳에서의 방어 체계가 서비스의 가치를 지킨다."**
> 본 가이드는 현대 프론트엔드 환경에서 발생할 수 있는 주요 보안 위협과 그에 대한 철저한 방어 표준을 제시합니다.

## 1. XSS (Cross-Site Scripting) 방어

사용자의 입력값이 스크립트로 실행되는 것을 방지합니다.

### 1.1 CSP (Content Security Policy) 설정
가장 강력한 방어 수단입니다. 브라우저에게 "이 도메인의 스크립트만 실행하라"고 지시합니다.

```html
<!-- index.html 예시 (meta 태그 방식) -->
<meta http-equiv="Content-Security-Policy" content="
  default-src 'self';
  script-src 'self' https://trusted-api.com;
  style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
  img-src 'self' data: https://images.unsplash.com;
  connect-src 'self' https://api.myserver.com;
">
```

### 1.2 데이터 새니타이징 (Sanitization)
`dangerouslySetInnerHTML` 사용은 원칙적으로 금지하며, 불가피한 경우 `DOMPurify`를 사용합니다.

```typescript
import DOMPurify from "dompurify";

const cleanHTML = DOMPurify.sanitize(userInputHTML);
return <div dangerouslySetInnerHTML={{ __html: cleanHTML }} />;
```

## 2. 안전한 토큰 관리 (Authentication)

JWT나 세션 토큰을 `localStorage`에 저장하는 것은 지양해야 합니다.

### 2.1 HttpOnly + Secure 쿠키 전략
토큰은 JavaScript에서 접근할 수 없는 **HttpOnly 쿠키**에 저장하여 XSS를 통한 탈취를 막습니다.

*   **HttpOnly**: JS 접근 금지
*   **Secure**: HTTPS 연결에서만 전송
*   **SameSite**: Lax 또는 Strict로 설정하여 CSRF 방어

### 2.2 In-memory 토큰 (Silent Refresh)
Access Token은 메모리에 변수로만 유지하고, Refresh Token을 쿠키에 담아 만료 시마다 자동으로 재발급받는 패턴을 권장합니다.

---

## 3. CSRF (Cross-Site Request Forgery) 방어

브라우저가 쿠키를 자동으로 전송하는 특성을 악용한 공격을 막습니다.

*   **SameSite=Lax**: 현대 브라우저의 기본값이지만, 명시적으로 설정하여 외부 사이트에서의 요청을 제한합니다.
*   **Custom Header**: API 요청 시 `X-Requested-With`와 같은 커스텀 헤더를 포함하면 브라우저의 CORS 정책에 의해 다른 사이트에서의 요청이 차단됩니다.

## 4. 보안 점검 자동화 (CI/CD 연계)

보안은 사람이 매번 체크하기 어렵습니다. 도구를 활용하세요.

1.  **npm audit**: 주기적으로 취약점이 발견된 패키지를 업데이트합니다.
2.  **Snyk**: 코드와 의존성의 보안 취약점을 실시간으로 모니터링합니다.
