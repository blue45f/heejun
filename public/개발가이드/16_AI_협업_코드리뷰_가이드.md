## 1. 코드리뷰 원칙

### 1.1 리뷰의 목표

1. **품질 보증**: 버그, 보안 취약점, 성능 문제 사전 탐지
2. **지식 공유**: 팀 전체의 코드 이해도 향상
3. **일관성 유지**: 코딩 표준 및 아키텍처 패턴 준수
4. **성장**: 리뷰어와 작성자 모두의 역량 향상

> **주니어 개발자를 위한 팁**: 코드리뷰는 "틀린 것을 찾는" 과정이 아니라 "더 나은 코드를 함께 만드는" 협업 과정이다. 리뷰를 받는 것이 곧 배움의 기회이고, 리뷰를 하는 것도 코드를 깊이 읽는 훈련이 된다.

### 1.2 리뷰 에티켓

| 역할 | 해야 할 것 | 하지 말아야 할 것 |
|------|------------|-------------------|
| 리뷰어 | 구체적 개선안 제시, 칭찬 포함, 질문 형태 피드백 | 인신공격, 모호한 "이상함", 취향 강요 |
| 작성자 | 변경 의도 설명, 리뷰 코멘트 24시간 내 응답 | 방어적 태도, 리뷰 무시, 과도하게 큰 PR |

**좋은 코멘트 vs 나쁜 코멘트 예시:**

```
// 나쁜 코멘트 - 모호하고 비건설적
"이 코드 이상해요"
"왜 이렇게 했어요?"

// 좋은 코멘트 - 구체적이고 건설적
"suggestion: 이 부분에서 useMemo를 적용하면 리렌더링을 방지할 수 있을 것 같아요.
현재 코드는 매 렌더링마다 새 배열을 생성하고 있어서, 하위 컴포넌트가 불필요하게
리렌더링될 수 있습니다."

// 좋은 코멘트 - 칭찬과 함께 제안
"praise: 에러 바운더리 적용이 깔끔하네요!
question: fallback UI에 '다시 시도' 버튼도 추가하면 어떨까요?"
```

### 1.3 PR 크기 가이드라인

| 크기 | 변경 라인 수 | 리뷰 시간 목표 | 권장 |
|------|-------------|----------------|------|
| XS | ~50줄 | 10분 이내 | 최적 |
| S | ~200줄 | 30분 이내 | 권장 |
| M | ~400줄 | 1시간 이내 | 허용 |
| L | ~800줄 | 분할 권장 | 주의 |
| XL | 800줄+ | 반드시 분할 | 금지 |

> **왜 작은 PR이 중요한가?** 연구에 따르면 200줄 이하 PR은 결함 발견율이 70% 이상이지만, 400줄을 넘으면 30% 이하로 떨어진다. 리뷰어의 집중력 한계 때문이다. 큰 기능은 [섹션 4의 Stacked PRs](#4-stacked-prs-20-graphite-cli)로 분할하자.

## 2. AI 리뷰 파이프라인 2.0

### 2.1 3단계 리뷰 아키텍처

```
PR 생성 -> [1단계: 자동] -> [2단계: 심화] -> [3단계: 아키텍처] -> Merge
              CodeRabbit       Greptile /        Claude Code Review
              (즉시)           Cursor BugBot     (요청 시)
                               (5분 이내)
```

| 단계 | 도구 | 범위 | 트리거 |
|------|------|------|--------|
| 1단계 자동 | CodeRabbit | 스타일, 버그 패턴, 보안 기본, 복잡도 (멀티 SCM 지원) | PR 생성 시 자동 |
| 2단계 심화 | Greptile / Cursor BugBot / GitHub Copilot Agent | 전체 코드베이스 인덱싱 기반 심층 분석 | 1단계 통과 후 자동 |
| 3단계 아키텍처 | Claude Code Review (Sonnet 4.7) | 설계 적합성, 대안 제시, RFC 준수 여부, 서브에이전트 분담 리뷰 | 라벨 `needs-arch-review` 또는 수동 |

> **각 단계의 역할을 쉽게 설명하면:**
> - **1단계(CodeRabbit)**: "맞춤법 검사기" 같은 역할. 누락된 세미콜론, 위험한 패턴, 보안 취약점 등 기계적으로 잡을 수 있는 것들을 자동 탐지한다. GitHub/GitLab/Bitbucket/Azure DevOps 등 멀티 SCM을 지원하는 것이 강점이며, 2026년 실측 기준 PR당 가장 많은 findings(약 5.6/PR)를 게시한다.
> - **2단계(Greptile / Cursor BugBot)**: "경험 많은 동료"가 로직을 한 번 훑는 단계. **Greptile**($30/seat)은 전체 코드베이스를 인덱싱하여 깊은 컨텍스트 기반 버그 탐지에 강하다(자체 벤치 약 82% catch rate, 단 false positive도 함께 증가). **Cursor BugBot**($40/seat)은 Cursor IDE 사용 팀에 적합하며 false positive율이 약 4.8%로 낮다. GitHub Copilot Agent(2026년부터 JetBrains/VS Code GA)도 동급 선택지다.
> - **3단계(Claude Code Review)**: "시니어 아키텍트"에게 설계를 리뷰 받는 단계. Claude Code의 서브에이전트(security-reviewer, architecture-reviewer 등)로 리뷰를 병렬 분담시킬 수 있다. RFC 문서와의 일관성, 아키텍처 패턴 준수 여부, 대안 제시 등을 수행한다. ([15. RFC 프로세스](./15_RFC_의사결정_프로세스.md), [18. AI 워크플로우](./18_AI_개발_워크플로우_종합.md) 참고)

#### 2026년 AI 코드리뷰 도구 실측 비교 표

| 도구 | 강점 | 약점 | 가격 (seat/월) | 추천 사용처 |
|------|------|------|---------------|------------|
| **CodeRabbit** | 멀티 SCM 지원, 가장 많은 findings, one-click diff 약 68% | 신호/소음비 보통 | $15~$30 | 기본 리뷰 자동화, 멀티 SCM 환경 |
| **Greptile** | 코드베이스 전체 인덱싱, 깊은 컨텍스트, 정밀도 우수 | False positive 다소 발생 | $30 | 복잡한 모노레포, 깊은 버그 탐지 필요 |
| **Cursor BugBot** | 낮은 false positive(4.8%), Cursor 통합 | Cursor 사용 팀만 효과 극대화 | $40 | Cursor IDE 메인 팀 |
| **GitHub Copilot Agent** | GitHub 네이티브 통합, JetBrains/VS Code GA | 깊은 추론은 Claude 대비 약함 | $10~$39 | GitHub 중심 워크플로우 |
| **Claude Code Review** | 200K 컨텍스트, 서브에이전트 분담 리뷰, 아키텍처 추론 | IDE 인라인 통합 제한적 | 사용량 기반 | 아키텍처/설계 리뷰, RFC 준수 검증 |

> 출처: 2026년 실측 비교 자료(146 PR / 679 findings, 3주 병렬 운영) 기준. 단일 도구로는 모든 약점을 보완할 수 없으므로, 1단계 CodeRabbit + 2단계 Greptile 또는 BugBot + 3단계 Claude의 조합이 가장 효과적이다.

### 2.2 AI 리뷰 파이프라인 구현

```typescript
// ai-review-pipeline.ts
// AI 리뷰 파이프라인의 각 단계를 정의하는 인터페이스
interface ReviewStage {
  name: string;
  tool: 'coderabbit' | 'copilot' | 'claude';
  trigger: 'auto' | 'manual' | 'label'; // auto: PR 생성 시 자동, label: 특정 라벨 부착 시
  timeout: number; // 밀리초 단위 타임아웃
  requiredForMerge: boolean; // true면 이 단계를 통과해야 머지 가능
}

// 파이프라인 전체 설정
interface PipelineConfig {
  stages: ReviewStage[];
  skipConditions: Array<{
    filePatterns: string[]; // glob 패턴으로 파일 매칭
    reason: string;
  }>;
  escalationRules: Array<{
    condition: string;
    escalateTo: string; // 알림을 보낼 팀
  }>;
}

const REVIEW_PIPELINE: PipelineConfig = {
  stages: [
    {
      name: '자동 린트/보안 검사',
      tool: 'coderabbit',
      trigger: 'auto',
      timeout: 120_000, // 2분
      requiredForMerge: true,
    },
    {
      name: '심화 로직 분석',
      tool: 'copilot',
      trigger: 'auto',
      timeout: 300_000, // 5분
      requiredForMerge: true,
    },
    {
      name: '아키텍처 리뷰',
      tool: 'claude',
      trigger: 'label', // 'needs-arch-review' 라벨이 있을 때만 실행
      timeout: 600_000, // 10분
      requiredForMerge: false, // 선택사항 - 모든 PR에 아키텍처 리뷰를 강제하지 않음
    },
  ],
  skipConditions: [
    {
      filePatterns: ['**/*.md', '**/*.json', '**/package.json'],
      reason: '문서/설정 파일만 변경된 PR은 1단계만 실행',
    },
    {
      filePatterns: ['**/*.lock'],
      reason: '락파일 변경은 AI 리뷰 스킵',
    },
  ],
  escalationRules: [
    {
      condition: 'security 관련 파일 변경 시',
      escalateTo: 'security-team',
    },
    {
      condition: 'DB 마이그레이션 포함 시',
      escalateTo: 'dba-team',
    },
    {
      condition: '공개 API 변경 시',
      escalateTo: 'api-team',
    },
  ],
};

// AI 리뷰 코멘트의 구조
interface AiReviewComment {
  path: string; // 파일 경로
  line: number; // 해당 라인 번호
  severity: 'critical' | 'suggestion' | 'nitpick' | 'praise';
  body: string; // 코멘트 내용
  stage: string; // 어떤 단계에서 생성되었는지
  tool: string; // 어떤 도구가 생성했는지
  confidence: number; // 0~1 사이의 신뢰도 (낮으면 사람이 재확인 필요)
}

// 파이프라인 실행 함수
async function runReviewPipeline(
  prNumber: number,
  changedFiles: string[],
  config: PipelineConfig,
): Promise<AiReviewComment[]> {
  const allComments: AiReviewComment[] = [];

  // 스킵 조건 평가: 문서만 변경된 PR 등은 일부 단계를 건너뜀
  const shouldSkipStages = evaluateSkipConditions(changedFiles, config.skipConditions);

  for (const stage of config.stages) {
    if (shouldSkipStages.includes(stage.name)) {
      continue;
    }

    // 라벨 기반 트리거는 해당 라벨이 있는지 확인
    if (stage.trigger === 'label') {
      const hasLabel = await checkPrLabel(prNumber, 'needs-arch-review');
      if (!hasLabel) continue;
    }

    const comments = await executeStage(stage, prNumber, changedFiles);
    allComments.push(...comments);

    // critical 이슈 발견 시 에스컬레이션 (예: 보안팀에 알림)
    const hasCritical = comments.some((c) => c.severity === 'critical');
    if (hasCritical) {
      await applyEscalationRules(prNumber, comments, config.escalationRules);
    }
  }

  return allComments;
}

// 스킵 조건 평가: 변경된 파일이 모두 스킵 대상 패턴에 해당하는지 확인
function evaluateSkipConditions(
  changedFiles: string[],
  conditions: PipelineConfig['skipConditions'],
): string[] {
  const skipped: string[] = [];

  for (const condition of conditions) {
    const allMatch = changedFiles.every((file) =>
      condition.filePatterns.some((pattern) => matchGlob(file, pattern)),
    );
    if (allMatch) {
      skipped.push(condition.reason);
    }
  }

  return skipped;
}
```

### 2.3 GitHub Actions: AI 리뷰 워크플로우

```yaml
# .github/workflows/ai-review.yml
name: AI Review Pipeline
on:
  pull_request:
    types: [opened, synchronize, labeled]

permissions:
  pull-requests: write
  contents: read

jobs:
  stage-1-auto:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: CodeRabbit Auto Review
        uses: coderabbitai/ai-pr-reviewer@v3
        with:
          review_level: detailed
          language: ko

  stage-2-deep:
    needs: stage-1-auto
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      # 2026년 기준 선택지: Greptile, Cursor BugBot, GitHub Copilot Agent 중 1개 사용
      # 아래는 Greptile 예시 (코드베이스 전체 인덱싱 기반 심층 분석)
      - name: Greptile Deep Review
        uses: greptileai/code-review-action@v1
        with:
          api_key: ${{ secrets.GREPTILE_API_KEY }}
          include_test_coverage: true
          # 모노레포의 경우 인덱싱 범위 지정으로 비용 최적화
          repo_paths: "src/,packages/"

  stage-3-architecture:
    if: contains(github.event.pull_request.labels.*.name, 'needs-arch-review')
    needs: stage-2-deep
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      # Claude Agent SDK 기반 서브에이전트 분담 리뷰
      # security-reviewer / architecture-reviewer / performance-reviewer를 병렬 실행하여
      # 각각의 결과를 단일 코멘트로 통합한다.
      - name: Claude Architecture Review (Subagent)
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          npx tsx scripts/claude-arch-review.ts \
            --pr=${{ github.event.pull_request.number }} \
            --depth=architecture \
            --subagents=security,architecture,performance
```

### 2.4 CodeRabbit 설정 예시 (.coderabbit.yaml)

프로젝트 루트에 `.coderabbit.yaml`을 추가하면 CodeRabbit의 동작을 상세히 제어할 수 있다.

```yaml
# .coderabbit.yaml
# CodeRabbit 설정 파일 - 프로젝트 루트에 위치
language: "ko" # 리뷰 코멘트를 한국어로 생성
reviews:
  # 자동 리뷰 활성화
  auto_review:
    enabled: true
    # draft PR은 리뷰하지 않음 (아직 작업 중이므로)
    drafts: false
    # 특정 경로만 리뷰
    path_filters:
      - "src/**"
      - "!src/**/*.test.ts"  # 테스트 파일은 제외
      - "!**/*.generated.ts" # 자동 생성 파일 제외
  # 리뷰 관점 설정
  review_comment:
    # Conventional Comments 형식 사용
    format: "conventional"
    # critical 이슈만 인라인 코멘트, 나머지는 요약에 포함
    inline_threshold: "suggestion"
  # 보안 검사 강화
  security:
    enabled: true
    # 하드코딩된 시크릿 탐지
    detect_secrets: true
```

> **주니어 개발자 가이드**: `.coderabbit.yaml` 파일은 팀 전체의 AI 리뷰 품질을 결정한다. 처음에는 위 기본 설정으로 시작하고, 팀에서 "이런 건 안 잡아줬으면" 또는 "이런 것도 잡아줬으면" 하는 피드백이 쌓이면 점진적으로 조정하자.

## 3. AI 프롬프트 시나리오 (리뷰어/작성자)

### 3.1 리뷰어 시나리오

```
[시나리오 1] "이 PR의 핵심 변경점 3줄 요약해줘"

프롬프트:
"다음 PR diff를 분석하여 핵심 변경점을 3줄로 요약해주세요.
각 줄은 한 문장이며, 가장 중요한 변경부터 나열해주세요.
형식:
1. [카테고리] 변경 내용
2. [카테고리] 변경 내용
3. [카테고리] 변경 내용

카테고리: 기능추가, 버그수정, 리팩토링, 성능, 보안, 테스트, 설정

[diff 붙여넣기]"
```

```
[시나리오 2] "이 코드에서 잠재적 문제를 찾아줘"
```

## 4. Stacked PRs 2.0 (Graphite CLI)

### 4.1 Stacked PRs 개요

대규모 변경을 논리적 단위로 분할하여 순차적으로 리뷰한다. 각 PR은 이전 PR에 의존하며, Graphite CLI로 스택을 관리한다.

```
main
  +-- feature/auth-types        (PR #1: 타입 정의)
       +-- feature/auth-api     (PR #2: API 레이어)
            +-- feature/auth-ui (PR #3: UI 컴포넌트)
```

**왜 Stacked PRs를 사용하는가?**

일반적인 개발 흐름에서 인증 기능 전체를 하나의 PR로 올리면 1000줄이 넘어간다. 리뷰어는 전체를 한 번에 파악해야 하므로 피로도가 높고, 리뷰 품질이 떨어진다. Stacked PRs는 이것을 3개의 200~300줄짜리 PR로 분할하여 각각 독립적으로 리뷰할 수 있게 한다.

### 4.2 Graphite CLI 핵심 명령어

```bash
# === 스택 생성 ===
gt branch create feature/auth-types    # 첫 번째 브랜치
# ... 타입 정의 작업 후 커밋
gt branch create feature/auth-api      # 두 번째 브랜치 (자동으로 위에 쌓임)
# ... API 레이어 작업 후 커밋
gt branch create feature/auth-ui       # 세 번째 브랜치
# ... UI 컴포넌트 작업 후 커밋

# === 스택 확인 ===
gt log                                 # 현재 스택의 모든 브랜치와 커밋 시각화
gt log --all                           # 모든 스택 확인

# === 스택 전체 PR 제출 ===
gt stack submit                        # 스택의 모든 브랜치를 PR로 제출
gt stack submit --draft                # 드래프트로 제출
gt stack submit --reviewers="user1"    # 리뷰어 지정

# === 스택 중간 브랜치 수정 후 리베이스 ===
gt branch checkout feature/auth-api    # 중간 브랜치로 이동
# ... 리뷰 반영 수정 후 커밋
gt stack restack                       # 이후 브랜치들 자동 리베이스

# === 스택 네비게이션 ===
gt branch up                           # 스택에서 위로 이동
gt branch down                         # 스택에서 아래로 이동
gt branch top                          # 스택 최상단으로 이동
gt branch bottom                       # 스택 최하단으로 이동

# === 머지 후 정리 ===
gt repo sync                           # main pull + 머지된 브랜치 정리
```

**실전 흐름 예시: 인증 기능 구현**

### 4.3 스택 리뷰 전략

```typescript
// stacked-pr-review-strategy.ts
// 스택 크기와 리뷰 방식을 정의하는 인터페이스
interface StackReviewStrategy {
  stackSize: number; // 스택 내 PR 개수
  reviewOrder: 'bottom-up' | 'top-down' | 'parallel';
  perPrPolicy: {
    maxChangedLines: number; // PR당 최대 변경 라인 수
    requiredApprovals: number;
    mergeOrder: 'sequential' | 'batch'; // 순차 머지 vs 일괄 머지
  };
}

const STACK_REVIEW_STRATEGIES: Record<string, StackReviewStrategy> = {
  // 3개 이하 스택: 가장 일반적인 케이스
  small: {
    stackSize: 3,
    reviewOrder: 'bottom-up', // 기반 PR부터 리뷰
    perPrPolicy: {
      maxChangedLines: 300,
      requiredApprovals: 1,
      mergeOrder: 'sequential', // 하나씩 순서대로 머지
    },
  },
  // 4~10개 스택: 대규모 리팩토링이나 새 기능
  large: {
    stackSize: 10,
    reviewOrder: 'bottom-up',
    perPrPolicy: {
      maxChangedLines: 200, // 스택이 크면 각 PR은 더 작게 유지
      requiredApprovals: 1,
      mergeOrder: 'sequential',
    },
  },
};

// 스택 리뷰 가이드라인:
// 1. 항상 bottom-up으로 리뷰 (기반 PR부터)
// 2. 각 PR은 독립적으로 이해 가능해야 함
// 3. 각 PR의 커밋 메시지가 해당 PR의 목적을 명확히 설명
// 4. 기반 PR이 승인되어야 다음 PR 리뷰 시작
// 5. 중간 PR 수정 시 gt stack restack으로 상위 브랜치 자동 업데이트

// PR 제목과 설명을 자동 생성하는 헬퍼 함수
interface StackPrTemplate {
  title: string;
  body: string;
}

function generateStackPrDescription(
  stackPosition: number,
  totalInStack: number,
  branchName: string,
  dependsOn?: number,
): StackPrTemplate {
  return {
    title: `[${stackPosition}/${totalInStack}] ${branchName}`,
    body: `## Stack Info
- **Position**: ${stackPosition} of ${totalInStack}
- **Depends on**: ${dependsOn ? `#${dependsOn}` : 'main'}
- **Review order**: 이 PR은 ${dependsOn ? `#${dependsOn} 승인 후` : '바로'} 리뷰해주세요.

---

## Changes
(변경 내용 기술)

## Context
이 PR은 스택의 일부입니다. 전체 스택 구조:
\`gt log\` 명령으로 확인하세요.`,
  };
}
```

## 5. 멀티 베타 환경별 리뷰 정책

### 5.1 환경별 리뷰 정책 매트릭스

| 환경 | AI 리뷰 | 사람 리뷰 | 필수 승인 수 | 자동 머지 |
|------|---------|-----------|-------------|-----------|
| Preview | 자동 AI만 (1-2단계) | 불필요 | 0 | 가능 |
| Staging | 자동 AI + 수동 | 팀원 1명 | 1 | 조건부 |
| Production | 자동 AI 전체 | 팀원 2명 + 테크리드 | 2+ | 불가 |

> **환경별 정책의 이유**: Preview 환경은 개발자가 자유롭게 실험하는 공간이므로 리뷰 문턱을 낮춘다. Staging은 QA 팀이 테스트하는 환경이므로 최소 1명의 사람 리뷰가 필요하다. Production은 실 사용자에게 영향을 주므로 가장 엄격한 정책을 적용한다. 배포 프로세스 전체는 [14. 배포 프로세스 체크리스트](./14_배포_프로세스_체크리스트.md)를 참고하자.

### 5.2 PR별 Preview URL 자동 포함

```typescript
// preview-url-commenter.ts
// PR에 Preview 배포 URL을 자동으로 코멘트하는 시스템
interface PreviewDeployment {
  prNumber: number;
  url: string;
  environment: string;
  status: 'deploying' | 'ready' | 'failed';
  deployedAt: string;
  expiresAt: string;
  commitSha: string;
}

async function postPreviewComment(
  prNumber: number,
  deployment: PreviewDeployment,
): Promise<void> {
  const statusLabel: Record<PreviewDeployment['status'], string> = {
    deploying: '[Deploying]',
    ready: '[Ready]',
    failed: '[Failed]',
  };

  // 마크다운 테이블 형태로 배포 정보를 보기 좋게 정리
  const comment = `## Preview Deployment ${statusLabel[deployment.status]}

| 항목 | 값 |
|------|-----|
| **URL** | [${deployment.url}](${deployment.url}) |
| **환경** | ${deployment.environment} |
| **커밋** | \`${deployment.commitSha.slice(0, 7)}\` |
| **배포 시간** | ${deployment.deployedAt} |
| **만료 예정** | ${deployment.expiresAt} |

### 확인 사항
- [ ] 주요 기능 동작 확인
- [ ] 반응형 레이아웃 확인
- [ ] 에러 상태 확인
- [ ] 접근성 확인 (키보드 탐색, 스크린리더)

> 이 환경은 ${deployment.expiresAt}에 자동 만료됩니다.`;

  // 기존 코멘트가 있으면 업데이트, 없으면 새로 생성
  await updateOrCreateComment(prNumber, 'preview-deployment', comment);
}

// 같은 식별자의 코멘트가 있으면 업데이트, 없으면 신규 생성
// HTML 주석 태그를 식별자로 사용하여 중복 코멘트를 방지
async function updateOrCreateComment(
  prNumber: number,
  identifier: string,
  body: string,
): Promise<void> {
  const existingComments = await listPrComments(prNumber);
  const existing = existingComments.find((c) =>
    c.body.includes(`<!-- ${identifier} -->`),
  );

  const taggedBody = `<!-- ${identifier} -->\n${body}`;

  if (existing) {
    await updateComment(existing.id, taggedBody);
  } else {
    await createComment(prNumber, taggedBody);
  }
}
```

```typescript
      'typecheck',

function getReviewPolicy(
  targetBranch: string,
): EnvironmentReviewPolicy {
  if (targetBranch === 'main' || targetBranch === 'production') {
    return ENVIRONMENT_POLICIES.find((p) => p.environment === 'production')!;
  }
  if (targetBranch.startsWith('staging') || targetBranch === 'develop') {
    return ENVIRONMENT_POLICIES.find((p) => p.environment === 'staging')!;
  }
  return ENVIRONMENT_POLICIES.find((p) => p.environment === 'preview')!;
}

// PR의 현재 상태를 정책과 비교하여 머지 가능 여부를 판단
function validateMergeReadiness(
  policy: EnvironmentReviewPolicy,
  prStatus: {
    aiReviewPassed: boolean;
    ciPassed: boolean;
    approvalCount: number;
    codeOwnerApproved: boolean;
    requiredTeamApprovals: Record<string, boolean>;
  },
): { canMerge: boolean; blockers: string[] } {
  const blockers: string[] = [];

  if (policy.aiReview.blockOnFailure && !prStatus.aiReviewPassed) {
    blockers.push('AI 리뷰를 통과하지 못했습니다.');
  }

  if (!prStatus.ciPassed) {
    blockers.push('CI 검사가 실패했습니다.');
  }

  if (policy.humanReview.required && prStatus.approvalCount < policy.humanReview.minApprovals) {
    blockers.push(
      `승인 ${prStatus.approvalCount}/${policy.humanReview.minApprovals}명 (부족)`,
    );
  }

  if (policy.humanReview.requireCodeOwner && !prStatus.codeOwnerApproved) {
    blockers.push('코드 오너의 승인이 필요합니다.');
  }

  for (const team of policy.humanReview.requiredTeams) {
    if (!prStatus.requiredTeamApprovals[team]) {
      blockers.push(`${team} 팀의 승인이 필요합니다.`);
    }
  }

  return {
    canMerge: blockers.length === 0,
    blockers,
  };
}
```

```typescript
// review-metrics-collector.ts
// 코드리뷰 품질을 정량적으로 측정하기 위한 메트릭 인터페이스
interface ReviewMetrics {
  period: { start: string; end: string };
  pullRequests: {
    total: number;
    merged: number;
    closed: number; // 머지 없이 닫힌 PR (리젝트 또는 대체됨)
    open: number;
    averageSize: number; // 평균 변경 라인 수
  };
  reviewTimes: {
    timeToFirstReview: number;       // 분 - PR 생성 후 첫 리뷰까지 걸린 시간
    timeToApproval: number;          // 분 - PR 생성 후 승인까지 걸린 시간
    timeToMerge: number;             // 분 - PR 생성 후 머지까지 (DORA Lead Time 구성 요소)
    reviewCycleCount: number;        // 리뷰 라운드 수 평균 (1이면 한 번에 통과)
  };
  participants: {
    activeReviewers: number; // 해당 기간 동안 리뷰에 참여한 사람 수
    averageReviewsPerPerson: number;
    reviewDistribution: Record<string, number>; // 리뷰어별 리뷰 횟수
  };
  aiMetrics: {
    aiCommentsTotal: number; // AI가 남긴 총 코멘트 수
    aiCommentsAccepted: number; // 작성자가 수용한 AI 코멘트
    aiCommentsDismissed: number; // 작성자가 무시한 AI 코멘트
    aiFalsePositiveRate: number; // 오탐율 (무시된 비율)
    timeSavedByAiMinutes: number; // AI 리뷰로 절약한 추정 시간
  };
  quality: {
    postMergeDefects: number; // 머지 후 발견된 결함 수
    revertRate: number; // 리버트된 PR 비율
    hotfixCount: number; // 핫픽스 횟수
  };
}

// GitHub API에서 가져온 PR 원시 데이터
interface GitHubPrData {
  number: number;
  createdAt: string;
  mergedAt: string | null;
  closedAt: string | null;
  additions: number;
  deletions: number;
  reviews: Array<{
    author: string;
    submittedAt: string;
    state: 'APPROVED' | 'CHANGES_REQUESTED' | 'COMMENTED';
  }>;
  comments: Array<{
    author: string;
    createdAt: string;
    isBot: boolean; // CodeRabbit, Copilot 등 봇 여부
    body: string;
  }>;
}

async function collectReviewMetrics(
  owner: string,
  repo: string,
  startDate: string,
  endDate: string,
): Promise<ReviewMetrics> {
  const prs = await fetchPullRequests(owner, repo, startDate, endDate);

  const merged = prs.filter((pr) => pr.mergedAt !== null);
  const closed = prs.filter((pr) => pr.closedAt !== null && pr.mergedAt === null);

  const reviewTimes = calculateReviewTimes(merged);
  const participants = calculateParticipantStats(prs);
  const aiMetrics = calculateAiMetrics(prs);

  return {
    period: { start: startDate, end: endDate },
    pullRequests: {
      total: prs.length,
      merged: merged.length,
      closed: closed.length,
      open: prs.length - merged.length - closed.length,
      averageSize: calculateAverageSize(prs),
    },
    reviewTimes,
    participants,
    aiMetrics,
    quality: await calculateQualityMetrics(owner, repo, startDate, endDate),
  };
}

function calculateReviewTimes(
  mergedPrs: GitHubPrData[],
): ReviewMetrics['reviewTimes'] {
  const firstReviewTimes: number[] = [];
  const approvalTimes: number[] = [];
  const mergeTimes: number[] = [];
  const cycleCounts: number[] = [];

  for (const pr of mergedPrs) {
    const created = new Date(pr.createdAt).getTime();
    const merged = new Date(pr.mergedAt!).getTime();

    // 첫 리뷰까지 시간 (봇 제외 - 사람 리뷰만 측정)
    const humanReviews = pr.reviews.filter(
      (r) => !pr.comments.some((c) => c.isBot && c.author === r.author),
    );
    if (humanReviews.length > 0) {
      const firstReview = new Date(humanReviews[0].submittedAt).getTime();
      firstReviewTimes.push((firstReview - created) / 60_000);
    }

    // 승인까지 시간
    const approvals = pr.reviews.filter((r) => r.state === 'APPROVED');
    if (approvals.length > 0) {
      const firstApproval = new Date(approvals[0].submittedAt).getTime();
      approvalTimes.push((firstApproval - created) / 60_000);
    }

    // 머지까지 시간 (DORA Lead Time 구성 요소)
    mergeTimes.push((merged - created) / 60_000);

    // 리뷰 라운드 수: CHANGES_REQUESTED 횟수 + 1
    // 예: 수정 요청 0번이면 1라운드(한 번에 통과), 2번이면 3라운드
    const changesRequested = pr.reviews.filter(
      (r) => r.state === 'CHANGES_REQUESTED',
    ).length;
    cycleCounts.push(changesRequested + 1);
  }

  return {
    timeToFirstReview: average(firstReviewTimes),
    timeToApproval: average(approvalTimes),
    timeToMerge: average(mergeTimes),
    reviewCycleCount: average(cycleCounts),
  };
}

// AI 코멘트의 수용/무시 비율을 측정하여 AI 리뷰의 실효성을 평가
function calculateAiMetrics(prs: GitHubPrData[]): ReviewMetrics['aiMetrics'] {
  let aiCommentsTotal = 0;
  let aiCommentsAccepted = 0;
  let aiCommentsDismissed = 0;

  for (const pr of prs) {
    const aiComments = pr.comments.filter((c) => c.isBot);
    aiCommentsTotal += aiComments.length;

    for (const comment of aiComments) {
      const wasAddressed = checkIfCommentAddressed(comment, pr);
      if (wasAddressed === 'accepted') aiCommentsAccepted++;
      if (wasAddressed === 'dismissed') aiCommentsDismissed++;
    }
  }

  const total = aiCommentsAccepted + aiCommentsDismissed;
  return {
    aiCommentsTotal,
    aiCommentsAccepted,
    aiCommentsDismissed,
    aiFalsePositiveRate: total > 0 ? aiCommentsDismissed / total : 0,
    // AI 코멘트 하나당 약 5분의 리뷰 시간을 절약한다고 추정
    timeSavedByAiMinutes: aiCommentsAccepted * 5,
  };
}

function average(values: number[]): number {
  if (values.length === 0) return 0;
  return Math.round(values.reduce((a, b) => a + b, 0) / values.length);
}
```

### 6.2 DORA Lead Time 측정

DORA 메트릭스는 소프트웨어 딜리버리 성과를 측정하는 업계 표준이다. 코드리뷰 시간은 Lead Time for Changes의 핵심 구성 요소이다.

```typescript
// dora-metrics.ts
interface DoraMetrics {
  // 배포 빈도: 얼마나 자주 프로덕션에 배포하는가
  deploymentFrequency: {
    value: number;
    unit: 'per-day' | 'per-week';
    rating: 'elite' | 'high' | 'medium' | 'low';
  };
  // 변경 리드 타임: 커밋부터 프로덕션 배포까지 걸리는 시간
  leadTimeForChanges: {
    value: number; // 분 단위
    rating: 'elite' | 'high' | 'medium' | 'low';
    breakdown: {
      codingTime: number; // 코딩 시간
      reviewTime: number; // 리뷰 대기 + 리뷰 시간
      deployTime: number; // 배포 파이프라인 시간
    };
  };
  // 변경 실패율: 배포 후 장애를 일으킨 비율
  changeFailureRate: {
    value: number; // 0~1 사이 비율
    rating: 'elite' | 'high' | 'medium' | 'low';
  };
  // 복구 시간: 장애 발생 후 복구까지 걸리는 시간
  timeToRestore: {
    value: number; // 분 단위
    rating: 'elite' | 'high' | 'medium' | 'low';
  };
}

// DORA 등급 기준 (2024 State of DevOps Report 기반)
function rateLeadTime(minutes: number): DoraMetrics['leadTimeForChanges']['rating'] {
  const hours = minutes / 60;
  if (hours < 24) return 'elite';      // 1일 미만
  if (hours < 24 * 7) return 'high';   // 1주 미만
  if (hours < 24 * 30) return 'medium'; // 1개월 미만
  return 'low';                         // 1개월 이상
}

function rateDeploymentFrequency(
  deploymentsPerWeek: number,
): DoraMetrics['deploymentFrequency']['rating'] {
  if (deploymentsPerWeek >= 7) return 'elite';    // 매일 이상
  if (deploymentsPerWeek >= 1) return 'high';     // 주 1회 이상
  if (deploymentsPerWeek >= 0.25) return 'medium'; // 월 1회 이상
  return 'low';
}

function rateChangeFailureRate(rate: number): DoraMetrics['changeFailureRate']['rating'] {
  if (rate <= 0.05) return 'elite';  // 5% 이하
  if (rate <= 0.10) return 'high';   // 10% 이하
  if (rate <= 0.15) return 'medium'; // 15% 이하
  return 'low';
}
```

> **팀 목표 설정 팁**: 처음에는 현재 수준을 측정하는 것부터 시작하자. "elite"를 목표로 하기보다, 매 분기 한 단계씩 개선하는 것이 현실적이다. 예를 들어 Lead Time이 현재 "medium"이라면 다음 분기에 "high"를 목표로 설정한다.

## 7. Conventional Comments 활용

리뷰 코멘트에 일관된 라벨을 붙이면 작성자가 코멘트의 의도와 중요도를 빠르게 파악할 수 있다. [Conventional Comments](https://conventionalcomments.org) 형식을 팀 표준으로 사용한다.

### 7.1 라벨 정의

| 라벨 | 의미 | 작성자 행동 |
|------|------|------------|
| `praise:` | 잘한 부분 칭찬 | 감사 표시 (선택) |
| `suggestion:` | 개선 제안 (선택 반영) | 반영 or 사유 설명 |
| `issue:` | 반드시 수정 필요 | 반드시 수정 후 재요청 |
| `question:` | 이해를 위한 질문 | 답변 필수 |
| `thought:` | 참고용 의견 | 읽기만 해도 OK |
| `nitpick:` | 사소한 스타일 지적 | 반영 권장 (블로킹 아님) |
| `todo:` | 이 PR은 아니지만 추후 개선 필요 | 이슈/TODO로 등록 |

## 8. 리뷰 체크리스트

### 8.1 기능 리뷰

- [ ] 요구사항을 정확히 구현했는가
- [ ] 엣지 케이스를 처리했는가 (빈 배열, null, 초과값 등)
- [ ] 에러 상태를 적절히 처리했는가 (네트워크 오류, 타임아웃, 4xx/5xx)
- [ ] 사용자 피드백 (로딩 스피너, 에러 메시지, 성공 토스트)이 적절한가
- [ ] 접근성 (키보드 탐색, 스크린리더) 고려했는가 - [19. 웹 접근성 가이드](./19_웹_접근성_가이드.md) 참고
- [ ] 국제화 (i18n) 처리했는가 - [23. 국제화 가이드](./23_국제화_가이드.md) 참고
- [ ] 반응형 디자인을 고려했는가 (모바일/태블릿/데스크탑)

### 8.2 코드 품질

- [ ] 네이밍이 의도를 명확히 전달하는가 (`d` 대신 `department`, `fn` 대신 `handleSubmit`)
- [ ] 함수/컴포넌트가 단일 책임을 가지는가
- [ ] 중복 코드가 없는가 (3번 이상 반복되면 추출)
- [ ] 타입이 정확하고 `any`를 사용하지 않았는가 - [01. TypeScript 심화 가이드](./01_TypeScript_심화_가이드.md) 참고
- [ ] 매직 넘버/문자열 대신 상수를 사용했는가 (`3000` 대신 `TIMEOUT_MS`)
- [ ] 불필요한 주석이 없고 코드 자체가 문서인가
- [ ] import 순서가 규칙에 맞는가 (external -> internal -> relative)

### 8.3 성능

- [ ] 불필요한 리렌더링이 없는가 (`React.memo`, `useMemo`, `useCallback` 적절 사용)
- [ ] 무거운 계산에 memoization을 적용했는가
- [ ] 이미지/에셋 최적화했는가 (WebP, lazy loading)
- [ ] 번들 크기에 영향을 주는 import가 있는가 (`import moment` 대신 `import dayjs`)
- [ ] 네트워크 요청이 효율적인가 (중복 요청, N+1 쿼리 없는지)
- [ ] 대량 데이터 렌더링 시 가상화를 적용했는가 - [08. 성능 최적화 가이드](./08_성능_최적화_가이드.md) 참고

- [ ] CSRF 방어가 되어 있는가
