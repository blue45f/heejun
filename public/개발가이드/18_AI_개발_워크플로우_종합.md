## 1. AI-First 개발 철학과 멀티 베타 전략

AI는 보조 도구가 아니라 **핵심 인프라**다. 코드의 70% 이상이 AI 협업으로 작성되며, 개발자는 "AI 오케스트레이터"로서 설계 의도를 전달하고 품질을 검증한다. 여기에 **멀티 베타 환경**을 결합하면 PR마다 독립 Preview가 생성되어 AI 리뷰와 배포 검증이 자동화된다.

### 핵심 원칙

| 원칙 | 설명 |
|------|------|
| **AI First** | 모든 작업의 시작점은 AI 도구. 직접 코딩 전에 AI에게 먼저 물어본다 |
| **검증 중심** | AI 생성 코드는 반드시 인간이 검증. 신뢰하되 확인한다 |
| **컨텍스트 최적화** | AI 품질은 컨텍스트 품질에 비례. 프로젝트 메타데이터를 체계적으로 관리 |
| **도구 조합** | 단일 AI에 의존하지 않고 각 도구의 강점을 조합 |
| **멀티 베타 통합** | PR마다 Preview 환경이 생성되고 AI가 해당 환경에서 자동 검증 수행 |
| **비용 인식** | AI 사용량을 추적하고 ROI를 측정 |
| **보안 우선** | AI에 전달하는 컨텍스트에 민감정보(API 키, 비밀번호 등) 포함 금지 |

### AI 도구 포지셔닝 맵

| 도구 | 주요 용도 | 강점 | 약점 | 월 비용 (팀) |
|------|-----------|------|------|-------------|
| **Claude Code** | 설계, 리팩토링, 디버깅, 멀티 에이전트 | 긴 컨텍스트(200K), 깊은 추론, 스킬 시스템 | IDE 통합 제한적 | $20~$100 |
| **GitHub Copilot** | 인라인 완성, 테스트, Agent | IDE 통합, Workspace Agent, 빠른 응답 | 복잡한 추론 약함 | $10~$39 |
| **Cursor** | 멀티파일 편집, Composer | 자연어 편집, .cursorrules, 코드베이스 인덱싱 | 비용 대비 제한적 모델 | $20~$40 |
| **CodeRabbit** | PR 리뷰 자동화, 보안 검사 | path_instructions, Preview URL 통합, 자동화 | 실시간 편집 불가 | $15~$30 |

### 도구 선택 의사결정 플로우

```
작업 유형 판단
├── 단순 코드 완성/자동완성 → GitHub Copilot (인라인)
├── 새 기능 설계/아키텍처 → Claude Code (깊은 추론)
├── 여러 파일 동시 편집 → Cursor (Composer)
├── PR 리뷰 자동화 → CodeRabbit (path_instructions)
├── 버그 디버깅/분석 → Claude Code (컨텍스트 분석)
└── 테스트 코드 생성 → Copilot (빠른 생성) + Claude Code (복잡한 케이스)
```

## 2. Claude Code 완벽 활용

### 2.1 CLAUDE.md 작성법

`CLAUDE.md`는 Claude Code가 프로젝트를 이해하는 핵심 컨텍스트 파일이다. 프로젝트 루트에 위치하며 세션 시작 시 자동으로 읽힌다. 잘 작성된 `CLAUDE.md`는 **매 프롬프트마다 반복되는 설명을 30% 이상 절감**시킨다.

```markdown
<!-- CLAUDE.md -->
# 프로젝트 컨텍스트

## 기술 스택
- Runtime: Node.js 22, TypeScript 5.7 strict
- Framework: React 19 + Next.js 15 (App Router)
- 상태관리: Zustand 5 + TanStack Query v5
- 스타일: Tailwind CSS 4 + CVA
- 테스트: Vitest 3 + Playwright 1.50
- 빌드: Turbopack (Next.js), pnpm 9

## 아키텍처 원칙
- Feature-Sliced Design (shared/entities/features/widgets/pages)
- Server Components 우선, Client Components는 최소화
- API 계층은 반드시 /src/shared/api/ 아래 위치
- 에러 바운더리로 모든 페이지 감싸기

## 코딩 규칙
- 함수형 컴포넌트만 사용, class 컴포넌트 금지
- named export만 사용 (default export 금지)
- 모든 함수에 JSDoc 또는 TSDoc 작성
- 매직 넘버 금지, 상수 파일로 분리
- any 타입 사용 금지, unknown + type guard 사용

## 멀티 베타 환경
- Preview URL 패턴: https://preview-{branch}.example.com
- Feature Flag: LaunchDarkly SDK 사용
- 환경 변수: NEXT_PUBLIC_DEPLOY_ENV (production|preview|development)

## 금지 사항
- console.log 커밋 금지 (logger 유틸 사용)
- 직접 DOM 조작 금지 (ref 제외)
- index.ts에 비즈니스 로직 금지
```

### 2.3 멀티 에이전트 워크플로우

Claude Code는 `--agent` 플래그나 스킬 시스템으로 멀티 에이전트 패턴을 구현할 수 있다. 각 에이전트가 고유한 역할을 맡아 파이프라인 형태로 협업한다.

```typescript
// claude-agents.config.ts
// Claude Code 멀티 에이전트 오케스트레이션 설정
// 각 에이전트는 의존성 그래프에 따라 순차/병렬 실행된다

/** 에이전트 파이프라인의 개별 작업 정의 */
interface AgentTask {
  /** 에이전트 식별자 (의존성 참조에 사용) */
  name: string;
  /** 에이전트에게 전달할 프롬프트 */
  prompt: string;
  /** 이 에이전트가 시작되기 전에 완료되어야 하는 에이전트 목록 */
  dependsOn?: string[];
  /** 타임아웃 (밀리초, 기본값: 300000) */
  timeout?: number;
}

// 설계 → 구현 → 테스트 → 리뷰 순서의 에이전트 파이프라인
const agentPipeline: AgentTask[] = [
  {
    // 1단계: 아키텍트 에이전트 - 요구사항을 기술 설계서로 변환
    name: 'architect',
    prompt: `
      요구사항을 분석하고 기술 설계서를 작성해라.
      포함: 컴포넌트 구조, 데이터 흐름, API 설계, 에러 시나리오.
      출력 형식: JSON Schema
    `,
  },
  {
    // 2단계: 구현 에이전트 - 설계서 기반 코드 작성
    name: 'implementer',
    prompt: `
      architect의 설계서를 기반으로 구현 코드를 작성해라.
      CLAUDE.md의 코딩 규칙을 반드시 따를 것.
      파일별로 구분하여 출력.
    `,
    dependsOn: ['architect'], // 아키텍트 완료 후 실행
  },
  {
    // 3단계: 테스트 에이전트 - 구현 코드의 테스트 작성
    name: 'tester',
    prompt: `
      implementer의 코드에 대한 테스트를 작성해라.
      커버리지 목표: 라인 90%, 브랜치 85%.
      에러/에지 케이스 포함.
    `,
    dependsOn: ['implementer'], // 구현 완료 후 실행
  },
  {
```

### 4.1 .cursorrules

`.cursorrules`는 Cursor AI가 프로젝트의 코딩 규칙을 이해하도록 돕는 설정 파일이다. 프로젝트 루트에 위치하며, Cursor의 모든 AI 기능(자동완성, Chat, Composer)에 적용된다.

```markdown
<!-- .cursorrules -->
You are a senior TypeScript/React developer working on a Next.js 15 project.

## Architecture
- Feature-Sliced Design: shared → entities → features → widgets → pages
- Server Components by default, 'use client' only when necessary
- API layer: /src/shared/api/ with typed fetch wrappers

## Code Style
- Strict TypeScript, no `any`, no `as` casting
- Named exports only
- Functional components with explicit return types
- Custom hooks: use{Domain}{Action} pattern
- Event handlers: handle{Action}{Element} pattern
- Constants in UPPER_SNAKE_CASE, extracted to constants.ts

## Multi-Beta
- Check NEXT_PUBLIC_DEPLOY_ENV for environment-specific behavior
- Preview environments: disable analytics, enable debug toolbar
- Feature flags: useFeatureFlag('flag-name') hook

## Error Handling
- All async operations must have error handling
- Use typed error classes, never throw plain strings
- Network errors → user-friendly messages + Sentry report

## Testing
- Vitest + React Testing Library
- Test file co-located: Component.test.tsx
- Korean test descriptions
- MSW for API mocking

## Performance
- React.lazy for routes and heavy components
- useMemo/useCallback only when profiler shows re-renders
- Image: next/image with explicit width/height
- No layout thrashing: batch DOM reads/writes

## Accessibility
- Semantic HTML first
- All interactive elements keyboard accessible
- ARIA attributes on custom widgets
- prefers-reduced-motion respected
```

### 4.2 Composer 활용 패턴

Composer는 여러 파일을 동시에 편집하는 Cursor의 핵심 기능이다. 자연어로 지시하면 관련된 모든 파일을 한 번에 수정한다.

```
# Composer 프롬프트 예시: 기능 모듈 일괄 생성

새로운 feature "coupon" 모듈을 만들어줘.

파일 구조:
src/features/coupon/
  ├── ui/
  │   ├── CouponCard.tsx        // 개별 쿠폰을 카드 형태로 표시하는 UI
  │   ├── CouponList.tsx        // 쿠폰 목록을 무한 스크롤로 렌더링
  │   └── CouponApplyModal.tsx  // 쿠폰 코드 입력 및 적용 확인 모달
  ├── model/
  │   ├── types.ts              // Coupon, CouponFilter, CouponStatus 타입 정의
  │   ├── store.ts              // Zustand 스토어 (선택된 쿠폰, 필터 상태)
  │   └── hooks.ts              // useCoupons, useApplyCoupon 커스텀 훅
  ├── api/
  │   ├── queries.ts            // TanStack Query 기반 쿠폰 조회 훅
  │   └── mutations.ts          // 쿠폰 적용/해제 mutation 훅
  └── index.ts                  // public API (named exports만 노출)

각 파일에 .cursorrules 규칙을 적용하고,
Preview 환경에서는 테스트 쿠폰 데이터를 자동 주입해줘.
```

### 6.2 AI 기반 배포 위험도 분석

코드 변경의 규모와 영향 범위를 자동 분석하여 배포 위험도를 산출한다. 위험도에 따라 배포 전략(자동/수동/카나리)이 결정된다.

```typescript
// scripts/ai-deploy-risk-analysis.ts
// git diff를 분석하여 배포 위험도를 자동 산출하는 스크립트
import { execSync } from 'node:child_process';

/** 배포 위험도 평가 결과 */
interface RiskAssessment {
  level: 'low' | 'medium' | 'high' | 'critical'; // 위험 수준
  score: number;           // 위험 점수 (가중치 합산)
  factors: RiskFactor[];   // 위험 요인 목록
  recommendation: string;  // 배포 권장 사항
}

/** 개별 위험 요인 */
interface RiskFactor {
  category: string;     // 위험 범주 (규모, 핵심 파일, DB, 테스트)
  description: string;  // 위험 설명
  weight: number;       // 가중치 (1~5, 높을수록 위험)
}

/**
 * 기준 브랜치 대비 현재 브랜치의 변경사항을 분석하여 배포 위험도를 산출한다.
 * @param baseBranch - 비교 기준이 되는 브랜치 (기본값: 'main')
 * @returns 위험도 평가 결과
 */
function analyzeDeployRisk(baseBranch: string = 'main'): RiskAssessment {
  // git diff로 변경된 파일 목록을 가져온다
  const diff = execSync(`git diff ${baseBranch}...HEAD --stat`).toString();
  const diffFiles = execSync(`git diff ${baseBranch}...HEAD --name-only`).toString().split('\n').filter(Boolean);

  const factors: RiskFactor[] = [];

  // 1. 변경 규모 분석: 파일 수에 따라 위험도를 가중한다
  const fileCount = diffFiles.length;
  if (fileCount > 50) {
    factors.push({ category: '규모', description: `${fileCount}개 파일 변경 (대규모)`, weight: 3 });
  } else if (fileCount > 20) {
    factors.push({ category: '규모', description: `${fileCount}개 파일 변경 (중규모)`, weight: 2 });
  }

  // 2. 핵심 파일 변경 감지: 인프라/설정 파일 변경은 높은 위험
  const criticalPaths = [
    { pattern: /\.env/, label: '환경변수' },
    { pattern: /middleware\.ts/, label: '미들웨어' },
    { pattern: /next\.config/, label: 'Next.js 설정' },
    { pattern: /package\.json/, label: '의존성' },
    { pattern: /prisma\/.*\.prisma/, label: 'DB 스키마' },
    { pattern: /src\/shared\/api/, label: 'API 계층' },
  ];

  for (const { pattern, label } of criticalPaths) {
    if (diffFiles.some((f) => pattern.test(f))) {
      factors.push({ category: '핵심 파일', description: `${label} 변경 감지`, weight: 3 });
    }
  }

  // 3. DB 마이그레이션 파일 확인: 스키마 변경은 가장 높은 위험
  if (diffFiles.some((f) => f.includes('migration'))) {
    factors.push({ category: 'DB', description: '마이그레이션 파일 포함', weight: 4 });
  }

  // 4. 테스트 커버리지 확인: 소스 변경에 테스트가 없으면 경고
  const testFiles = diffFiles.filter((f) => f.includes('.test.'));
  const srcFiles = diffFiles.filter((f) => f.startsWith('src/') && !f.includes('.test.'));
  if (srcFiles.length > 0 && testFiles.length === 0) {
    factors.push({ category: '테스트', description: '소스 변경에 대한 테스트 없음', weight: 2 });
  }

  // 위험 점수 합산 및 수준 결정
  const score = factors.reduce((sum, f) => sum + f.weight, 0);
  const level = score >= 10 ? 'critical' : score >= 6 ? 'high' : score >= 3 ? 'medium' : 'low';

  // 수준별 배포 권장 사항
  const recommendations: Record<string, string> = {
    low: '자동 배포 가능. Preview 환경에서 기본 스모크 테스트 권장.',
    medium: 'Preview 환경에서 수동 검증 후 배포. 변경 영역별 확인 필요.',
    high: '팀 리뷰 필수. Preview 환경에서 전체 회귀 테스트 수행.',
    critical: '배포 동결 검토. 아키텍트 승인 + 단계적 롤아웃(Canary) 필수.',
  };

  return { level, score, factors, recommendation: recommendations[level] };
}
```

```typescript
// src/shared/config/environment.ts
// 배포 환경별 설정을 타입 안전하게 관리하는 모듈

/** 배포 환경 타입 (production, preview, development 중 하나) */
type DeployEnv = 'production' | 'preview' | 'development';

/** 환경별 설정 인터페이스 */
interface EnvConfig {
  deployEnv: DeployEnv;           // 현재 배포 환경
  apiBaseUrl: string;             // API 서버 기본 URL
  analyticsEnabled: boolean;      // Google Analytics 등 분석 도구 활성화 여부
  debugToolbar: boolean;          // 디버그 툴바 표시 여부
  featureFlagEnv: string;         // LaunchDarkly 환경 식별자
  sentryDsn: string | null;       // Sentry 에러 추적 DSN (null이면 비활성)
  previewBranch: string | null;   // Preview 환경의 소스 브랜치명
}

/**
 * 환경 변수에서 현재 배포 환경을 읽어 해당 설정을 반환한다.
 * NEXT_PUBLIC_DEPLOY_ENV가 설정되지 않으면 development로 기본값을 사용한다.
 */
function getEnvConfig(): EnvConfig {
  const deployEnv = (process.env.NEXT_PUBLIC_DEPLOY_ENV as DeployEnv) ?? 'development';

  const configs: Record<DeployEnv, EnvConfig> = {
    production: {
      deployEnv: 'production',
      apiBaseUrl: 'https://api.example.com',
      analyticsEnabled: true,       // 프로덕션에서만 분석 활성화
      debugToolbar: false,          // 프로덕션에서는 디버그 도구 숨김
      featureFlagEnv: 'production',
      sentryDsn: process.env.NEXT_PUBLIC_SENTRY_DSN ?? null,
      previewBranch: null,
    },
    preview: {
      deployEnv: 'preview',
      apiBaseUrl: 'https://api-preview.example.com',
      analyticsEnabled: false,      // Preview에서는 분석 비활성화 (데이터 오염 방지)
      debugToolbar: true,           // Preview에서는 디버그 도구 표시
      featureFlagEnv: 'preview',
      sentryDsn: process.env.NEXT_PUBLIC_SENTRY_DSN ?? null,
      previewBranch: process.env.NEXT_PUBLIC_PREVIEW_BRANCH ?? null,
    },
    development: {
      deployEnv: 'development',
      apiBaseUrl: 'http://localhost:3001',
      analyticsEnabled: false,      // 개발 환경에서는 분석 비활성화
      debugToolbar: true,           // 개발 환경에서는 디버그 도구 표시
      featureFlagEnv: 'development',
      sentryDsn: null,              // 개발 환경에서는 Sentry 비활성화
      previewBranch: null,
    },
  };

  return configs[deployEnv];
}

/** 앱 전역에서 사용하는 환경 설정 싱글톤 */
export const envConfig = getEnvConfig();

/** 현재 환경이 Preview인지 확인하는 유틸리티 */

  return envConfig.deployEnv === 'preview';
}

/** 현재 환경이 Production인지 확인하는 유틸리티 */
export function isProduction(): boolean {
```

```typescript
// src/shared/lib/feature-flags.ts
// LaunchDarkly 기반 Feature Flag 관리 모듈
// Preview 환경에서는 강제 활성화/비활성화 옵션을 제공한다

import { useFlags, useLDClient } from 'launchdarkly-react-client-sdk';
import { envConfig } from '@/shared/config/environment';

/** Feature Flag 옵션 */
interface FeatureFlagOptions {
  /** Preview 환경에서 이 플래그를 강제로 활성화할지 여부 */
  enableInPreview?: boolean;
  /** Preview 환경에서 이 플래그를 강제로 비활성화할지 여부 */
  disableInPreview?: boolean;
}

/**
 * Feature Flag 값을 읽는 커스텀 훅.
 * Preview 환경에서는 옵션에 따라 강제 오버라이드가 가능하다.
 *
 * @param flagKey - LaunchDarkly에 등록된 플래그 키
 * @param defaultValue - 플래그가 없을 때의 기본값
 * @param options - Preview 환경 오버라이드 옵션
 * @returns 플래그의 현재 값 (boolean)
 *
 * @example
 * // 기본 사용: LaunchDarkly 값을 그대로 반환
 * const isNewCheckout = useFeatureFlag('new-checkout');
 *
 * // Preview 환경에서 항상 활성화
 * const isNewCheckout = useFeatureFlag('new-checkout', false, { enableInPreview: true });
 */
export function useFeatureFlag(
  flagKey: string,
  defaultValue: boolean = false,
  options: FeatureFlagOptions = {}
): boolean {
  const flags = useFlags();

  // Preview 환경에서는 옵션에 따라 강제 오버라이드
  if (envConfig.deployEnv === 'preview') {
    if (options.enableInPreview) return true;
    if (options.disableInPreview) return false;
  }

  return (flags[flagKey] as boolean) ?? defaultValue;
}

/**
 * Preview/Development 환경에서 Feature Flag를 실시간으로 토글하는 디버그 훅.
 * Production 환경에서는 토글이 차단된다.
 */
export function useFeatureFlagDebug(): {
  flags: Record<string, boolean>;
  toggle: (key: string) => void;
} {
  const flags = useFlags();
  const client = useLDClient();

  const toggle = (key: string): void => {
    // Production 환경에서 실수로 토글하는 것을 방지
    if (envConfig.deployEnv !== 'preview' && envConfig.deployEnv !== 'development') {
      console.warn('Feature flag 토글은 preview/development 환경에서만 가능합니다.');
      return;
    }
    // LaunchDarkly 개별 사용자 타겟팅으로 오버라이드
    client?.identify({
      key: 'debug-user',
      custom: { [key]: !(flags[key] as boolean) },
    });
  };

  return { flags: flags as Record<string, boolean>, toggle };
}
```

### 7.5 배포 단계

### 7.6 모니터링 단계

배포 후 에러와 성능 지표를 자동 수집한다. 환경별로 다른 전략을 적용하여 Preview에서는 콘솔 로그, Production에서는 Sentry로 보고한다. 참고: [09. 장애 대응 및 Sentry 표준](./09_장애_대응_및_Sentry_표준.md)

```typescript
// src/shared/lib/monitoring.ts
// 환경별 모니터링 이벤트 수집 모듈
// Preview: 콘솔 출력, Development: 무시, Production: Sentry + 커스텀 메트릭

import * as Sentry from '@sentry/nextjs';
import { envConfig } from '@/shared/config/environment';

/** 모니터링 이벤트의 구조 */
interface MonitoringEvent {
  type: 'error' | 'performance' | 'business'; // 이벤트 유형
  name: string;                                // 이벤트 이름 (예: 'api_timeout')
  metadata: Record<string, unknown>;           // 추가 메타데이터
}

/**
 * 모니터링 이벤트를 환경에 맞게 수집한다.
 * - Preview: 콘솔에 출력 (디버깅용)
 * - Development: 무시 (노이즈 방지)
 * - Production: Sentry에 보고
 */
export function trackEvent(event: MonitoringEvent): void {
  // Preview 환경: 콘솔에 출력하여 개발자가 디버깅할 수 있도록 한다
  if (envConfig.deployEnv === 'preview') {
    console.log('[Preview Monitor]', event);
    return;
  }

  // Development 환경: 모니터링 이벤트를 무시한다
  if (envConfig.deployEnv === 'development') return;

  // Production 환경: Sentry에 에러와 메트릭을 보고한다
  if (event.type === 'error') {
    Sentry.captureException(new Error(event.name), {
      tags: { eventType: event.type },
      extra: event.metadata,
    });
  }

  if (event.type === 'performance') {
    Sentry.metrics.distribution(event.name, event.metadata.value as number, {
      unit: (event.metadata.unit as string) ?? 'millisecond',
    });
  }
}

/**
 * Web Vitals (LCP, FID, CLS 등)를 자동으로 수집하여 모니터링 시스템에 전달한다.
 * Next.js의 reportWebVitals에 연결하여 사용한다.
 *
 * @example
 * // app/layout.tsx에서 연결
 * export { reportWebVitals } from '@/shared/lib/monitoring';
 */
export function reportWebVitals(metric: { name: string; value: number; id: string }): void {
  trackEvent({
    type: 'performance',
    name: `web_vital_${metric.name}`,
    metadata: { value: metric.value, id: metric.id },
  });
}
```

## 8. 프롬프트 엔지니어링 for 개발자

### 8.1 효과적인 프롬프트 구조

AI에게 원하는 결과를 얻으려면 체계적인 프롬프트 구조가 필수다. 다음 5요소를 조합하면 결과 품질이 크게 향상된다.

```
[역할] + [컨텍스트] + [구체적 요구사항] + [제약 조건] + [출력 형식]
```

| 요소 | 설명 | 예시 |
|------|------|------|
| **역할** | AI의 전문성 범위 설정 | "시니어 TypeScript 개발자로서" |
| **컨텍스트** | 프로젝트/상황 정보 | "Next.js 15 App Router 프로젝트에서" |
| **구체적 요구사항** | 무엇을 해야 하는지 | "이 API 응답 타입을 Zod 스키마로 변환해줘" |
| **제약 조건** | 지켜야 할 규칙 | "any 타입 금지, strict mode" |
| **출력 형식** | 결과물 형태 | "파일별로 분리해서 코드 블록으로" |

### 8.2 체인 프롬프트 (단계적 접근)

복잡한 작업은 한 번에 요청하지 않고 단계별로 나누어 요청한다. 각 단계의 결과를 확인한 후 다음 단계로 진행한다.

```
# Step 1: 분석 - 현재 상태를 먼저 파악한다
"이 코드베이스의 의존성 그래프를 분석해줘. 순환 참조가 있는지 확인."

# Step 2: 계획 (Step 1 결과 기반) - 분석 결과를 바탕으로 계획을 세운다
"순환 참조를 해결하기 위한 리팩토링 계획을 세워줘. 단계별로."

# Step 3: 실행 (Step 2 계획 기반) - 계획의 첫 단계를 실행한다
"계획의 1단계를 실행해줘. 변경되는 파일과 코드를 보여줘."

# Step 4: 검증 (Step 3 결과 기반) - 변경이 올바른지 확인한다
"변경 후 기존 테스트가 모두 통과하는지 확인해줘."
```

### 8.3 Anti-Pattern 피하기

| Anti-Pattern | 문제 | 개선 |
|-------------|------|------|
| "코드 짜줘" | 컨텍스트 부족 → 제네릭한 결과 | 구체적 요구사항 + 제약 조건 명시 |
| 너무 긴 프롬프트 | 핵심 요구사항 희석 | 단계별 체인 프롬프트 분리 |
| 결과 검증 안 함 | AI 환각(hallucination) 미발견 | 항상 타입 체크 + 테스트 실행 |
| 하나의 도구만 사용 | 도구별 강점 미활용 | Claude(설계) → Copilot(구현) → CodeRabbit(리뷰) |
| 프롬프트 재사용 안 함 | 매번 처음부터 작성 | 프롬프트 라이브러리 구축 |
| AI 결과를 그대로 복붙 | 코드 이해 부족 → 유지보수 어려움 | 반드시 이해한 후 수정/통합 |
| 민감정보 포함 | API 키, 비밀번호 유출 위험 | 환경변수명만 전달, 실제 값은 제외 |

## 9. AI 도구 비용 최적화

### 9.1 비용 추적 대시보드

AI 도구 사용량을 팀 단위로 추적하고 최적화 포인트를 자동으로 식별한다.

```typescript
// src/shared/lib/ai-cost-tracker.ts
// AI 도구 사용량을 추적하고 비용 최적화 권장 사항을 생성하는 모듈

/** AI 도구 사용 기록 하나의 단위 */
interface AIUsageRecord {
  tool: 'claude' | 'copilot' | 'cursor' | 'coderabbit'; // 사용한 AI 도구
  action: string;         // 수행한 작업 (예: '코드 리뷰', '기능 설계')
  tokensUsed: number;     // 사용한 토큰 수
  estimatedCost: number;  // 추정 비용 (USD)
  timestamp: Date;        // 사용 시각
  developer: string;      // 개발자 식별자
}

/** 월간 AI 사용량 요약 */
interface MonthlySummary {
  totalCost: number;       // 총 비용
  byTool: Record<string, number>;      // 도구별 비용 합계
  byDeveloper: Record<string, number>; // 개발자별 비용 합계
  topActions: Array<{ action: string; count: number; totalCost: number }>; // 상위 작업
  recommendations: string[]; // 비용 절감 권장 사항
}

/**
 * 사용 기록을 분석하여 비용 절감 권장 사항을 생성한다.
 * 반복 패턴, 고비용 작업, 비효율적 도구 선택을 자동으로 감지한다.
 */
function generateRecommendations(records: AIUsageRecord[]): string[] {
  const recommendations: string[] = [];

  // 1. 반복 프롬프트 감지: 10회 이상 반복되는 작업은 자동화 대상
  const actionCounts = new Map<string, number>();
  for (const r of records) {
    actionCounts.set(r.action, (actionCounts.get(r.action) ?? 0) + 1);
  }
  for (const [action, count] of actionCounts) {
    if (count > 10) {
      recommendations.push(
        `"${action}" 작업이 ${count}회 반복됨 → CLAUDE.md 스킬 또는 Copilot 스니펫으로 자동화 권장`
      );
    }
  }

  // 2. 고비용 작업 식별: $1 이상인 단일 작업은 컨텍스트 최적화 필요
  const highCostActions = records
    .filter((r) => r.estimatedCost > 1)
    .map((r) => r.action);
  if (highCostActions.length > 0) {
    recommendations.push(
      `고비용 작업 감지: ${[...new Set(highCostActions)].join(', ')} → 컨텍스트 축소 또는 캐싱 검토`
    );
  }

  // 3. 도구 선택 최적화: 단순 작업에 Claude를 쓰면 Copilot으로 대체 권장
  const claudeSimpleActions = records.filter(
    (r) => r.tool === 'claude' && r.tokensUsed < 500 && r.action.includes('완성')
  );
  if (claudeSimpleActions.length > 5) {
    recommendations.push(
      '단순 코드 완성에 Claude 사용 감지 → Copilot 인라인 완성으로 대체 권장 (비용 90% 절감)'
    );
  }

  return recommendations;
}
```

### 9.2 비용 최적화 전략

| 전략 | 설명 | 절감 효과 |
|------|------|----------|
| **컨텍스트 관리** | CLAUDE.md로 반복 설명 제거 | ~30% 토큰 절감 |
| **도구 선택 최적화** | 단순 작업은 Copilot, 복잡 작업은 Claude | ~40% 비용 절감 |
| **프롬프트 캐싱** | 자주 쓰는 프롬프트를 스킬/스니펫으로 | ~20% 시간 절감 |
| **배치 처리** | 여러 파일 리뷰를 한 세션에서 | ~25% 토큰 절감 |
| **Preview 환경 활용** | AI 리뷰와 수동 검증 병행 → 재작업 감소 | ~50% 반복 비용 절감 |
| **세션 관리** | 긴 대화 분할, /clear 후 요약 전달 | ~15% 토큰 절감 |
