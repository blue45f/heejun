## 1. AI 기반 RFC 초안 자동 생성

RFC 작성의 가장 큰 병목은 초안 작성이다. AI를 활용하면 기술 비교, 장단점 분석, 대안 조사를 자동화하여 초안 작성 시간을 80% 이상 단축할 수 있다.

### 1.1 AI 초안 생성 워크플로우

```
1. 작성자가 배경/문제/제약 조건을 정리 (10분)
2. AI에 프롬프트 입력 -> RFC 초안 자동 생성 (2분)
3. 작성자가 팀 고유 맥락(레거시, 인력, 일정) 보완 (20분)
4. AI 자동 리뷰로 초안 품질 사전 점검 (2분)
5. Review 상태로 전환하여 팀 논의 시작
```

### 1.2 프롬프트 예시 1: 기술 스택 변경 RFC

```text
아래 조건으로 기술 스택 변경 RFC 초안을 작성해줘:

[배경]
- 현재 상태: 빌드 도구로 Webpack 5를 사용 중
- 문제점: 콜드 스타트 45초, HMR 3~5초, 프로덕션 빌드 4분 30초
- 제약 조건: 프론트엔드 팀 6명, 전환 기간 최대 8주, 운영 중단 불가

[요구사항]
- 최소 3가지 대안 비교 (Vite, Turbopack, Webpack+SWC 등)
- 각 대안의 장단점을 정량적 지표(빌드 시간, 번들 크기, 플러그인 호환성)로 제시
- 마이그레이션 비용과 리스크 분석 포함
- 팀 학습 곡선 고려
- 의사결정 매트릭스(가중치 포함) 포함

[출력 형식]
- 메타 정보, 요약, 동기, 제안, 대안 분석, 영향도 분석, 성공 지표, 구현 계획 섹션 포함
- 마크다운 테이블 형식으로 정리
```

### 1.3 프롬프트 예시 2: 아키텍처 결정 RFC

```text
아래 조건으로 아키텍처 변경 RFC 초안을 작성해줘:

[배경]
- 현재 상태: 모든 페이지가 CSR(Client-Side Rendering)으로 구현
- 문제점: 클라이언트 번들 380KB(gzipped), 모바일 LCP 3.2초, SEO 대응 별도 SSR 유지
- 제약 조건: React 기반 코드베이스 유지, 점진적 전환 필수

[요구사항]
- Server Components, Islands Architecture, 기존 CSR+코드스플리팅 3가지 대안 비교
- 컴포넌트 분류 기준(Server vs Client) 제시
- 번들 사이즈, LCP, INP 등 Core Web Vitals 기반 성공 지표
- Phase별 마이그레이션 계획(신규 페이지 -> 저트래픽 -> 전체)
- 롤백 전략 포함

[출력 형식]
- RFC 표준 템플릿에 맞춰 작성
- 의사결정 매트릭스 + 리스크 매트릭스 포함
```

### 1.4 프롬프트 예시 3: 프로세스 개선 RFC

```text
아래 조건으로 개발 프로세스 개선 RFC 초안을 작성해줘:

[배경]
- 현재 상태: 코드 리뷰를 사람이 전적으로 수행, 평균 리뷰 대기 시간 18시간
- 문제점: 리뷰 병목으로 PR 머지까지 평균 2.3일, 반복적 스타일/패턴 지적이 전체 코멘트의 40%
- 제약 조건: 기존 GitHub PR 기반 워크플로우 유지, 보안/비즈니스 로직은 사람 리뷰 필수

[요구사항]
- AI 코드 리뷰 1차 + 사람 리뷰 2차 파이프라인 설계
- AI 리뷰 도구 3가지 비교 (정확도, 비용, 연동성)
- 리뷰 자동화 범위와 사람 리뷰 필수 영역 구분
- 도입 전후 예상 지표(리뷰 대기 시간, PR 머지 시간, 리뷰 품질) 제시
- 파일럿 운영 -> 전체 확대 단계별 계획

[출력 형식]
- GitHub Actions 워크플로우 예시 코드 포함
- 의사결정 매트릭스 + 비용 분석 포함
```

### 1.5 AI 초안 생성 시 주의사항

| 항목 | 설명 |
|------|------|
| **팀 맥락 보완 필수** | AI는 팀의 레거시 코드, 인력 구성, 조직 문화를 모른다. 반드시 사람이 보완한다 |
| **데이터 출처 검증** | AI가 제시한 벤치마크, 통계, 사례의 출처를 반드시 확인한다 |
| **최신 정보 확인** | AI 학습 데이터의 기준 시점을 고려하여 최신 버전/기능을 별도 검증한다 |
| **복수 AI 교차 검증** | 중요한 RFC는 Claude와 GPT 등 복수 AI로 교차 검증하여 편향을 줄인다 |

## 2. AI 기반 RFC 자동 리뷰

### 2.1 AI 리뷰 활용 범위

| 리뷰 관점 | AI 자동화 | 사람 판단 필수 | 설명 |
|-----------|:---:|:---:|------|
| **영향도 분석** | O | - | 코드베이스/팀/프로세스에 미치는 영향 자동 식별 |
| **대안 평가** | O | - | 누락된 대안 제안, 각 대안의 장단점 보완 |
| **논리적 허점 탐지** | O | - | 숨겨진 가정, 논리 비약, 근거 부족 식별 |
| **리스크 식별** | O | - | 보안/성능/접근성/호환성 관점 누락 리스크 탐지 |
| **템플릿 준수 검사** | O | - | 필수 섹션 누락, 용어 일관성, 가독성 점검 |
| **비즈니스 적합성** | - | O | 조직 전략/우선순위와의 정합성은 사람이 판단 |
| **조직 문화 적합성** | - | O | 팀 역량/문화와의 적합성은 사람이 판단 |

### 2.2 AI 자동 리뷰 프롬프트: 영향도 분석 + 대안 평가

```text
아래 RFC 초안을 리뷰해줘. 다음 7가지 관점에서 분석하고 피드백을 줘:

1. **문제 정의**: 구체적이고 데이터로 뒷받침되는가? 정량적 근거가 충분한가?
2. **대안 분석**: 3개 이상이며 공정하게 평가되었는가? 누락된 대안이 있는가?
3. **숨겨진 가정**: 명시되지 않은 가정(hidden assumption)이 있는가?
4. **리스크**: 보안/성능/접근성/호환성 관점에서 누락된 리스크가 있는가?
5. **구현 계획**: 롤백 전략이 포함되었는가? 단계별 마일스톤이 현실적인가?
6. **성공 지표**: 측정 가능하고 현실적인가? 측정 시점과 방법이 명확한가?
7. **영향도**: 영향받는 팀/코드베이스/프로세스가 빠짐없이 식별되었는가?

각 항목에 대해 [통과 / 보완 필요 / 미흡] 등급과 구체적 개선 제안을 제시해줘.

[RFC 초안]
{RFC 초안 내용 붙여넣기}
```

```text
아래 RFC의 의사결정 매트릭스를 검증해줘:

1. 평가 기준의 가중치가 합리적인가? 누락된 기준이 있는가?

3. 점수 간 상대적 차이가 설명 가능한가?
4. 가중치나 점수를 조정했을 때 결론이 뒤집히는 민감도 분석을 수행해줘
5. 최종 추천이 매트릭스 결과와 일치하는가?

[의사결정 매트릭스]

### 2.4 AI 리뷰 결과 처리 기준

| AI 리뷰 결과 | 조치 |
|-------------|------|
| **Critical** (논리적 결함, 중대한 리스크 누락) | 반드시 수정 후 재리뷰, Review 상태 전환 차단 |
| **Warning** (대안 누락, 불충분한 근거) | 작성자가 보완하고 변경 이력에 기록 |
| **Info** (문서 품질, 용어 일관성) | 작성자 재량으로 반영 |
| **False Positive** | AI 리뷰 결과에 반박 근거를 기록하고 무시 |

### 2.5 AI 리뷰 체크리스트

- [ ] 문제 정의가 구체적이고 데이터로 뒷받침되는가
- [ ] 대안이 3개 이상이며 공정하게 평가되었는가
- [ ] 숨겨진 가정(hidden assumption)이 식별되었는가
- [ ] 구현 계획에 롤백 전략이 포함되었는가
- [ ] 성공/실패 지표가 측정 가능한가
- [ ] 보안, 성능, 접근성 관점이 누락되지 않았는가
- [ ] AI가 제시한 벤치마크 데이터의 출처가 검증되었는가
- [ ] 영향받는 팀/코드베이스/프로세스가 빠짐없이 식별되었는가

## 3. RFC 라이프사이클

### 3.1 상태 흐름

```
Draft (초안)
  |
  +-- 작성자가 AI로 RFC 초안 자동 생성
  +-- AI 자동 리뷰로 초안 품질 사전 점검
  +-- 챔피언(Champion) 지정
  |
  v
Review (리뷰)
  |
  +-- 비동기 코멘트 수집 (최소 5영업일)
  +-- AI 리뷰 결과 팀에 공유
  +-- 필요 시 동기 회의 (30분 이내 타임박싱)
  +-- 대안 추가/수정
  |
  v
Accepted / Rejected (결정)
  |
  +-- 의사결정 매트릭스 기반 평가
  +-- 거버넌스 기준에 따른 승인
  +-- ADR(Architecture Decision Record) 연동
  |
  v
Implemented (구현)
  |
  +-- 구현 계획 수립 (Phase별 마일스톤)
  +-- 진행 상황 정기 공유
  +-- 완료 후 회고 및 성공 지표 측정
```

### 3.2 상태 정의

| 상태 | 설명 | 다음 상태 |
|------|------|----------|
| **Draft** | 초안 작성 중. AI 초안 생성 + AI 리뷰 수행 | Review |
| **Review** | 공식 리뷰 요청 상태. 논의 타이머 시작 | Accepted / Rejected / Withdrawn |
| **Accepted** | 승인됨. 구현 진행 | Implemented / Superseded |
| **Rejected** | 기각됨. 사유 기록 필수 | (종료) |
| **Implemented** | 구현 완료. 성과 지표 기록 | Superseded / Deprecated |
| **Superseded** | 새로운 RFC로 대체됨 | (종료) |
| **Withdrawn** | 작성자가 자발적으로 철회 | (종료) |
| **Deprecated** | 더 이상 유효하지 않음 | (종료) |

### 3.3 타임라인 가이드

| 규모 | 논의 기간 | 최소 리뷰어 | 예시 |
|------|----------|------------|------|
| Small | 3영업일 | 2명 | 린팅 규칙 변경, 유틸 패턴 표준화 |
| Medium | 5영업일 | 3명 | 상태 관리 라이브러리 변경, 테스트 전략 |
| Large | 10영업일 | 5명 + 아키텍트 | 모노레포 전환, 렌더링 전략 변경 |

## 4. RACI 거버넌스

### 4.1 역할 정의 (RACI 매트릭스)

| 활동 | 작성자 (Author) | 챔피언 (Champion) | 리뷰어 (Reviewer) | 승인권자 (Approver) |
|------|:---:|:---:|:---:|:---:|
| RFC 초안 작성 (AI 활용) | **R** | I | - | - |
| AI 자동 리뷰 실행 | R | I | - | - |
| 비동기 코멘트 | R | C | **R** | I |
| 쟁점 중재 | I | **R** | C | I |
| 최종 승인/기각 | I | C | C | **R** |
| 구현 추적 | **R** | A | I | I |
| 성과 지표 검증 | R | **A** | I | I |

> R: Responsible(실행) / A: Accountable(책임) / C: Consulted(자문) / I: Informed(통보)

### 4.2 승인 기준

| RFC 규모 | 승인 요건 | 승인권자 |
|---------|----------|---------|
| Small | 리뷰어 2명 승인 | 챔피언 |
| Medium | 리뷰어 3명 승인 + 시니어 1명 | 테크 리드 |
| Large | 리뷰어 5명 승인 + 아키텍처 리뷰 | 아키텍트 / CTO |

### 4.3 의사결정 판단 기준

```
1. 되돌릴 수 있는가? (Reversibility)
   +-- 쉽게 되돌릴 수 있음 -> 빠르게 결정, 실행 후 학습
   +-- 되돌리기 어려움 -> 충분한 논의, 신중한 결정

2. 영향 범위는? (Blast Radius)
   +-- 단일 팀 -> 해당 팀 내 결정
   +-- 다수 팀 -> 관련 팀 합의 필요
   +-- 전사 -> 아키텍처 위원회 검토

3. 긴급한가? (Urgency)
   +-- 긴급 (장애, 보안) -> 간소화 프로세스 적용
   +-- 비긴급 -> 표준 프로세스 적용
```

### 4.4 분쟁 해결

1. **1단계**: 작성자-리뷰어 간 비동기 논의
2. **2단계**: 챔피언 중재 (동기 회의, 30분 제한)
3. **3단계**: 테크 리드 최종 결정 (결정 사유 기록 필수)

## 5. 비동기 의사결정 프로세스

### 5.1 비동기 우선 원칙

RFC 논의는 **비동기를 기본**으로 한다. 동기 회의는 비동기로 해결되지 않는 쟁점이 있을 때만 소집한다.

### 5.2 도구별 활용 가이드

| 플랫폼 | 활용 방법 | 적합한 상황 |
|--------|----------|-----------|
| **GitHub Discussions** | RFC 전용 카테고리 생성, 스레드 기반 논의 | 코드 기반 기술 결정 |
| **Notion** | RFC 데이터베이스 생성, 인라인 코멘트 활용 | 비개발자 포함 논의, 시각적 문서 |
| **GitHub PR** | Draft PR로 RFC 등록, 코드 리뷰 방식 논의 | 구현과 밀접한 기술 결정 |
| **Slack/Teams** | 쟁점 알림, 투표, 빠른 의견 수집 | 리마인더, 간단한 의견 조율 |

### 5.3 비동기 리뷰 가이드라인

**리뷰어 역할**:
- 지정받은 후 **2영업일 이내** 최소 1회 코멘트
- 반대 의견은 반드시 **대안 제시**와 함께 기록
- "LGTM"만으로는 충분하지 않음 -- 동의 근거를 1줄 이상 작성

**작성자 역할**:
- 모든 코멘트에 **2영업일 이내** 응답
- 반영한 내용은 변경 이력에 기록
- 논의가 교착 상태면 동기 회의 소집 또는 챔피언에게 에스컬레이션

### 5.4 비동기 의사결정 매커니즘

#### Lazy Consensus (소규모 RFC)
- 제안 후 3영업일 이내 반대 의견이 없으면 자동 승인
- 반대 의견 발생 시 일반 논의 프로세스로 전환

#### 명시적 승인 (중/대규모 RFC)
- 필수 리뷰어 전원의 명시적 승인 필요
- 승인 기한 초과 시 챔피언이 리마인더 발송
- 2주 이상 미응답 시 해당 리뷰어 제외 후 진행

#### 투표 (의견 분열 시)
- 찬성/반대/중립 3가지 선택지
- 과반수 기준 결정 (동점 시 챔피언 결정권)
- 투표 전 반드시 각 입장의 근거를 문서화

## 7. 실전 RFC 예시

### 7.1 예시 1: 번들러 전환 (기술 스택 변경)

```markdown
# RFC-042: 번들러를 Webpack에서 Vite로 전환

## 메타 정보

| 항목 | 내용 |
|------|------|
| 작성자 | @developer-a |
| 챔피언 | @tech-lead |
| 작성일 | YYYY-MM-DD |
| 상태 | Accepted |
| 규모 | Large |
| AI 보조 | Claude (초안 생성, 대안 분석), GPT (리스크 교차 검증) |

## 1. 요약

프로젝트의 번들러를 Webpack 5에서 Vite로 전환하여 개발 서버 시작 시간과
빌드 속도를 대폭 개선한다.

## 2. 동기

### 2.1 현재 상황
- 개발 서버 콜드 스타트: 45초
- HMR 반영 시간: 3~5초
- 프로덕션 빌드: 4분 30초
- Webpack 설정 파일: 850줄 (복잡도 높음)

### 2.2 문제점
- 개발 생산성 저하: 하루 평균 15회 서버 재시작 x 45초 = 11분 유휴 시간
- 새 팀원 환경 설정 어려움: Webpack 설정 이해에 평균 3일 소요
- CI/CD 파이프라인 병목: 빌드 단계가 전체 파이프라인의 60% 차지

### 2.3 목표
- 개발 서버 콜드 스타트 5초 이내
- HMR 반영 시간 500ms 이내
- 프로덕션 빌드 2분 이내

## 3. 제안

Vite + Rolldown 기반으로 전환하며, 3단계로 진행한다.

| Phase | 기간 | 내용 |
|-------|------|------|
| Phase 1 | 2주 | 신규 프로젝트에 Vite 적용, 호환성 검증 |
| Phase 2 | 4주 | 기존 프로젝트 순차 전환 (중요도 낮은 것부터) |
| Phase 3 | 2주 | 전체 전환 완료, Webpack 설정 제거 |

## 4. 대안 분석 (AI 자동 생성 + 사람 보완)

| 기준 | 가중치 | Vite | Turbopack | Webpack + SWC |
|------|--------|------|-----------|---------------|
| 빌드 성능 | 30% | 9 | 8 | 5 |
| 생태계 성숙도 | 25% | 9 | 6 | 10 |
| 마이그레이션 비용 | 20% | 7 | 8 | 10 |
| DX (개발자 경험) | 15% | 9 | 7 | 4 |
| 장기 유지보수 | 10% | 8 | 7 | 5 |
| **가중 총점** | | **8.45** | **7.25** | **6.65** |

## 5. AI 리뷰 결과

| 항목 | 등급 | 피드백 |
|------|------|--------|
| 문제 정의 | 통과 | 정량적 근거 충분 |
| 대안 분석 | 보완 필요 | esbuild 대안 누락 -> 작성자가 검토 후 제외 사유 추가 |
| 리스크 | 보완 필요 | 서드파티 Webpack 플러그인 호환성 리스크 누락 -> Phase 1에 호환성 매트릭스 추가 |
| 성공 지표 | 통과 | 측정 가능하고 현실적 |

## 6. 성공 지표

| 지표 | 현재 | 목표 | 측정 시점 |
|------|------|------|----------|
| 콜드 스타트 | 45초 | 5초 이내 | Phase 1 완료 후 |
| HMR 반영 | 3~5초 | 500ms 이내 | Phase 1 완료 후 |
| 프로덕션 빌드 | 4분 30초 | 2분 이내 | Phase 2 완료 후 |
```

### 7.2 예시 2: AI 코드 리뷰 파이프라인 도입 (프로세스 개선)

```markdown
# RFC-058: AI 코드 리뷰 1차 자동화 파이프라인 도입

## 메타 정보

| 항목 | 내용 |
|------|------|
| 작성자 | @developer-c |
| 챔피언 | @tech-lead |
| 작성일 | YYYY-MM-DD |
| 상태 | Accepted |
| 규모 | Medium |
| AI 보조 | Claude (초안 생성), GPT (대안 비교 검증) |

## 1. 요약

PR 생성 시 AI가 1차 코드 리뷰(스타일, 보안, 성능 패턴)를 자동 수행하고,
사람은 2차 리뷰(비즈니스 로직, 아키텍처 적합성)에 집중하는 2단계 파이프라인을 도입한다.

## 2. 동기

### 2.1 현재 상황
- 코드 리뷰를 사람이 전적으로 수행
- 평균 리뷰 대기 시간: 18시간
- PR 머지까지 평균 2.3일

### 2.2 문제점
- 반복적 스타일/패턴 지적이 전체 리뷰 코멘트의 40%
- 리뷰어 피로도 증가로 심층 리뷰 품질 저하
- 시니어 개발자의 리뷰 병목

### 2.3 목표
- 리뷰 대기 시간 50% 감소 (18시간 -> 9시간)
- 반복적 코멘트 비율 40% -> 10%로 감소
- PR 머지 시간 2.3일 -> 1.5일로 단축

## 3. 제안

### 3.1 2단계 리뷰 파이프라인

```yaml
# .github/workflows/ai-review.yml
name: AI Code Review
on: [pull_request]
jobs:
  ai-review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: AI Review
        uses: ai-code-review-action@v2
        with:
          model: "claude-sonnet"
          rules: |
            - security_scan: required
            - performance_check: required
            - accessibility_check: required
            - style_check: optional
```

### 3.2 AI/사람 리뷰 범위 구분

| 리뷰 영역 | AI 1차 | 사람 2차 |
|-----------|:---:|:---:|
| 코드 스타일/포맷 | O | - |
| 일반적 버그 패턴 | O | - |
| 성능 안티패턴 | O | - |
| 보안 취약점 | O | O |
| 비즈니스 로직 | - | O |
| 아키텍처 적합성 | - | O |

## 4. 성공 지표

| 지표 | 현재 | 목표 | 측정 시점 |
|------|------|------|----------|
| 리뷰 대기 시간 | 18시간 | 9시간 | 파일럿 4주 후 |
| 반복 코멘트 비율 | 40% | 10% | 파일럿 4주 후 |
| PR 머지 시간 | 2.3일 | 1.5일 | 전체 확대 4주 후 |
```
