## 개요

**프론트엔드 개발팀 전체에 영향이 있을 수 있는 표준(정책/가이드)를 논의해요**

지금까지 각 팀에서 자체적으로 수행하던 표준, 가이드 등의 업무를 조직 표준으로 올리고 프론트엔드 구성원들과 함께 논의하고 발전시킬 수 있어요.

### 논의 가능 주제 예시

- 웹 성능 가이드
- 어드민 가이드라인
- 프론트엔드 아키텍처 표준
- 테스트 전략 가이드
- 코드 리뷰 가이드라인
- 스타일링 라이브러리 표준
- 상태 관리 표준
- 기타 조직 전체에 영향을 미치는 기술 표준

## 표준 문서 상태

표준 문서는 다음과 같은 상태를 가집니다:

| 상태 | 설명 |
|------|------|
| **대기** | 작성이 완료되어 대기 중입니다. |
| **논의 진행중** | 작성이 완료되어 논의 진행 중입니다. |
| **완료** | 완료된 표준입니다. |
| **업데이트 공유** | 완료된 표준을 최신화를 진행해 업데이트를 하였습니다. |

## 표준 제안 및 선포 프로세스

### 프로세스 흐름

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   표준 제안   │ ──→ │   논의 진행   │ ──→ │   합의 도출   │ ──→ │   표준 선포   │
│   (문서 작성) │     │   (코멘트)   │     │   (피드백)   │     │   (완료)    │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
      │                   │                   │                   │
      │                   │                   │                   │
      ▼                   ▼                   ▼                   ▼
   대기 상태           논의 진행중           검토/수정             완료
```

### 세부 단계

#### 1단계: 표준 제안 (문서 작성)
- RFC 폴더에 새 문서를 생성합니다
- 표준의 목적, 배경, 상세 내용을 작성합니다
- 문서 상태를 "대기"로 설정합니다

#### 2단계: 논의 진행
- 작성된 문서에 대해 위키 코멘트를 통해 논의를 진행합니다
- 관련 있거나 제안하고 싶은 내용에 대해 위키 코멘트를 남깁니다
- 문서 상태를 "논의 진행중"으로 변경합니다

#### 3단계: 합의 도출
- 코멘트와 피드백을 반영하여 문서를 수정합니다
- 충분한 논의와 합의가 이루어졌는지 확인합니다

#### 4단계: 표준 선포
- 최종 합의된 내용으로 문서를 확정합니다
- 문서 상태를 "완료"로 변경합니다
- 필요시 전체 구성원에게 공지합니다

## 과제화 프로세스

표준으로 제안된 경우 이후 후속 작업을 위해 업무가 필요해지는 상황이 있습니다.

### 과제화 필요 시 진행 방식

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│   표준 선포      │ ──→ │   과제 필요성    │ ──→ │   백로그 등록    │
│   (프론트엔드 팀) │     │   검토          │     │   (담당 팀)      │
└─────────────────┘     └─────────────────┘     └─────────────────┘
                                                       │
                                                       ▼
                                              ┌─────────────────┐
                                              │   과제 수행      │
                                              │   (담당 팀)      │
                                              └─────────────────┘
```

### 세부 절차

1. **표준 선포**: 프론트엔드 팀에서 표준이 완료됩니다.
2. **과제 필요성 검토**: 해당 표준을 적용하기 위해 추가 개발이나 작업이 필요한지 검토합니다.
3. **백로그 등록**: 과제가 필요한 경우 담당 팀의 백로그에 등록합니다.
4. **과제 수행**: 담당 팀에서 과제를 수행하고 완료합니다.

## 커뮤니케이션 방법

### 위키 코멘트 활용

- **표준 문서는 위키 코멘트를 통해 커뮤니케이션을 진행합니다**
- 관련 있거나 제안하고 싶은 문서에 위키 코멘트를 남겨주세요!

### 논의 발의 방법

1. RFC 폴더에서 새 문서를 생성합니다
2. 표준 제안 내용을 상세히 작성합니다
3. 관련 팀원들에게 공유하고 코멘트를 요청합니다

### 효과적인 논의를 위한 팁

- **명확한 목적 제시**: 표준이 필요한 이유와 기대 효과를 명확히 작성합니다
- **구체적인 제안**: 추상적인 내용보다 구체적인 가이드라인을 제시합니다
- **예시 포함**: 가능한 경우 코드 예시나 사례를 포함합니다
- **열린 자세**: 다양한 의견을 수렴하고 건설적인 논의를 유도합니다
- **적시 응답**: 코멘트에 대해 적절한 시간 내에 응답합니다

## 표준 문서 작성 가이드

### 권장 문서 구조

```markdown
# [표준명]

## 배경
- 이 표준이 필요한 이유
- 현재 상황과 문제점

## 목적
- 이 표준을 통해 달성하고자 하는 목표

## 상세 내용
- 구체적인 가이드라인
- 예시 코드 (필요시)
- 적용 범위

## 예외 사항
- 표준을 적용하지 않아도 되는 경우

## 참고 자료
- 관련 문서 링크
- 외부 참고 자료
```

### 좋은 표준 문서의 특징

- **명확성**: 누구나 이해할 수 있도록 명확하게 작성
- **실용성**: 실제 업무에 바로 적용 가능한 내용
- **유지보수성**: 변경이 필요할 때 쉽게 업데이트 가능
- **합의 기반**: 충분한 논의와 합의를 통해 도출

## 자주 묻는 질문 (FAQ)

### Q: 누구나 표준을 제안할 수 있나요?
A: 네, 프론트엔드 개발팀의 모든 구성원이 표준을 제안할 수 있습니다.

### Q: 표준 논의에 얼마나 시간이 걸리나요?
A: 주제의 복잡성과 영향 범위에 따라 다르지만, 일반적으로 2-4주 정도의 논의 기간을 가집니다.

### Q: 완료된 표준을 수정할 수 있나요?
A: 네, 완료된 표준도 업데이트가 필요한 경우 "업데이트 공유" 상태로 변경하여 수정할 수 있습니다.

### Q: 표준을 반드시 따라야 하나요?
A: 표준은 가이드라인이며, 특수한 상황에서는 예외가 인정될 수 있습니다. 다만, 예외 적용 시에는 그 이유를 명확히 문서화해야 합니다.
