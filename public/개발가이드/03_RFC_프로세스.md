## 1. AI 기반 RFC 초안 자동 생성

RFC 작성의 가장 큰 병목은 초안 작성이다. AI를 활용하면 기술 비교, 장단점 분석, 대안 조사를 자동화하여 초안 작성 시간을 80% 이상 단축할 수 있다.

### 1.1 AI 초안 생성 워크플로우

```
1. 작성자가 배경/문제/제약 조건을 정리 (10분)
2. AI에 프롬프트 입력 -> RFC 초안 자동 생성 (2분)
3. 작성자가 팀 고유 맥락(레거시, 인력, 일정) 보완 (20분)
4. AI 자동 리뷰로 초안 품질 사전 점검 (2분)
5. Review 상태로 전환하여 팀 논의 시작
```

### 1.2 AI 초안 생성 시 주의사항

| 항목 | 설명 |
|------|------|
| **팀 맥락 보완 필수** | AI는 팀의 레거시 코드, 인력 구성, 조직 문화를 모른다. 반드시 사람이 보완한다 |
| **데이터 출처 검증** | AI가 제시한 벤치마크, 통계, 사례의 출처를 반드시 확인한다 |
| **최신 정보 확인** | AI 학습 데이터의 기준 시점을 고려하여 최신 버전/기능을 별도 검증한다 |
| **복수 AI 교차 검증** | 중요한 RFC는 Claude와 GPT 등 복수 AI로 교차 검증하여 편향을 줄인다 |

## 2. AI 기반 RFC 자동 리뷰

### 2.1 AI 리뷰 활용 범위

| 리뷰 관점 | AI 자동화 | 사람 판단 필수 | 설명 |
|-----------|:---:|:---:|------|
| **영향도 분석** | O | - | 코드베이스/팀/프로세스에 미치는 영향 자동 식별 |
| **대안 평가** | O | - | 누락된 대안 제안, 각 대안의 장단점 보완 |
| **논리적 허점 탐지** | O | - | 숨겨진 가정, 논리 비약, 근거 부족 식별 |
| **리스크 식별** | O | - | 보안/성능/접근성/호환성 관점 누락 리스크 탐지 |
| **템플릿 준수 검사** | O | - | 필수 섹션 누락, 용어 일관성, 가독성 점검 |
| **비즈니스 적합성** | - | O | 조직 전략/우선순위와의 정합성은 사람이 판단 |
| **조직 문화 적합성** | - | O | 팀 역량/문화와의 적합성은 사람이 판단 |

### 2.2 AI 리뷰 결과 처리 기준

| AI 리뷰 결과 | 조치 |
|-------------|------|
| **Critical** (논리적 결함, 중대한 리스크 누락) | 반드시 수정 후 재리뷰, Review 상태 전환 차단 |
| **Warning** (대안 누락, 불충분한 근거) | 작성자가 보완하고 변경 이력에 기록 |
| **Info** (문서 품질, 용어 일관성) | 작성자 재량으로 반영 |
| **False Positive** | AI 리뷰 결과에 반박 근거를 기록하고 무시 |

### 2.3 AI 리뷰 체크리스트

- [ ] 문제 정의가 구체적이고 데이터로 뒷받침되는가
- [ ] 대안이 3개 이상이며 공정하게 평가되었는가
- [ ] 숨겨진 가정(hidden assumption)이 식별되었는가
- [ ] 구현 계획에 롤백 전략이 포함되었는가
- [ ] 성공/실패 지표가 측정 가능한가
- [ ] 보안, 성능, 접근성 관점이 누락되지 않았는가
- [ ] AI가 제시한 벤치마크 데이터의 출처가 검증되었는가
- [ ] 영향받는 팀/코드베이스/프로세스가 빠짐없이 식별되었는가

## 3. RFC 라이프사이클

### 3.1 상태 흐름

```
Draft (초안)
  |
  +-- 작성자가 AI로 RFC 초안 자동 생성
  +-- AI 자동 리뷰로 초안 품질 사전 점검
  +-- 챔피언(Champion) 지정
  |
  v
Review (리뷰)
  |
  +-- 비동기 코멘트 수집 (최소 5영업일)
  +-- AI 리뷰 결과 팀에 공유
  +-- 필요 시 동기 회의 (30분 이내 타임박싱)
  +-- 대안 추가/수정
  |
  v
Accepted / Rejected (결정)
  |
  +-- 의사결정 매트릭스 기반 평가
  +-- 거버넌스 기준에 따른 승인
  +-- ADR(Architecture Decision Record) 연동
  |
  v
Implemented (구현)
  |
  +-- 구현 계획 수립 (Phase별 마일스톤)
  +-- 멀티 베타 환경에서 검증 (해당 시)
  +-- 진행 상황 정기 공유
  +-- 완료 후 회고 및 성공 지표 측정
```

### 3.2 상태 정의

| 상태 | 설명 | 다음 상태 |
|------|------|----------|
| **Draft** | 초안 작성 중. AI 초안 생성 + AI 리뷰 수행 | Review |
| **Review** | 공식 리뷰 요청 상태. 논의 타이머 시작 | Accepted / Rejected / Withdrawn |
| **Accepted** | 승인됨. 구현 진행 | Implemented / Superseded |
| **Rejected** | 기각됨. 사유 기록 필수 | (종료) |
| **Implemented** | 구현 완료. 성과 지표 기록 | Superseded / Deprecated |
| **Superseded** | 새로운 RFC로 대체됨 | (종료) |
| **Withdrawn** | 작성자가 자발적으로 철회 | (종료) |
| **Deprecated** | 더 이상 유효하지 않음 | (종료) |

### 3.3 타임라인 가이드

| 규모 | 논의 기간 | 최소 리뷰어 | 예시 |
|------|----------|------------|------|
| Small | 3영업일 | 2명 | 린팅 규칙 변경, 유틸 패턴 표준화 |
| Medium | 5영업일 | 3명 | 상태 관리 라이브러리 변경, 테스트 전략 |
| Large | 10영업일 | 5명 + 아키텍트 | 멀티 베타 환경 도입, 모노레포 전환, 렌더링 전략 변경 |

## 4. RACI 거버넌스

### 4.1 역할 정의 (RACI 매트릭스)

| 활동 | 작성자 (Author) | 챔피언 (Champion) | 리뷰어 (Reviewer) | 승인권자 (Approver) |
|------|:---:|:---:|:---:|:---:|
| RFC 초안 작성 (AI 활용) | **R** | I | - | - |
| AI 자동 리뷰 실행 | R | I | - | - |
| 비동기 코멘트 | R | C | **R** | I |
| 쟁점 중재 | I | **R** | C | I |
| 최종 승인/기각 | I | C | C | **R** |
| 구현 추적 | **R** | A | I | I |
| 성과 지표 검증 | R | **A** | I | I |

> R: Responsible(실행) / A: Accountable(책임) / C: Consulted(자문) / I: Informed(통보)

### 4.2 승인 기준

| RFC 규모 | 승인 요건 | 승인권자 |
|---------|----------|---------|
| Small | 리뷰어 2명 승인 | 챔피언 |
| Medium | 리뷰어 3명 승인 + 시니어 1명 | 테크 리드 |
| Large | 리뷰어 5명 승인 + 아키텍처 리뷰 | 아키텍트 / CTO |

### 4.3 의사결정 판단 기준

```
1. 되돌릴 수 있는가? (Reversibility)
   +-- 쉽게 되돌릴 수 있음 -> 빠르게 결정, 실행 후 학습
   +-- 되돌리기 어려움 -> 충분한 논의, 신중한 결정

2. 영향 범위는? (Blast Radius)
   +-- 단일 팀 -> 해당 팀 내 결정
   +-- 다수 팀 -> 관련 팀 합의 필요
   +-- 전사 -> 아키텍처 위원회 검토

3. 긴급한가? (Urgency)
   +-- 긴급 (장애, 보안) -> 간소화 프로세스 적용
   +-- 비긴급 -> 표준 프로세스 적용
```

### 4.4 분쟁 해결

1. **1단계**: 작성자-리뷰어 간 비동기 논의
2. **2단계**: 챔피언 중재 (동기 회의, 30분 제한)
3. **3단계**: 테크 리드 최종 결정 (결정 사유 기록 필수)

## 5. 비동기 의사결정 프로세스

### 5.1 비동기 우선 원칙

RFC 논의는 **비동기를 기본**으로 한다. 동기 회의는 비동기로 해결되지 않는 쟁점이 있을 때만 소집한다.

### 5.2 도구별 활용 가이드

| 플랫폼 | 활용 방법 | 적합한 상황 |
|--------|----------|-----------|
| **GitHub Discussions** | RFC 전용 카테고리 생성, 스레드 기반 논의 | 코드 기반 기술 결정 |
| **Notion** | RFC 데이터베이스 생성, 인라인 코멘트 활용 | 비개발자 포함 논의, 시각적 문서 |
| **GitHub PR** | Draft PR로 RFC 등록, 코드 리뷰 방식 논의 | 구현과 밀접한 기술 결정 |
| **Slack/Teams** | 쟁점 알림, 투표, 빠른 의견 수집 | 리마인더, 간단한 의견 조율 |

### 5.3 비동기 리뷰 가이드라인

**리뷰어 역할**:
- 지정받은 후 **2영업일 이내** 최소 1회 코멘트
- 반대 의견은 반드시 **대안 제시**와 함께 기록
- "LGTM"만으로는 충분하지 않음 -- 동의 근거를 1줄 이상 작성

**작성자 역할**:
- 모든 코멘트에 **2영업일 이내** 응답
- 반영한 내용은 변경 이력에 기록
- 논의가 교착 상태면 동기 회의 소집 또는 챔피언에게 에스컬레이션

### 5.4 비동기 의사결정 매커니즘

#### Lazy Consensus (소규모 RFC)
- 제안 후 3영업일 이내 반대 의견이 없으면 자동 승인
- 반대 의견 발생 시 일반 논의 프로세스로 전환

#### 명시적 승인 (중/대규모 RFC)
- 필수 리뷰어 전원의 명시적 승인 필요
- 승인 기한 초과 시 챔피언이 리마인더 발송
- 2주 이상 미응답 시 해당 리뷰어 제외 후 진행

#### 투표 (의견 분열 시)
- 찬성/반대/중립 3가지 선택지
- 과반수 기준 결정 (동점 시 챔피언 결정권)
- 투표 전 반드시 각 입장의 근거를 문서화

### 프롬프트 1: RFC 초안 생성

```text

- 현재 상태: {현재 기술/프로세스 설명}
- 문제점: {해결하려는 핵심 문제}

## 8. 실전 RFC 예시: 멀티 베타 환경 도입

```markdown
# RFC-071: PR별 멀티 베타 환경 동적 프로비저닝 도입

## 메타 정보

| 항목 | 내용 |
|------|------|
| 작성자 | @infra-engineer |
| 챔피언 | @tech-lead |
| 작성일 | YYYY-MM-DD |
| 상태 | Accepted |
| 규모 | Large |
| AI 보조 | Claude (초안 생성, 대안 분석, CDK 코드 생성) |

## 1. 요약

PR이 생성될 때마다 독립된 S3 + CloudFront 인프라를 CDK로 자동 프로비저닝하고,
PR이 머지/닫힐 때 자동으로 정리하는 멀티 베타 환경을 도입한다.

## 2. 동기

### 2.1 현재 상황
- 스테이징 환경 1개를 전체 팀이 공유
- 배포 순서 충돌로 평균 대기 시간 4시간
- QA 팀이 여러 기능을 동시에 검증할 수 없음

### 2.2 문제점
- 정량적: 스테이징 배포 대기 시간 4시간, 주간 배포 충돌 평균 6회
- 정성적: 개발자 배포 대기 스트레스, QA 병목

### 2.3 목표
- PR별 독립 베타 환경 자동 생성 (프로비저닝 10분 이내)
- 배포 대기 시간 0으로 감소
- 동시 N개 기능의 병렬 QA 가능

### 2.4 비목표
- 백엔드 API 멀티 베타 (프론트엔드 정적 배포만 대상)
- 데이터베이스 격리 (공유 스테이징 API 사용)

## 3. 제안

### 3.1 핵심 제안
AWS CDK TypeScript로 PR별 S3 버킷 + CloudFront Distribution을 동적 생성하고,
GitHub Actions에서 PR 라이프사이클과 연동하여 자동 프로비저닝/정리한다.

### 3.2 기술 설계

```typescript
// 핵심 인프라 구성 요약
interface BetaInfrastructure {
  s3Bucket: string;            // beta-{pr}-{hash} 형태
  cloudFrontDistribution: string;
  customDomain: string;        // pr-{number}.beta.example.com
  ttlDays: number;             // 기본 7일
  featureFlags: string[];      // Edge Function 라우팅용
}

// 라이프사이클
type BetaLifecycle =
  | 'PR opened -> CDK Deploy'
  | 'PR synchronized -> S3 sync + CF invalidation'
  | 'PR closed -> CDK Destroy'
  | 'TTL expired -> Scheduled sweep';
```

### 3.3 구현 계획

| Phase | 기간 | 내용 | 산출물 |
|-------|------|------|--------|
| Phase 1 | 2주 | CDK 스택 개발 + 단일 PR 테스트 | CDK 코드, GitHub Actions |
| Phase 2 | 2주 | Feature Flag Edge 라우팅 + 비용 모니터링 | Edge Function, 비용 대시보드 |
| Phase 3 | 2주 | 전체 팀 적용 + 자동 정리 스케줄 | 운영 가이드, 모니터링 알림 |

## 4. 대안 분석 (AI 자동 생성 + 사람 보완)

| 기준 | 가중치 | CDK 동적 생성 | Terraform Workspace | 단일 S3 경로 분리 |
|------|--------|--------------|--------------------|--------------------|
| 환경 격리 수준 | 30% | 10 | 9 | 5 |
| 프로비저닝 속도 | 25% | 7 | 6 | 10 |
| 비용 효율성 | 20% | 8 | 7 | 10 |
| 운영 복잡도 | 15% | 7 | 6 | 9 |
| 확장성 | 10% | 9 | 8 | 4 |
| **가중 총점** | | **8.30** | **7.25** | **7.45** |

**CDK 동적 생성 선택 사유**:
- 가장 높은 환경 격리 수준 (독립 CloudFront Distribution)
- TypeScript 기반으로 프론트엔드 팀 친화적
- AWS 네이티브 통합 (태깅, 비용 추적, 모니터링)

## 5. AI 리뷰 결과

| 항목 | 등급 | 피드백 |
|------|------|--------|
| 문제 정의 | 통과 | 정량적 근거(대기 시간, 충돌 횟수) 충분 |
| 대안 분석 | 보완 필요 | Vercel Preview 대안 누락 -> 외부 서비스 의존성 사유로 제외 기록 |
| 비용 분석 | 보완 필요 | N개 환경 시 비용 시뮬레이션 추가 필요 -> 비용 최적화 섹션 추가 |
| 리스크 | 통과 | CDK Deploy 실패, 고아 리소스 등 핵심 리스크 식별됨 |
| 성공 지표 | 통과 | 측정 가능하고 현실적 |

## 6. 성공 지표

| 지표 | 현재 | 목표 | 측정 시점 |
|------|------|------|----------|
| 배포 대기 시간 | 4시간 | 0분 | Phase 1 완료 후 |
| 프로비저닝 시간 | N/A | 10분 이내 | Phase 1 완료 후 |
| 주간 배포 충돌 | 6회 | 0회 | Phase 3 완료 후 |
| 동시 QA 환경 수 | 1개 | 무제한 | Phase 3 완료 후 |
| 월간 추가 인프라 비용 | $0 | $50 이내 | Phase 3 완료 후 |
```
