## 1. AI 기반 코드 리뷰 혁명

2026년 코드 리뷰의 패러다임은 **"AI First, Human Final"**이다. AI가 1차 리뷰를 수행하고, 사람은 비즈니스 맥락과 아키텍처 판단에 집중한다.

### 1.1 GitHub Copilot Code Review 설정 및 활용

GitHub Copilot Code Review는 PR이 열릴 때 자동으로 코드를 분석하고 인라인 코멘트를 남긴다.

```yaml
# .github/copilot-review.yml
review:
  auto_review: true
  review_language: "ko"
  focus_areas:
    - security
    - performance
    - error-handling
    - type-safety
    - accessibility
  severity_threshold: "medium"  # low, medium, high, critical
  ignore_paths:
    - "**/*.test.ts"
    - "**/*.spec.ts"
    - "**/*.stories.tsx"
    - "**/generated/**"
    - "**/migrations/**"
  custom_rules:
    - id: "no-any-type"
      description: "any 타입 사용 금지"
      severity: "high"
    - id: "async-error-handling"
      description: "async 함수에서 try-catch 필수"
      severity: "medium"
    - id: "max-function-length"
      description: "함수 길이 50줄 이하 권장"
      severity: "low"
  auto_approve:
    enabled: false  # AI 자동 승인은 비활성화 권장
```

**활용 팁:**

- PR 설명에 `@copilot review` 태그를 추가하면 수동 재리뷰 요청 가능
- 특정 파일만 집중 리뷰: `@copilot review --focus src/auth/`
- 리뷰 결과에 대해 `@copilot explain` 으로 추가 설명 요청

### 1.2 Claude Code Review 워크플로우

Claude는 대규모 코드베이스의 맥락을 깊이 이해하며, 특히 아키텍처 수준의 피드백에 강점이 있다.

**프롬프트 예시 1 — 보안 리뷰:**

```
이 PR의 변경사항을 보안 관점에서 리뷰해줘.

중점 확인 항목:
- 사용자 입력 검증 누락 (XSS, SQL Injection, Path Traversal)
- 인증/인가 우회 가능성
- 민감 데이터 노출 (로그, 에러 메시지, API 응답)
- 의존성의 알려진 취약점 (CVE)
- 환경변수/시크릿 하드코딩

각 발견사항에 대해 [심각도: Critical/High/Medium/Low]와
구체적인 수정 코드를 제시해줘.
```

**프롬프트 예시 2 — 성능 리뷰:**

```
이 코드의 성능 병목을 분석해줘.

확인 관점:
- 불필요한 리렌더링 유발 패턴 (React)
- N+1 쿼리 또는 비효율적 데이터 페칭
- 메모리 누수 가능성 (이벤트 리스너, 구독 해제 누락)
- 번들 사이즈 영향 (tree-shaking 불가능 import)
- 큰 리스트의 가상화 미적용

각 항목에 대해 Before/After 코드와 예상 성능 개선 효과를 제시해줘.
```

**프롬프트 예시 3 — 아키텍처 리뷰:**

```
이 PR이 기존 아키텍처에 미치는 영향을 분석해줘.

확인 관점:
- 레이어 간 의존성 방향 위반 (Clean Architecture)
- 도메인 로직이 인프라 계층에 누출되었는지
- 인터페이스 분리 원칙(ISP) 준수 여부
- 변경의 영향 범위와 결합도
- 향후 확장 시 예상되는 제약사항

구체적인 의존성 다이어그램 변화와 대안 설계를 제시해줘.
```

### 1.3 CodeRabbit 설정 및 커스텀 규칙

CodeRabbit은 PR을 자동 요약하고, 변경 파일 단위로 점진적 리뷰를 제공한다.

```yaml
# .coderabbit.yaml
language: "ko"
tone_instructions: "간결하고 실용적인 톤. 구체적인 수정 코드를 포함할 것."

early_access: true

reviews:
  auto_review:
    enabled: true
    drafts: false
    base_branches:
      - main
      - develop
  request_changes_workflow: true
  high_level_summary: true
  high_level_summary_placeholder: "@coderabbitai summary"
  poem: false  # PR 시 생성은 비활성화

  path_instructions:
    - path: "src/api/**"
      instructions: |
        API 엔드포인트 변경 시 다음을 확인:
        - OpenAPI 스펙과의 일치 여부
        - 에러 응답 형식 표준 준수
        - Rate limiting 설정 적절성
        - 인증/인가 미들웨어 적용 여부
    - path: "src/components/**"
      instructions: |
        컴포넌트 변경 시 다음을 확인:
        - Props 인터페이스의 확장성
        - 접근성(a11y) 속성 누락
        - 불필요한 리렌더링 방지 (memo, useMemo, useCallback)
    - path: "src/hooks/**"
      instructions: |
        커스텀 훅 변경 시 다음을 확인:
        - 의존성 배열의 정확성
        - cleanup 함수 구현 여부
        - 반환 타입의 명확성

  path_filters:
    - "!dist/**"
    - "!node_modules/**"
    - "!*.lock"
    - "!**/*.generated.ts"

  tools:
    eslint:
      enabled: true
    biome:
      enabled: true
    github-checks:
      enabled: true
    ast-grep:
      enabled: true
      packages:
        - "typescript-security-rules"

chat:
  auto_reply: true
```

### 1.4 AI vs 사람 역할 분담 매트릭스

| 리뷰 영역 | AI 담당 | 사람 담당 | 비고 |
|-----------|---------|----------|------|
| 코딩 컨벤션/포맷팅 | **주도** | 예외 승인 | Lint로 자동 차단, AI가 나머지 검출 |
| 일반 버그 패턴 | **주도** | 최종 확인 | null 참조, off-by-one, 타입 오류 |
| 보안 취약점 | **1차 스캔** | **최종 판단** | AI 스캔 + 사람의 맥락 기반 검증 |
| 성능 이슈 | **탐지** | **판단** | AI가 후보를 제시, 사람이 트레이드오프 결정 |
| 비즈니스 로직 | 보조 | **주도** | 도메인 지식 필요, AI는 논리 흐름만 분석 |
| 아키텍처 적합성 | 보조 | **주도** | 팀 컨텍스트, 장기 전략 고려 필요 |
| 도메인 모델링 | 패턴 제안 | **주도** | 유비쿼터스 언어 준수는 사람만 판단 가능 |
| 테스트 커버리지 | **측정** | 전략 결정 | 커버리지 수치는 AI, 무엇을 테스트할지는 사람 |
| 팀원 멘토링 | 참고자료 제공 | **주도** | 성장 피드백은 반드시 사람이 직접 전달 |
| PR 요약/영향 분석 | **주도** | 검증 | AI가 자동 생성, 사람이 정확성 확인 |

### 1.5 AI 리뷰 결과 활용 원칙 — 맹신 금지

AI 리뷰는 강력한 도구이나, 다음 원칙을 반드시 지킨다:

**검증 체크리스트:**

```markdown
## AI 리뷰 검증 체크리스트

- [ ] AI가 제안한 코드 변경이 현재 프로젝트 컨텍스트에 적합한가?
- [ ] AI가 놓친 비즈니스 로직 오류는 없는가?
- [ ] AI의 보안 경고 중 오탐(false positive)은 없는가?
- [ ] AI가 제안한 성능 개선이 실제로 측정 가능한 차이를 만드는가?
- [ ] AI의 리팩토링 제안이 팀 컨벤션과 일치하는가?
- [ ] AI가 참조한 라이브러리 API가 현재 사용 버전과 일치하는가?
- [ ] AI가 생성한 코드에 환각(hallucination) 패턴이 없는가?
```

**AI 오탐 관리 프로세스:**

```typescript
// 팀 내 AI 리뷰 오탐 기록 및 피드백 루프
interface AIReviewFalsePositive {

  category: 'security' | 'performance' | 'style' | 'bug';
  description: string;
  codeContext: string;
  reportedAt: string;
  resolution: 'config-updated' | 'rule-disabled' | 'accepted-as-noise';
}

// 월간 AI 리뷰 품질 리포트에 오탐 비율 포함
// 오탐률이 20%를 초과하면 해당 규칙/도구 설정 재검토
```

## 2. 코드 리뷰 마인드셋 2026

### 2.1 심리적 안전성 기반 리뷰

코드 리뷰는 코드의 품질을 높이는 과정이지, 사람을 평가하는 과정이 아니다.

**좋은 리뷰 vs 나쁜 리뷰 비교:**

| 상황 | 나쁜 예시 | 좋은 예시 |
|------|----------|----------|
| 로직 오류 발견 | "이 코드 왜 이렇게 짰어요?" | "이 부분에서 edge case가 발생할 수 있어요. `amount`가 0일 때 어떻게 동작할까요?" |
| 더 나은 방법 제안 | "이건 안티패턴입니다." | "suggestion: `useMemo`로 감싸면 리렌더링을 줄일 수 있어요. 관련 문서를 첨부합니다." |
| 이해 안 되는 코드 | "이건 뭐예요? 설명 좀..." | "question: 이 변환 로직의 의도가 궁금합니다. 어떤 시나리오를 처리하기 위한 건가요?" |
| 설계 의견 차이 | "이 설계는 틀렸습니다." | "thought: 다른 접근도 고려해볼 수 있을 것 같아요. Strategy 패턴을 쓰면 확장이 쉬워질 수 있는데, 어떻게 생각하세요?" |
| 좋은 코드 발견 | (코멘트 없음) | "praise: 이 에러 핸들링 방식 깔끔하네요. 팀 전체에 공유하면 좋겠어요." |
| 사소한 스타일 | "스타일 가이드 좀 읽으세요." | "nit: 네이밍이 `getUserList`보다 `fetchUsers`가 팀 컨벤션에 맞아요. 다만 blocking은 아닙니다." |

### 2.2 Conventional Comments 고도화

[Conventional Comments](https://conventionalcomments.org/) 형식에 **blocking/non-blocking 데코레이션**을 추가한다.

**형식:**

```
<label> (<decoration>): <subject>

[discussion]
```

**라벨과 데코레이션 체계:**

| 라벨 | 용도 | 기본 데코레이션 |
|------|------|----------------|
| `suggestion` | 개선 제안 | non-blocking |
| `issue` | 반드시 수정 필요 | **blocking** |
| `question` | 이해를 위한 질문 | non-blocking |
| `thought` | 아이디어 공유 | non-blocking |
| `nit` | 사소한 스타일 | non-blocking |
| `praise` | 칭찬 | non-blocking |
| `todo` | 후속 작업 필요 | non-blocking (if-minor) |
| `typo` | 오타/오류 | non-blocking |

**실제 사용 예시:**

```
issue (blocking): SQL injection 위험이 있습니다.

사용자 입력이 직접 쿼리에 삽입되고 있어요.
parameterized query로 변경해주세요.

Before:
  const query = `SELECT * FROM users WHERE name = '${name}'`;

After:
  const query = 'SELECT * FROM users WHERE name = $1';
  const result = await db.query(query, [name]);
```

```
suggestion (non-blocking): Optional chaining으로 간소화할 수 있어요.

Before:
  const city = user && user.address && user.address.city;

After:
  const city = user?.address?.city;
```

```
todo (non-blocking, if-minor): 이 함수에 JSDoc을 추가하면 좋겠어요.

이번 PR에서 하기 어려우면 후속 이슈로 남겨도 괜찮습니다.
```

### 2.3 비동기 리뷰 효율화 원칙 및 SLA

| 항목 | SLA | 비고 |
|------|-----|------|
| 최초 리뷰 시작 | PR 생성 후 **4시간 이내** (업무시간 기준) | AI 1차 리뷰는 즉시 |
| 리뷰 완료 | PR 생성 후 **1 영업일 이내** | 500줄 미만 기준 |
| 리뷰어 코멘트 응답 | 코멘트 후 **4시간 이내** | 비동기 소통 기본 |
| hotfix PR | PR 생성 후 **2시간 이내** | 라벨: `priority: critical` |
| 재리뷰 요청 | 수정 후 **4시간 이내** | re-review 라벨 활용 |

**비동기 리뷰 원칙:**

1. **Self-contained 코멘트** - 한 번에 충분한 맥락을 전달하여 왕복 횟수를 최소화한다
2. **Batch 리뷰** - 파일별로 쪼개지 말고, 전체 PR을 검토한 뒤 한 번에 코멘트를 남긴다
3. **결정 명시** - 각 리뷰에 `Approve`, `Request Changes`, `Comment` 중 하나를 반드시 명시한다
4. **재리뷰 범위 표시** - 수정 시 어떤 코멘트에 대한 대응인지 명확히 표시한다

## 3. PR 작성 Best Practices

### 3.1 500줄 이하 원칙과 분리 전략

```
PR 크기별 리뷰 품질 통계 (Google 연구):

  ~100줄: 리뷰 품질 최상, 결함 발견율 가장 높음
  ~300줄: 리뷰 품질 양호
  ~500줄: 리뷰 품질 저하 시작점
  ~1000줄: 리뷰어가 "LGTM"으로 대충 넘기는 비율 급증
  1500줄+: 사실상 효과적 리뷰 불가능
```

**분리 전략:**

| 전략 | 설명 | 예시 |
|------|------|------|
| **레이어 분리** | 인프라 → 도메인 → UI 순서로 PR 분리 | DB 스키마 PR → API PR → 프론트엔드 PR |
| **기능 분리** | 하나의 기능을 독립된 단위로 분리 | 회원가입 폼 PR → 유효성검증 PR → API 연동 PR |
| **리팩토링 분리** | 기능 변경과 리팩토링을 절대 혼합하지 않음 | 리팩토링 PR (동작 동일) → 기능 추가 PR |
| **테스트 분리** | 테스트 추가만으로 별도 PR | 테스트 PR → 구현 PR (TDD 시) |

### 3.2 Stacked PRs

하나의 큰 기능을 여러 PR로 쪼개되, 의존 관계를 유지하며 순차적으로 리뷰/머지한다.

**Graphite 활용:**

```bash
# Graphite로 스택 생성
gt create -m "feat: 사용자 모델 정의" -a
# ... 코드 수정 ...
gt create -m "feat: 사용자 API 엔드포인트" -a
# ... 코드 수정 ...
gt create -m "feat: 사용자 목록 UI" -a

# 스택 전체 제출
gt submit --stack

# 스택 시각화
gt log
# 출력 예시:
#   main
#   └── feat/user-model
#       └── feat/user-api
#           └── feat/user-ui  ← (현재)
```

**git-branchless 활용:**

```bash
# 스택 브랜치 생성 및 관리
git branchless init
git checkout -b feat/user-model
# ... 코드 수정, 커밋 ...
git checkout -b feat/user-api
# ... 코드 수정, 커밋 ...

# 스택 시각화
git branchless smartlog

# 하위 브랜치 자동 리베이스
git branchless sync
```

### 3.3 PR 템플릿

```markdown
<!-- .github/pull_request_template.md -->

## 변경 사항
<!-- 이 PR에서 무엇을 변경했는지 간결하게 설명 -->

## 변경 이유
<!-- 왜 이 변경이 필요한지 배경과 동기 -->

## 변경 유형
- [ ] 기능 추가 (새로운 기능)
- [ ] 버그 수정 (기존 기능의 문제 해결)
- [ ] 리팩토링 (동작 변경 없는 코드 개선)
```

## 4. 리뷰 체크리스트 — 4관점 심층 가이드

### 4.1 보안

| 체크 항목 | Bad | Good |
|----------|-----|------|
| 사용자 입력 검증 | `eval(userInput)` | `zod.parse(userInput)` |
| SQL 쿼리 | `` `SELECT * FROM users WHERE id = '${id}'` `` | `db.query('SELECT * FROM users WHERE id = $1', [id])` |
| 민감정보 로깅 | `console.log('Token:', token)` | `console.log('Token: [REDACTED]')` |
| 에러 노출 | `res.json({ error: err.stack })` | `res.json({ error: 'Internal server error', code: 'E001' })` |

```typescript
// Bad: XSS 취약 - dangerouslySetInnerHTML 무방비 사용
function Comment({ content }: { content: string }) {
  return <div dangerouslySetInnerHTML={{ __html: content }} />;
}

// Good: DOMPurify로 sanitize 후 렌더링
import DOMPurify from 'dompurify';

function Comment({ content }: { content: string }) {
  const sanitized = DOMPurify.sanitize(content, {
    ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'p', 'br'],
    ALLOWED_ATTR: [],
  });
  return <div dangerouslySetInnerHTML={{ __html: sanitized }} />;
}
```

### 4.2 성능

| 체크 항목 | Bad | Good |
|----------|-----|------|
| 리렌더링 방지 | 매 렌더링마다 새 객체/함수 생성 | `useMemo`, `useCallback` 활용 |
| 리스트 렌더링 | 인덱스를 key로 사용 | 고유 ID를 key로 사용 |
| 번들 사이즈 | `import _ from 'lodash'` | `import groupBy from 'lodash/groupBy'` |
| 이미지 로딩 | `<img src={url} />` | `<Image src={url} loading="lazy" />` |

```typescript
// Bad: 매 렌더링마다 필터링 재실행 + 불필요한 리렌더링 유발
function UserList({ users, filter }: Props) {
  const filtered = users.filter(u => u.role === filter);
  const handleClick = (id: string) => { navigate(`/user/${id}`); };

  return (
    <ul>
      {filtered.map((user, index) => (
        <li key={index} onClick={() => handleClick(user.id)}>
          {user.name}
        </li>
      ))}
    </ul>
  );
}

// Good: 메모이제이션 + 안정적 key + 콜백 최적화
function UserList({ users, filter }: Props) {
  const filtered = useMemo(
    () => users.filter(u => u.role === filter),
    [users, filter]
  );

  const handleClick = useCallback(
    (id: string) => { navigate(`/user/${id}`); },
    [navigate]
  );

  return (
    <ul>
      {filtered.map(user => (
        <li key={user.id} onClick={() => handleClick(user.id)}>
          {user.name}
        </li>
      ))}
    </ul>
  );
}
```

### 4.3 접근성 (a11y)

| 체크 항목 | Bad | Good |
|----------|-----|------|
| 클릭 요소 | `<div onClick={handleClick}>` | `<button onClick={handleClick}>` |
| 이미지 대체 텍스트 | `<img src={url} />` | `<img src={url} alt="사용자 프로필 사진" />` |
| 폼 라벨 | `<input placeholder="이름" />` | `<label htmlFor="name">이름</label><input id="name" />` |
| 컬러 대비 | `color: #ccc` on white | WCAG AA 기준 4.5:1 이상 |

```typescript
// Bad: 접근성 미준수 모달
function Modal({ isOpen, onClose, children }: ModalProps) {
  if (!isOpen) return null;
  return (
    <div className="overlay" onClick={onClose}>
      <div className="modal">

function Modal({ isOpen, onClose, title, children }: ModalProps) {
  const modalRef = useRef<HTMLDivElement>(null);

  useEffect(() => {
    if (isOpen) modalRef.current?.focus();
  }, [isOpen]);

  if (!isOpen) return null;

  return (
    <div
      className="overlay"
      role="presentation"
      onClick={onClose}
    >
      <div
        ref={modalRef}
        role="dialog"
        aria-modal="true"
        aria-labelledby="modal-title"
        tabIndex={-1}
        onClick={e => e.stopPropagation()}
        onKeyDown={e => e.key === 'Escape' && onClose()}
      >
        <h2 id="modal-title">{title}</h2>
        <button
          onClick={onClose}
          aria-label="모달 닫기"
        >
          X
        </button>
        {children}
      </div>
    </div>
  );
}
```

### 4.4 타입 안전성

| 체크 항목 | Bad | Good |
|----------|-----|------|
| 타입 단언 | `data as UserResponse` | `zod.parse(data)` + 타입 추론 |
| any 타입 | `function process(data: any)` | `function process(data: UserInput)` |
| 옵셔널 처리 | `user.address!.city` | `user.address?.city ?? 'N/A'` |
| API 응답 | 수동 타입 정의 | OpenAPI 스펙에서 자동 생성 |

```typescript
// Good: Zod 스키마로 런타임 검증 + 타입 추론
import { z } from 'zod';

const UserSchema = z.object({
  id: z.string().uuid(),
  name: z.string().min(1),
  email: z.string().email(),
  role: z.enum(['admin', 'member', 'viewer']),
  createdAt: z.string().datetime(),
});

type User = z.infer<typeof UserSchema>;

async function fetchUser(id: string): Promise<User> {
  const response = await fetch(`/api/users/${id}`);

  if (!response.ok) {
    throw new HttpError(response.status, `사용자 조회 실패: ${id}`);
  }

  const data: unknown = await response.json();
  return UserSchema.parse(data);  // 런타임 검증 + 타입 보장
}

function displayUser(user: User): string {
  return `${user.name} (${user.email})`;
```

### 6.2 GitHub API 측정 스크립트

```typescript
// scripts/review-metrics.ts
import { Octokit } from '@octokit/rest';

interface ReviewMetrics {
  prNumber: number;
  title: string;
  linesChanged: number;
  timeToFirstReviewHours: number;
  timeToMergeHours: number;
  reviewRounds: number;
  reviewerCount: number;
}

async function collectReviewMetrics(
  owner: string,
  repo: string,
  days: number = 30,
): Promise<ReviewMetrics[]> {
  const octokit = new Octokit({ auth: process.env.GITHUB_TOKEN });
  const since = new Date(Date.now() - days * 24 * 60 * 60 * 1000);

  const { data: pulls } = await octokit.pulls.list({
    owner,
    repo,
    state: 'closed',
    sort: 'updated',
    direction: 'desc',
    per_page: 100,
  });

  const mergedPRs = pulls.filter(
    pr => pr.merged_at && new Date(pr.created_at) >= since,
  );

  const metrics: ReviewMetrics[] = [];

  for (const pr of mergedPRs) {
    const { data: reviews } = await octokit.pulls.listReviews({
      owner,
      repo,
      pull_number: pr.number,
    });

    const humanReviews = reviews.filter(
      r => !r.user?.login?.includes('[bot]'),
    );

    const firstReview = humanReviews[0];
    const createdAt = new Date(pr.created_at).getTime();
    const mergedAt = new Date(pr.merged_at!).getTime();
    const firstReviewAt = firstReview
      ? new Date(firstReview.submitted_at!).getTime()
      : mergedAt;

    const reviewRounds = new Set(
      humanReviews
        .filter(r => r.state === 'CHANGES_REQUESTED')
        .map(r => r.user?.login),
    ).size;

    metrics.push({
      prNumber: pr.number,
      title: pr.title,
      linesChanged: (pr.additions ?? 0) + (pr.deletions ?? 0),
      timeToFirstReviewHours:
        Math.round((firstReviewAt - createdAt) / (1000 * 60 * 60) * 10) / 10,
      timeToMergeHours:
        Math.round((mergedAt - createdAt) / (1000 * 60 * 60) * 10) / 10,
      reviewRounds,
      reviewerCount: new Set(humanReviews.map(r => r.user?.login)).size,
    });
  }

  return metrics;
}

async function printSummary(owner: string, repo: string): Promise<void> {
  const metrics = await collectReviewMetrics(owner, repo);

  if (metrics.length === 0) {
    console.log('측정 대상 PR이 없습니다.');
    return;
  }

  const avg = (arr: number[]) =>
    Math.round((arr.reduce((a, b) => a + b, 0) / arr.length) * 10) / 10;

  const avgFirstReview = avg(metrics.map(m => m.timeToFirstReviewHours));
  const avgMergeTime = avg(metrics.map(m => m.timeToMergeHours));
  const avgSize = avg(metrics.map(m => m.linesChanged));
  const avgRounds = avg(metrics.map(m => m.reviewRounds));
  const oversizedPRs = metrics.filter(m => m.linesChanged > 500).length;

  console.log('=== 코드 리뷰 메트릭스 (최근 30일) ===');
  console.log(`분석 PR 수: ${metrics.length}개`);
  console.log(`평균 최초 리뷰 시간: ${avgFirstReview}시간 (목표: <4시간)`);
  console.log(`평균 머지 시간: ${avgMergeTime}시간 (목표: <24시간)`);
  console.log(`평균 PR 크기: ${avgSize}줄 (목표: <500줄)`);
  console.log(`평균 리뷰 라운드: ${avgRounds}회 (목표: <=2회)`);
  console.log(
    `500줄 초과 PR: ${oversizedPRs}개 (${Math.round((oversizedPRs / metrics.length) * 100)}%)`,
  );

  // SLA 위반 PR 목록
  const slaViolations = metrics.filter(m => m.timeToFirstReviewHours > 4);
  if (slaViolations.length > 0) {
    console.log(`\n⚠ 최초 리뷰 SLA(4시간) 위반 PR: ${slaViolations.length}개`);
    slaViolations.forEach(m =>
      console.log(`  #${m.prNumber}: ${m.timeToFirstReviewHours}시간 - ${m.title}`),
    );
  }
}

// 실행
const [owner, repo] = (process.env.GITHUB_REPOSITORY ?? '/').split('/');
printSummary(owner, repo).catch(console.error);
```

## 7. 원격/비동기 팀 리뷰 전략

### 7.1 시차 대응 전략

여러 시간대에 걸친 팀의 경우, 리뷰 병목을 방지하기 위한 전략이 필요하다.

| 전략 | 설명 | 적용 시점 |
|------|------|----------|
| **겹치는 시간대 활용** | 팀원 간 겹치는 업무시간에 동기 리뷰 집중 | 매일 |
| **리뷰 버디 시스템** | 같은 시간대 동료를 1차 리뷰어로 지정 | 상시 |
| **시간대별 리뷰어 풀** | CODEOWNERS에 시간대별 그룹 구성 | PR 생성 시 |
| **AI 1차 리뷰 위임** | 비업무시간 PR은 AI가 즉시 1차 리뷰 | 자동 |
| **비동기 승인 정책** | 1명 승인 + AI 리뷰 통과 시 머지 허용 | 긴급 시 |

```
# 시간대별 리뷰 플로우 예시
#
# [KST 09:00] 개발자 A가 PR 생성
#       ↓
# [즉시] AI 봇이 1차 리뷰 코멘트 생성
#       ↓
# [KST 10:00] 같은 시간대 리뷰어 B가 리뷰 시작
#       ↓
# [KST 14:00] 리뷰어 B 승인 → 머지
#
# -- 만약 B가 부재 시 --
#
# [KST 18:00 = PST 01:00] PST 시간대 리뷰어 C가 리뷰
#       ↓
# [다음날 KST 09:00] A가 피드백 반영 → 재리뷰 요청
```

### 7.2 비디오 리뷰

텍스트 코멘트로 전달하기 어려운 복잡한 피드백은 **비디오 리뷰**를 활용한다.

**비디오 리뷰가 효과적인 경우:**

- 아키텍처 수준의 설계 변경 제안
- 여러 파일에 걸친 복잡한 상호작용 설명
- 주니어 개발자 멘토링 목적의 상세 리뷰
- 텍스트로 3회 이상 왕복이 예상되는 논의

**비디오 리뷰 가이드라인:**

```
1. 길이: 5~10분 이내 (길면 챕터로 분리)
2. 도구: Loom, Screen Studio 등 화면 녹화 도구
3. 형식:
   - 코드를 화면에 띄우고 커서로 가리키며 설명
   - 문제점 → 개선안 → 구체적 코드 변경 순서로 진행
4. 공유: PR 코멘트에 링크 첨부
5. 요약: 비디오 내용을 텍스트 bullet으로도 요약 (검색 가능성)
```

### 7.3 Pair Review 패턴

두 사람이 실시간으로 함께 코드를 리뷰하는 방식. 비동기 리뷰 대비 깊이 있는 논의가 가능하다.

**언제 Pair Review를 사용하는가:**

| 상황 | 권장 방식 |
|------|----------|
| 500줄 이하, 단순 변경 | 비동기 리뷰 |
| 500줄 이상, 복잡한 로직 | **Pair Review** |
| 신규 아키텍처 도입 | **Pair Review** + 문서화 |
| 보안 민감 변경 | **Pair Review** (보안 전문가 참여) |
| 온보딩 중인 신규 팀원 PR | **Pair Review** (멘토링 목적) |
| 핫픽스 긴급 배포 | **Pair Review** (빠른 의사결정) |

**Pair Review 진행 방식:**

```
1. 사전 준비 (10분)
   - 리뷰어가 PR diff를 미리 읽고 질문/코멘트 초안 작성

2. 실시간 세션 (20~40분)
   - 작성자가 변경의 배경과 의도를 설명 (5분)
   - 코드를 함께 순회하며 논의 (15~30분)
   - 합의된 액션 아이템 정리 (5분)

3. 후속 작업
   - 합의 사항을 PR 코멘트로 기록 (비디오 리뷰 대비 검색 가능)
   - 작성자가 수정 후 비동기로 재리뷰 요청
```

### 7.4 리뷰 문화 성숙도 모델

팀의 리뷰 문화를 점진적으로 발전시키기 위한 로드맵:

| 단계 | 특징 | 목표 |
|------|------|------|
| **Level 1: 기본** | 리뷰 의무화, 1명 이상 승인 | 리뷰 습관 형성 |
| **Level 2: 구조화** | Conventional Comments, PR 템플릿, SLA | 리뷰 품질 표준화 |
| **Level 3: 자동화** | AI 리뷰, CI 품질 게이트, CODEOWNERS | 사람의 리뷰 부담 감소 |
| **Level 4: 데이터 기반** | 메트릭스 측정, DORA 연계, 주간 리포트 | 지속적 개선 |
| **Level 5: 문화** | 심리적 안전성, Pair Review, 멘토링 | 팀 역량 전체 향상 |
