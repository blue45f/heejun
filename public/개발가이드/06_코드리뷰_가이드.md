## 코드 리뷰의 목적

| 순서 | 목표 | 효과 |
|------|------|------|
| 1차 | 코드 품질 향상 | 버그 조기 발견 → 프로덕션 장애 방지 |
| 2차 | 지식 공유 | 코드를 통한 학습 → 팀 전체 역량 향상 |
| 3차 | 팀 문화 구축 | 건설적인 피드백 → 신뢰와 성장의 문화 |

## 코드 리뷰 8가지 마인드셋

### 1. 코드에 대한 리뷰, 사람에 대한 리뷰가 아님
- ❌ "이렇게 짜면 안 되죠"
- ✅ "이 부분은 이렇게 개선하면 어떨까요?"

### 2. 질문으로 시작하기
- ❌ "이거 왜 이렇게 했어요?"
- ✅ "이 접근법을 선택한 이유가 궁금합니다"

### 3. 칭찬도 리뷰의 일부
- ✅ "이 추상화 정말 깔끔하네요!"
- ✅ "테스트 코드가 읽기 쉽게 작성되었습니다"
- ✅ "에러 처리를 꼼꼼히 하셨네요"

### 4. 구체적인 제안하기
- ❌ "성능 개선이 필요해 보입니다"
- ✅ "useMemo를 사용하면 불필요한 재계산을 막을 수 있을 것 같습니다"

### 5. 배울 자세로 임하기
- ✅ "저는 이렇게 접근했었는데, 이 방법이 더 나은 이유가 뭘까요?"

### 6. 니트픽(Nitpick)과 블로커(Blocker) 구분
- 🔴 **Blocker**: 반드시 수정 필요
- 🟡 **Suggestion**: 수정 권장
- 🔵 **Nitpick**: 사소한 의견

### 7. 신속한 리뷰
- 목표: 24시간 이내 첫 리뷰
- 이상: 4시간 이내

### 8. 논쟁보다 대화
- 의견 차이 → Slack/대면 논의 → 팀 컨벤션으로 정리

## PR 작성 가이드

### PR 크기

**이상적인 크기:**
- 변경 라인: ~200줄 (최대 400줄 이내 권장)
- 파일 개수: ~10개
- 리뷰 시간: ~20분

> 연구에 따르면 200줄 이하의 PR은 결함 발견율이 70~90%인 반면, 400줄을 넘어가면 발견율이 급격히 떨어집니다.

**너무 큰 PR의 문제:**
- 리뷰어 부담 증가
- 리뷰 품질 하락
- 머지 충돌 가능성 증가
- 문제 발생 시 롤백 어려움

**Trunk-Based Development와 PR 크기:**

Trunk-Based Development(TBD)를 사용하는 경우, 작은 PR은 필수입니다:
- 짧은 수명의 브랜치 (최대 1~2일) 유지
- Feature Flag를 활용해 미완성 기능도 안전하게 머지
- 메인 브랜치에 자주, 작게 통합하여 충돌 최소화
- CI가 항상 녹색을 유지하도록 보장

```
# Trunk-Based Development 흐름
main ─────●────●────●────●────●──── (항상 배포 가능)
            \  /      \  /    \  /
  feature-a ●●   fix-b ●●  feat-c ●●  (1~2일 수명)
```

**큰 작업 쪼개는 방법 (예: 결제 시스템 리뉴얼):**
- PR #1: 데이터 모델 변경 (DB, API 타입)
- PR #2: 결제 모듈 리팩토링 (비즈니스 로직)
- PR #3: UI 컴포넌트 개선
- PR #4: 통합 및 E2E 테스트

**Stacked PRs (연쇄 PR) 활용:**

큰 기능을 논리적 단위로 분리하여 순차적으로 리뷰받는 패턴:
- 각 PR이 이전 PR 브랜치를 베이스로 생성
- 도구 활용: GitHub의 base branch 변경, graphite, ghstack 등
- 리뷰어가 작은 단위로 점진적 리뷰 가능

### PR 템플릿

```markdown
## 변경 내용 (What)
이 PR에서 무엇을 변경했는지 간단 명료하게

## 배경 (Why)
왜 이 변경이 필요한지
어떤 문제를 해결하는지

## 접근 방법 (How)
어떻게 구현했는지
주요 기술적 결정 사항

## 테스트 시나리오
어떻게 테스트했는지
- [ ] 단위 테스트 추가/수정
- [ ] 수동 테스트 완료
- [ ] E2E 테스트 (필요 시)

## 영향 범위
어떤 부분에 영향을 미치는지
- 영향받는 페이지/기능:
- API 변경 사항:
- 데이터베이스 변경:

## 배포 참고사항
배포 시 주의할 점
- [ ] 환경 변수 추가 필요
- [ ] DB 마이그레이션 필요
- [ ] 캐시 무효화 필요

## 스크린샷/영상
(UI 변경 시 필수)

## 체크리스트
- [ ] 로컬에서 테스트 완료
- [ ] 컨벤션 준수
- [ ] 불필요한 코드 제거
- [ ] 주석 정리
- [ ] Self Review 완료

## 관련 이슈
Closes #123
Relates to #456
```

### PR 제목 컨벤션

**태그:**
- `[FEAT]` 새로운 기능 추가
- `[FIX]` 버그 수정
- `[REFACTOR]` 코드 리팩토링
- `[DOCS]` 문서 수정
- `[TEST]` 테스트 추가/수정
- `[CHORE]` 빌드, 설정 변경
- `[STYLE]` 코드 포맷팅
- `[PERF]` 성능 개선

**좋은 예시:**
- ✅ `[FEAT] 장바구니에 쿠폰 적용 기능 추가`
- ✅ `[FIX] 결제 완료 후 페이지 이동 오류 수정`
- ✅ `[REFACTOR] 사용자 인증 로직 Hook으로 분리`

**나쁜 예시:**
- ❌ "수정"
- ❌ "버그 fix"
- ❌ "작업 완료"

## 리뷰어 가이드

### 5단계 리뷰 프로세스

#### 1단계: 기본 사항 확인 (5분)

**자동화 체크:**
- [ ] CI/CD 통과
- [ ] 테스트 커버리지 유지/향상
- [ ] Lint 통과
- [ ] 타입 체크 통과

**PR 정보 체크:**
- [ ] 제목이 명확한가?
- [ ] 설명이 충분한가?
- [ ] 이슈 번호가 연결되어 있는가?
- [ ] 리뷰어가 적절히 지정되었는가?

#### 2단계: 코드 품질 리뷰 (10분)

**가독성:**
```typescript
// ❌ 나쁜 예
const fn = (x) => x.map(y => y.z ? y.z.a : null).filter(z => z)

// ✅ 좋은 예
const getUserNames = (users) => {
  return users
    .map(user => user.profile?.name)
    .filter(name => name !== null);
}
```

**네이밍:**
```typescript
// ❌ 나쁜 예
const data = fetchData();
const result = process(data);

// ✅ 좋은 예
const userOrders = await fetchUserOrders(userId);
const sortedOrders = sortOrdersByDate(userOrders);
```

**함수 크기:**
```typescript
// ❌ 너무 긴 함수 (100줄+)
function processOrder() {
  // 검증, 재고 확인, 결제 처리, 알림 발송, 로깅 ... 100줄
}

// ✅ 작은 함수들로 분리
function processOrder(order) {
  validateOrder(order);
  checkInventory(order.items);
  const payment = processPayment(order);
  sendNotification(order, payment);
  logOrderEvent(order);
}
```

**주석:**
```typescript
// ❌ 불필요한 주석
// 사용자 이름 가져오기
const userName = user.name;

// ✅ 필요한 주석
// 외부 API의 Rate Limit이 분당 100건이므로 캐싱 필수
const cachedData = await getCachedAPIData(key);
```

#### 3단계: 로직 및 테스트 리뷰 (10분)

**버그 가능성 체크:**
```typescript
// 🔴 Blocker - Null/Undefined 체크 누락
function getUserEmail(user) {
  return user.profile.email; // user나 profile이 없으면?
}

// ✅ 안전한 코드
function getUserEmail(user) {
  return user?.profile?.email ?? 'no-email@example.com';
}
```

**에지 케이스:**
```typescript
// 🟡 Suggestion
function divide(a, b) {
  return a / b;
}
// 리뷰 코멘트: "b가 0인 경우 처리가 필요합니다"

// ✅ 개선된 코드
function divide(a, b) {
  if (b === 0) {
    throw new Error('Division by zero');
  }
  return a / b;
}
```

**테스트 충분성:**
- [ ] Happy Path 테스트
- [ ] 에러 케이스 테스트
- [ ] Boundary Condition 테스트
- [ ] Edge Case 테스트

#### 4단계: 아키텍처 리뷰 (5분)

**적절한 추상화:**
```typescript
// ❌ 추상화 부족
function sendEmail(to: string, subject: string, body: string) {
  await ses.sendEmail({...});
}

// ✅ 적절한 추상화
interface EmailService {
  send(email: Email): Promise<void>;
}

class SESEmailService implements EmailService {
  async send(email: Email) {
    await this.ses.sendEmail({...});
  }
}
```

**의존성 방향:**
```
// ❌ 순환 의존성
// UserService → OrderService → UserService

// ✅ 단방향 의존성
// UserService ← OrderService ← CheckoutService
```

**SOLID 원칙 위반:**
```typescript
// 🔴 Blocker: 단일 책임 원칙 위반
class UserManager {
  validateUser() {}
  saveUser() {}
  sendWelcomeEmail() {} // 이메일 발송은 다른 책임
  generateReport() {}   // 리포트 생성도 다른 책임
}

// ✅ 책임 분리
class UserValidator { validateUser() {} }
class UserRepository { saveUser() {} }
class EmailService { sendWelcomeEmail() {} }
class ReportGenerator { generateReport() {} }
```

#### 5단계: 성능 및 보안 리뷰 (5분)

**성능 문제:**
```typescript
// 🔴 Blocker: N+1 문제
users.forEach(user => {
  const orders = await fetchOrders(user.id); // 매번 DB 쿼리
});

// ✅ 배치 쿼리
const userIds = users.map(u => u.id);
const allOrders = await fetchOrdersByUserIds(userIds);
```

**메모리 누수:**
```typescript
// 🟡 Suggestion: 이벤트 리스너 정리 누락
useEffect(() => {
  window.addEventListener('resize', handleResize);
  // cleanup 함수 누락!
}, []);

// ✅ 정리 함수 추가
useEffect(() => {
  window.addEventListener('resize', handleResize);
  return () => window.removeEventListener('resize', handleResize);
}, []);
```

**보안 이슈:**
```typescript
// 🔴 Blocker: XSS 취약점
element.innerHTML = userInput;

// ✅ 안전한 처리
element.textContent = userInput;
// 또는 DOMPurify 같은 라이브러리 사용
```

## Conventional Comments 형식

[Conventional Comments](https://conventionalcomments.org/)는 리뷰 코멘트에 레이블을 붙여 의도를 명확히 전달하는 표준 형식입니다.

### 기본 형식

```
<label>: <subject>

[discussion]
```

### 주요 레이블

| 레이블 | 의미 | 예시 |
|--------|------|------|
| `praise:` | 칭찬, 긍정적 피드백 | `praise: 이 에러 처리 패턴이 깔끔하고 재사용성이 높네요!` |
| `nitpick:` | 사소한 의견 (비차단) | `nitpick: 여기 trailing comma를 추가하면 diff가 깔끔해집니다.` |
| `suggestion:` | 개선 제안 | `suggestion: useMemo를 사용하면 불필요한 재계산을 줄일 수 있습니다.` |
| `issue:` | 수정이 필요한 문제 | `issue: user가 null일 때 런타임 에러가 발생합니다.` |
| `question:` | 의도 확인 질문 | `question: try-catch 없이 처리한 이유가 궁금합니다.` |
| `thought:` | 아이디어 공유 (비차단) | `thought: 이 패턴을 다른 모듈에도 적용하면 좋겠네요.` |
| `chore:` | 정리 작업 요청 | `chore: 사용하지 않는 import를 제거해주세요.` |

### 데코레이터 (선택사항)

레이블 뒤에 괄호로 데코레이터를 추가하여 추가 맥락을 제공합니다:

```
suggestion (non-blocking): Map 대신 Object를 쓰면 더 간결해질 수 있습니다.

issue (blocking): 이 쿼리에 인덱스가 없어서 프로덕션에서 성능 문제가 발생할 수 있습니다.

nitpick (if-minor): 변수명을 data 대신 userOrders로 바꾸면 가독성이 좋아질 것 같습니다.
```

- `(blocking)`: 반드시 해결 후 머지 (기본값: issue)
- `(non-blocking)`: 선택적 반영
- `(if-minor)`: 간단히 수정 가능하면 반영

### 적용 예시

```
praise: 이 커스텀 Hook 추상화가 정말 좋습니다! 재사용성이 뛰어나네요.

issue (blocking): user.profile에 접근하기 전에 null 체크가 필요합니다.
Optional chaining을 사용해주세요: `user?.profile?.email`

suggestion (non-blocking): 이 로직을 별도 유틸 함수로 분리하면
테스트하기 더 쉬워질 것 같습니다.

question: 이 타임아웃 값(5000ms)은 어떤 기준으로 설정한 건가요?
```

## 리뷰 코멘트 작성 요령

### 좋은 코멘트 예시

**칭찬:**
> ✅ "이 커스텀 Hook의 인터페이스가 직관적이네요! 재사용성이 높아 보입니다."

**제안:**
> ✅ "이 부분은 useMemo를 사용하면 어떨까요? 의존성이 변경되지 않을 때 재계산을 막을 수 있을 것 같습니다."
> ```tsx
> const sortedItems = useMemo(() =>
>   items.sort((a, b) => a.date - b.date),
>   [items]
> );
> ```

**질문:**
> ✅ "try-catch 없이 에러를 처리하는 이유가 있을까요? 의도가 궁금합니다."

**심각한 문제:**
> 🔴 Blocker  
> "user가 null일 수 있는데 체크가 없어서 런타임 에러가 발생할 수 있습니다. Optional Chaining을 추가해주세요: `user?.profile?.email`"

### 나쁜 코멘트 예시
- ❌ "이거 왜 이렇게 했어요?" (비난조, 구체적이지 않음)
- ❌ "이상하네요" (무엇이 이상한지 설명 없음)
- ❌ "제 스타일은 아닌데요" (주관적, 건설적이지 않음)
- ❌ "이거 안 될 것 같은데요" (근거 없는 의견)

## 리뷰 받는 사람(Author) 가이드

### 리뷰 요청 전 Self Review

```markdown
## Self Review 체크리스트
- [ ] 전체 diff 한 번 더 읽기
- [ ] console.log / debugger 제거
- [ ] 불필요한 공백/줄바꿈 제거
- [ ] 임시 주석 제거
- [ ] TODO 주석 정리
- [ ] 테스트 코드 작성
- [ ] 문서 업데이트 (필요 시)
```

### 피드백 대응하기

**좋은 대응:**
- ✅ "좋은 지적 감사합니다! useMemo로 수정했습니다."
- ✅ "이 부분은 XXX 이유로 이렇게 구현했는데, 더 나은 방법이 있을까요?"
- ✅ "제가 놓친 부분이네요. 곧 수정하겠습니다."

**방어적 대응 (지양):**
- ❌ "원래 이렇게 하는 거예요"
- ❌ "이미 테스트했는데요"
- ❌ "나중에 리팩토링할게요"

### 의견 충돌 시

1. **이해 확인**: "제가 의도한 것은 XXX인데, 제안하신 YYY 방식이 더 나은 이유를 설명해주실 수 있을까요?"
2. **대안 논의**: "두 가지 방법 모두 장단점이 있는 것 같습니다. 팀 컨벤션상 어떤 게 더 맞을까요?"
3. **팀 논의**: "이 부분은 팀 전체 논의가 필요할 것 같습니다. 다음 회의 안건으로 올려도 될까요?"

## 코드 리뷰 5단계 체크리스트

### Level 1: 기본 사항 ✅
- [ ] CI/CD 통과
- [ ] 브랜치가 최신 main/develop와 sync
- [ ] 커밋 메시지가 명확
- [ ] PR 템플릿 모두 작성
- [ ] 적절한 라벨 추가
- [ ] 리뷰어 지정

### Level 2: 코드 품질 ⭐
- [ ] 네이밍이 명확하고 일관성 있음
- [ ] 함수가 단일 책임 원칙을 따름
- [ ] 중복 코드 없음 (DRY 원칙)
- [ ] 매직 넘버/문자열 상수화
- [ ] 주석이 "왜"를 설명 (What/How는 코드가 설명)
- [ ] 컨벤션 준수

### Level 3: 로직 및 버그 🐛
- [ ] Null/Undefined 체크
- [ ] 에러 처리 (try-catch, error boundary)
- [ ] 경계 조건 처리 (0, empty, max 등)
- [ ] 비동기 처리 적절함
- [ ] Race Condition 고려
- [ ] 예상 가능한 Edge Case 처리

### Level 4: 테스트 🧪
- [ ] 단위 테스트 추가/수정
- [ ] 테스트 커버리지 유지/향상
- [ ] Happy Path 테스트
- [ ] 에러 케이스 테스트
- [ ] 테스트가 독립적이고 반복 가능
- [ ] Mock/Stub 적절히 사용

### Level 5: 아키텍처 & 성능 🏗️
- [ ] 적절한 추상화 수준
- [ ] 의존성 방향 올바름
- [ ] SOLID 원칙 준수
- [ ] 불필요한 Re-render 없음 (React)
- [ ] N+1 쿼리 없음
- [ ] 메모리 누수 가능성 없음
- [ ] 보안 취약점 없음 (XSS, SQL Injection 등)

## AI 기반 코드 리뷰 도구

AI 기반 코드 리뷰 도구를 활용하면 반복적인 검토 작업을 자동화하고, 리뷰어가 아키텍처와 비즈니스 로직 같은 고수준 리뷰에 집중할 수 있습니다.

### GitHub Copilot Code Review

GitHub에서 공식으로 제공하는 AI 코드 리뷰 기능:
- PR 생성 시 리뷰어로 `Copilot`을 지정하면 자동으로 코드 리뷰 수행
- 버그 가능성, 보안 취약점, 성능 문제 등을 자동 탐지
- 구체적인 수정 제안(suggested change)을 인라인으로 제공
- 코딩 가이드라인(Custom Coding Guidelines)을 설정하여 팀 컨벤션에 맞는 리뷰 가능

```yaml
# .github/copilot-review-guidelines.md 예시
# 프로젝트 맞춤 가이드라인을 정의하면 Copilot이 이를 참고하여 리뷰합니다
- 모든 API 호출에는 에러 처리가 포함되어야 합니다
- React 컴포넌트에서 인라인 스타일을 사용하지 마세요
- 비동기 함수에는 반드시 타임아웃을 설정하세요
```

### 기타 AI 코드 리뷰 도구

| 도구 | 특징 |
|------|------|
| **CodeRabbit** | PR 요약 자동 생성, 보안/성능 분석, 대화형 리뷰 |
| **Sourcery** | Python/JS/TS 코드 품질 분석, 리팩토링 제안 |
| **Qodo (구 CodiumAI)** | 테스트 코드 자동 생성, 에지 케이스 탐지 |
| **Amazon CodeGuru** | AWS 환경 특화, 성능/보안 자동 리뷰 |

### AI 리뷰 도구 활용 가이드라인

**AI 리뷰가 잘 하는 것:**
- 코딩 스타일 및 컨벤션 일관성 검사
- 일반적인 버그 패턴 탐지 (null 참조, 리소스 누수 등)
- 보안 취약점 식별 (XSS, SQL Injection, 하드코딩된 시크릿 등)
- 테스트 커버리지 부족 영역 식별
- PR 요약 및 변경 사항 문서화

**사람이 집중해야 할 것:**
- 비즈니스 로직의 정확성 검증
- 아키텍처 결정의 적절성 판단
- 사용자 경험(UX)에 미치는 영향 평가
- 팀 컨텍스트를 고려한 트레이드오프 판단
- 유지보수성과 확장성 평가

> AI 리뷰는 사람 리뷰를 대체하는 것이 아니라, 보완하는 도구입니다. AI가 기계적인 검토를 담당하고, 사람은 맥락과 판단이 필요한 리뷰에 집중하세요.

## 도구 활용

### GitHub PR Template

`.github/pull_request_template.md` 파일을 생성하여 PR 템플릿 자동 적용

### Danger.js

```javascript
// 자동 체크
import { danger, warn, fail } from 'danger';

// PR이 너무 크면 경고
const bigPRThreshold = 500;
if (danger.github.pr.additions + danger.github.pr.deletions > bigPRThreshold) {
  warn(':exclamation: PR이 큽니다. 여러 개로 나눌 수 있을까요?');
}

// 테스트 파일이 없으면 경고
const hasTests = danger.git.modified_files.some(file => file.includes('test'));
if (!hasTests) {
  warn('테스트 파일이 변경되지 않았습니다.');
}
```

### Reviewdog

```yaml
# .github/workflows/reviewdog.yml
name: reviewdog
on: [pull_request]
jobs:
  eslint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: reviewdog/action-eslint@v1
        with:
          reporter: github-pr-review
          eslint_flags: 'src/**/*.{js,jsx,ts,tsx}'
```

### GitHub Actions를 활용한 PR 자동 체크

```yaml
# .github/workflows/pr-checks.yml
name: PR Checks
on: [pull_request]
jobs:
  pr-size-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Check PR size
        run: |
          ADDITIONS=$(gh pr view ${{ github.event.pull_request.number }} --json additions -q '.additions')
          DELETIONS=$(gh pr view ${{ github.event.pull_request.number }} --json deletions -q '.deletions')
          TOTAL=$((ADDITIONS + DELETIONS))
          if [ "$TOTAL" -gt 400 ]; then
            echo "::warning::PR size is ${TOTAL} lines. Consider splitting into smaller PRs (recommended: under 400 lines)."
          fi
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

## 정리

효과적인 코드 리뷰는:
- **존중**: 사람이 아닌 코드를 리뷰
- **명확성**: Conventional Comments 형식으로 의도를 분명히 전달
- **신속성**: 24시간 이내 응답, 작은 PR로 리뷰 부담 최소화
- **균형**: 문제 지적 + 칭찬
- **학습**: 서로에게서 배우는 기회
- **자동화**: AI 리뷰 도구로 기계적 검토를 자동화하고, 사람은 고수준 리뷰에 집중

이 가이드를 팀 상황에 맞게 조정하여 사용하세요!
