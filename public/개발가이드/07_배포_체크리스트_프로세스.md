## 배포 핵심 원칙

1. **사용자 영향 최소화가 최우선** — 빠른 배포 < 안전한 배포
2. **항상 롤백 가능해야 함** — 배포 후 15분 내 롤백 가능 상태 유지
3. **명확한 책임 분담** — 작업자 ≠ 배포담당자 ≠ 모니터링담당자
4. **관측 가능성(Observability) 우선** — 배포 전 계측(instrumentation) 확인, 배포 후 즉시 추적 가능해야 함
5. **Feature Flag로 배포와 출시 분리** — 코드 배포 ≠ 기능 활성화, 점진적 롤아웃으로 리스크 관리
6. **자동화된 검증과 롤백** — 수동 판단 의존도를 줄이고, 자동 검증 및 자동 롤백 파이프라인 구축

## 배포 역할 정의 (R&R)

### 1. 작업자 (Developer)
- 코드 작성 및 테스트
- PR 작성 및 리뷰 대응
- 배포 문서 작성
- 롤백 시 즉시 대응

### 2. 배포담당자 (Deployer)
- 배포 체크리스트 검증
- 배포 실행
- 배포 과정 모니터링
- 이슈 발생 시 즉시 조치

### 3. 모니터링담당자 (Observer)
- 배포 전후 지표 확인
- 에러율/성능 모니터링
- 이상 징후 즉시 알림
- 사인오프 판단

### 4. 사인오프담당자 (Sign-off)
- 최종 배포 승인
- 비즈니스 임팩트 평가
- 배포 완료 선언

## 배포 유형별 프로세스

### 일반 배포 (Regular Deployment)
- **정의**: 일반적인 기능 추가, 버그 수정
- **승인**: 작업자 → 코드 리뷰(2명) → Tech Lead 승인 → 배포
- **배포 시간**: 평일 오전 10시 ~ 오후 5시, 월요일/금요일 지양

### 긴급 배포 (Hotfix)
- **정의**: 프로덕션 장애 수정
- **승인**: 작업자 → Tech Lead 승인 → 즉시 배포 (코드 리뷰는 사후 진행)
- **배포 시간**: 즉시 (24/7)

### 대규모 배포 (Major Release)
- **정의**: 아키텍처 변경, DB 마이그레이션 포함
- **승인**: 작업자 → 코드 리뷰(3명) → Tech Lead → CTO 승인 → 사전 공지 → 배포
- **배포 시간**: 화요일 ~ 목요일, 오후 2시 ~ 4시 (트래픽 낮은 시간), 전 팀 대기 상태

## Observability 체크리스트

배포 전후로 관측 가능성(Observability)을 확보하여 문제를 빠르게 탐지하고 근본 원인을 추적합니다.

### OpenTelemetry 설정 확인

```markdown
## 트레이싱(Tracing)
- [ ] OpenTelemetry SDK 초기화 확인
- [ ] 서비스 이름(service.name) 및 버전(service.version) 리소스 속성 설정
- [ ] 배포 환경(deployment.environment) 속성 설정
- [ ] HTTP/gRPC 자동 계측(auto-instrumentation) 활성화
- [ ] 커스텀 스팬(Custom Span) 주요 비즈니스 로직에 추가
- [ ] 트레이스 샘플링 비율 적절히 설정 (프로덕션: tail-based sampling 권장)
- [ ] W3C Trace Context 전파(propagation) 설정 확인

## 메트릭(Metrics)
- [ ] RED 메트릭 수집 확인 (Rate, Errors, Duration)
- [ ] 비즈니스 메트릭 커스텀 카운터/히스토그램 등록
- [ ] 배포 이벤트 마커(Deployment Event Marker) 설정
- [ ] 메트릭 익스포터(Exporter) 연결 확인 (Prometheus/OTLP)

## 로그(Logs)
- [ ] 구조화된 로그 포맷(JSON) 사용
- [ ] trace_id, span_id 자동 주입 설정
- [ ] 로그 레벨별 적절한 사용 (ERROR/WARN/INFO/DEBUG)
- [ ] 민감 정보 마스킹 처리 확인
- [ ] 로그 집계 파이프라인 연결 확인
```

### 구조화된 로그(Structured Logging) 표준

```typescript
// 구조화된 로그 출력 예시
import { Logger } from './logger';

const logger = new Logger({
  service: 'checkout-service',
  version: process.env.APP_VERSION,
  environment: process.env.NODE_ENV,
});

// 올바른 구조화된 로그
logger.info('결제 처리 완료', {
  orderId: order.id,
  amount: order.totalAmount,
  paymentMethod: order.paymentMethod,
  duration_ms: endTime - startTime,
  trace_id: span.spanContext().traceId,
});

// 배포 이벤트 로그
logger.info('배포 시작', {
  event: 'deployment.started',
  version: process.env.APP_VERSION,
  previousVersion: process.env.PREV_VERSION,
  deployer: process.env.DEPLOYER,
  featureFlags: getActiveFlags(),
});
```

### OpenTelemetry 초기화 예시

```typescript
import { NodeSDK } from '@opentelemetry/sdk-node';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';
import { OTLPMetricExporter } from '@opentelemetry/exporter-metrics-otlp-http';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';
import { Resource } from '@opentelemetry/resources';
import {
  ATTR_SERVICE_NAME,
  ATTR_SERVICE_VERSION,
  ATTR_DEPLOYMENT_ENVIRONMENT_NAME,
} from '@opentelemetry/semantic-conventions';

const sdk = new NodeSDK({
  resource: new Resource({
    [ATTR_SERVICE_NAME]: 'my-frontend-service',
    [ATTR_SERVICE_VERSION]: process.env.APP_VERSION ?? 'unknown',
    [ATTR_DEPLOYMENT_ENVIRONMENT_NAME]: process.env.NODE_ENV ?? 'development',
  }),
  traceExporter: new OTLPTraceExporter({
    url: process.env.OTEL_EXPORTER_OTLP_ENDPOINT,
  }),
  metricReader: new OTLPMetricExporter({
    url: process.env.OTEL_EXPORTER_OTLP_ENDPOINT,
  }),
  instrumentations: [getNodeAutoInstrumentations()],
});

sdk.start();
```

## Feature Flag 배포 통합

배포와 기능 출시를 분리하여 리스크를 최소화합니다. 코드는 먼저 배포하고, Feature Flag를 통해 점진적으로 기능을 활성화합니다.

### Feature Flag 배포 워크플로우

```
1. 코드 배포 (Feature Flag OFF 상태)
      ↓
2. 배포 안정성 확인 (5~10분)
      ↓
3. Feature Flag ON (내부 사용자 대상)
      ↓
```

### Feature Flag 통합 코드 패턴

```typescript
// Feature Flag 평가와 함께 관측 가능성 연동
import { featureFlagClient } from './feature-flags';
import { trace, metrics } from '@opentelemetry/api';

const meter = metrics.getMeter('feature-flags');
const flagEvaluationCounter = meter.createCounter('feature_flag.evaluation', {
  description: 'Feature flag 평가 횟수',
});

function evaluateFlag(flagKey: string, userId: string): boolean {
  const span = trace.getActiveSpan();
  const value = featureFlagClient.evaluate(flagKey, userId);

  // 트레이스에 Flag 정보 추가
  span?.setAttributes({
    [`feature_flag.${flagKey}`]: value,
    'feature_flag.provider': 'internal',
  });

  // 메트릭에 Flag 평가 기록
  flagEvaluationCounter.add(1, {
    flag_key: flagKey,
    flag_value: String(value),
  });

  return value;
}

// 사용 예시
function CheckoutPage() {
  const useNewFlow = evaluateFlag('new-checkout-flow', user.id);

  if (useNewFlow) {
    return <NewCheckoutFlow />;
  }
  return <LegacyCheckoutFlow />;
}
```

## 롤백 자동화 패턴

수동 롤백 판단에 의존하면 대응 시간이 길어집니다. 자동 롤백 파이프라인을 구축하여 장애 감지에서 복구까지의 시간을 최소화합니다.

### 자동 롤백 아키텍처

```
배포 완료
  ↓
자동 헬스 체크 (30초 간격)
  ↓
이상 감지? ──(아니오)──→ 모니터링 계속 (30분)
  │                              ↓
 (예)                      배포 성공 확정
  ↓
자동 롤백 트리거
  ↓
이전 버전 배포
  ↓
알림 발송 (담당자 + 팀 채널)
  ↓
수동 확인 및 원인 분석
```

### 자동 롤백 조건 정의

```yaml
# rollback-policy.yaml
rollback:
  enabled: true
  evaluation_window: 300  # 5분간 평가
  conditions:
    # 하나라도 충족 시 자동 롤백
    - metric: error_rate
      threshold: 2.0        # 에러율 2% 초과
      comparison: greater_than
      duration: 60           # 60초 이상 지속

    - metric: p99_latency_ms
      threshold: 5000        # P99 응답 시간 5초 초과
      comparison: greater_than
      duration: 120          # 120초 이상 지속

    - metric: health_check_failures
      threshold: 3           # 헬스 체크 3회 연속 실패
      comparison: greater_than_or_equal

    - metric: success_rate
      threshold: 90.0        # 핵심 기능 성공률 90% 미만
      comparison: less_than
      duration: 60

  actions:
    - type: rollback
      target: previous_stable_version
    - type: notify
      channels: ['deployment-alerts', 'on-call']
    - type: create_incident
      severity: high
```

### Smoke Test 자동화 스크립트

```typescript
// post-deploy-validation.ts
interface ValidationResult {
  name: string;
  status: 'pass' | 'fail' | 'warn';
  duration_ms: number;
  details?: string;
}

async function runPostDeployValidation(baseUrl: string): Promise<ValidationResult[]> {
  const results: ValidationResult[] = [];

  // 1. 헬스 체크
  results.push(await validateHealthCheck(baseUrl));

  // 2. 핵심 페이지 로딩 확인
  const criticalPages = ['/', '/products', '/checkout', '/account'];
  for (const page of criticalPages) {
    results.push(await validatePageLoad(baseUrl, page));
  }

  // 3. API 엔드포인트 확인
  results.push(await validateApiEndpoints(baseUrl));

  // 4. 정적 자원(Asset) 무결성 확인
  results.push(await validateStaticAssets(baseUrl));

  // 5. Core Web Vitals 확인
  results.push(await validateCoreWebVitals(baseUrl));

  return results;
}

async function validateHealthCheck(baseUrl: string): Promise<ValidationResult> {
  const start = Date.now();
  try {
    const response = await fetch(`${baseUrl}/health`);
    const data = await response.json();
    return {
      name: 'Health Check',
      status: data.status === 'healthy' ? 'pass' : 'fail',
      duration_ms: Date.now() - start,
      details: JSON.stringify(data),
    };
  } catch (error) {
    return {
      name: 'Health Check',
      status: 'fail',
      duration_ms: Date.now() - start,
      details: String(error),
    };
  }
}

async function validatePageLoad(baseUrl: string, path: string): Promise<ValidationResult> {
  const start = Date.now();
  try {
    const response = await fetch(`${baseUrl}${path}`);
    const duration = Date.now() - start;
    return {
      name: `Page Load: ${path}`,
      status: response.ok && duration < 3000 ? 'pass' : (duration < 5000 ? 'warn' : 'fail'),
      duration_ms: duration,
      details: `HTTP ${response.status}`,
    };
  } catch (error) {
    return {
      name: `Page Load: ${path}`,
      status: 'fail',
      duration_ms: Date.now() - start,
      details: String(error),
    };
  }
}
```

### 메트릭 비교 검증

```typescript
// compare-deploy-metrics.ts
interface MetricComparison {
  metric: string;
  before: number;
  after: number;
  change_percent: number;
  status: 'pass' | 'fail' | 'warn';
}

async function compareDeployMetrics(
  version: string,
  windowMinutes: number,
): Promise<MetricComparison[]> {
  const comparisons: MetricComparison[] = [];

  const metrics = [
    { name: 'error_rate', maxIncrease: 50 },        // 에러율 50% 이상 증가 시 실패
    { name: 'p95_latency', maxIncrease: 30 },        // P95 지연 30% 이상 증가 시 실패
    { name: 'throughput', maxDecrease: 20 },          // 처리량 20% 이상 감소 시 실패
    { name: 'apdex_score', maxDecrease: 10 },         // Apdex 10% 이상 감소 시 실패
  ];

  for (const metric of metrics) {
    const before = await getMetricValue(metric.name, 'before', windowMinutes);
    const after = await getMetricValue(metric.name, 'after', windowMinutes);
    const changePct = ((after - before) / before) * 100;

    const threshold = metric.maxIncrease ?? -(metric.maxDecrease ?? 0);
    comparisons.push({
      metric: metric.name,
      before,
      after,
      change_percent: changePct,
      status: Math.abs(changePct) > Math.abs(threshold) ? 'fail' : 'pass',
    });
  }

  return comparisons;
}
```

## 배포 전략

### Blue-Green 배포

```
Blue (현재 버전) ← 100% 트래픽
Green (신규 버전) ← 준비 중
        ↓ (배포)
Blue (현재 버전) ← 0% 트래픽
Green (신규 버전) ← 100% 트래픽
```

- **장점**: 즉시 롤백 가능, 배포 중 다운타임 없음
- **단점**: 2배 인프라 비용, 데이터베이스 호환성 유지 필요
- **적용**: 대규모 트래픽 서비스, 다운타임 허용 불가

### Canary 배포

- 5% → 50% → 100% 점진적 전환, 각 단계마다 모니터링 및 검증
- **장점**: 리스크 최소화, 문제 조기 발견
- **단점**: 배포 시간 길어짐, 복잡한 트래픽 라우팅
- **적용**: 신규 기능 출시, 대규모 리팩토링

### Feature Flag 배포

```tsx
if (featureFlags.newCheckoutFlow) {
  return <NewCheckout />;
} else {
  return <OldCheckout />;
}
```

- **장점**: 배포와 출시 분리, A/B 테스트 가능, 즉시 기능 비활성화
- **단점**: 코드 복잡도 증가, 플래그 관리 오버헤드
- **적용**: 점진적 기능 출시, A/B 테스트, 긴급 비활성화

## 자주 발생하는 배포 이슈

### 이슈 1: "배포 후 일부 사용자만 에러 발생"
- **원인**: CDN 캐시 불일치
- **해결**: `aws cloudfront create-invalidation --distribution-id DIST_ID --paths "/*"`

### 이슈 2: "배포 후 CSS가 깨짐"
- **원인**: CSS 파일 버전 불일치 (HTML과 CSS 파일 해시 미스매치)
- **해결**: Webpack의 contenthash 사용, HTML과 정적 자산 동시 배포 확인

### 이슈 3: "배포 후 API 호출 실패"
- **원인**: API 버전 호환성 문제
- **해결**: API Versioning, Backward Compatibility 유지, Feature Flag로 점진적 전환

### 이슈 4: "롤백해도 문제 지속"
- **원인**: CDN/브라우저 캐시
- **해결**:
  ```bash
  # 1. CloudFront 캐시 완전 무효화
  aws cloudfront create-invalidation --distribution-id DIST_ID --paths "/*"
  # 2. 브라우저 캐시 우회 (Cache-Control 헤더 수정)
  Cache-Control: no-cache, no-store, must-revalidate
  ```

## 정리

배포는 단순한 코드 업로드가 아니라 **팀의 협업 프로세스**입니다:

- **사전 준비**: 철저한 테스트와 문서화
- **Observability**: OpenTelemetry 계측과 구조화된 로그로 완전한 관측 가능성 확보
- **Feature Flag**: 배포와 출시를 분리하여 리스크 관리, 킬 스위치로 즉시 비활성화
- **점진적 배포**: Canary로 리스크 최소화
- **집중 모니터링**: 실시간 지표 추적 및 배포 전후 자동 비교
- **자동화된 검증**: 배포 후 Smoke Test, 합성 모니터링, 메트릭 비교 자동 실행
- **자동 롤백**: 임계값 기반 자동 롤백으로 장애 복구 시간 최소화
- **빠른 롤백**: 15분 내 복구 가능 상태 유지

이 체크리스트를 팀의 상황에 맞게 커스터마이징하여 사용하세요!
