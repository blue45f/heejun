## 1. 개요

본 문서는 프론트엔드 개발 팀에서 진행된 RFC(Request for Comments) 문서들과 표준화 관련 문서들을 종합 정리한 자료입니다. 각 RFC는 팀 전체에 적용될 표준을 제안하고 논의하는 과정을 담고 있습니다.

### RFC 진행 상태 범례

|------|------|
| 작성중 | RFC 초안 작성 중 |
| 논의 진행중 | 참여자들과 논의 진행 중 |
| 완료 | RFC 승인 및 표준화 완료 |

## 2. RFC - 조직 웹표준 개발환경

### 기본 정보

| 항목 | 내용 |
|------|------|
| 발의자 | 프론트엔드팀 |
| 발의일자 | YYYY-MM-DD |
| 문서 상태 | 작성중 |
| 챔피언 | 기술리드/프론트엔드팀 |

### 문제 정의

- **팀별 개발 환경 파편화**: 번들러, 상태 관리, 테스팅 도구 등이 팀마다 상이
- **잦은 팀 간 인력 이동**: TF 구성, 애자일 조직 운영, 프로젝트 우선순위 변경으로 인한 빈번한 팀 이동
- **높은 온보딩 비용**: 팀 이동 시 평균 2-4주의 개발 환경 적응 기간 필요
- **협업 비효율성**: 중복 R&D 투자, 사내 라이브러리 호환성 문제, 긴급 지원 시 즉시 투입 어려움
- **외주 개발 시 일정하지 못한 퀄리티**: 외주 개발 진행 시 코드 퀄리티 불균일

### 목표

- **온보딩 기간 75% 단축**: 팀 이동 시 적응 기간을 2-4주 → 2-3일로 단축
- **즉시 생산성 확보**: 첫 주부터 실질적인 코드 기여 가능
- **유연한 조직 운영**: 프로젝트 요구에 따른 유연한 인력 배치 지원
- **R&D 리소스 최적화**: 중복 투자 최소화 및 개발 생산성 향상

### 핵심 제안

#### 표준 기술 스택 마련

1. **CLI 스케폴딩 도구**: `npx create-org-app`으로 즉시 프로젝트 시작
2. **표준 템플릿 제공**: 내부 라이브러리 사전 통합, 기본 구조 및 설정 포함
3. **개발 도구 통합**: ESLint, Prettier, Husky 등 표준 설정
4. **가이드 문서**: 팀 이동자용 빠른 시작 가이드, 개발 패턴 가이드

#### 구현 계획 (6개월)

| Phase | 기간 | 내용 |
|-------|------|------|
| Phase 1 | 1-2개월 | 표준 스택 정립 |
| Phase 2 | 2-3개월 | 스케폴딩 도구 개발 |
| Phase 3 | 3-5개월 | 파일럿 운영 (2-3개 팀) |
| Phase 4 | 5-6개월 | 조직 전체 확산 |

### 주요 장점

- 프로젝트 빠른 시작, 의사결정 시간 단축
- 내부 도구 완벽 호환, 팀 간 지식 공유 활성화
- 개발자 팀 이동 시 경험 재활용 가능
- 외주 개발 시 일정한 퀄리티 제공
- **강력한 베네핏 제공**:
  - 의존성 라이브러리 업데이트에 대한 지원
  - 주기적인 업데이트 및 마이그레이션 가이드 제공
  - 디자인 시스템 등 내부 라이브러리와의 완벽한 호환성 제공

### 주요 리스크 및 대응 방안

| 리스크 | 대응 방안 |
|--------|----------|
| 기술 선택 자유도 제한 | 예외 정책으로 대응 |
| 레거시 마이그레이션 부담 | 단계적 전환, 강제 아닌 권고 |
| 표준 환경 경직성 | 분기별 리뷰로 지속 개선 |

### FAQ

**Q: 기존 프로젝트도 반드시 전환해야 하나요?**
A: 아니요. 이는 권고사항이며, 리팩토링 또는 재구축 시점에 검토하는 것을 권장합니다.

**Q: 표준에 없는 라이브러리를 사용할 수 있나요?**
A: 네, 추가 라이브러리 사용이 가능합니다. 그러나 핵심 스택은 표준 준수를 권장합니다.

## 3. RFC - 웹앱 표준 인터페이스 네이밍

### 기본 정보

| 항목 | 내용 |
|------|------|
| 발의자 | 프론트엔드팀 |
| 발의일자 | YYYY-MM-DD |
| 문서 상태 | 작성중 |
| 챔피언 | 기술리드/프론트엔드팀 |

### 문제 정의

1. **인터페이스의 설계 원칙 부재 및 개발 주체 분산으로 인한 비표준화 심화**
   - 일관된 명명 규칙이나 설계 원칙 없이 필요에 따라 인터페이스 추가
   - 여러 개발 주체에 의해 각기 다른 시점에 추가

2. **딥링크, 딥링크 액션, 자바스크립트 인터페이스 용어 및 사용 기준 부재**
   - 각 개념이 앱과 웹, 네이티브와 웹 사이에서 얽혀 있어 혼란 발생

3. **WebView 라이프사이클 정의 부재**
   - 웹뷰 자체의 생명주기에 연동되는 표준화된 인터페이스 부재
   - 웹 개발자가 앱의 생명주기 이벤트를 직접 파악해야 하는 어려움

4. **미래 확장성 및 유지보수성 저하에 대한 선제적 대응 필요**

### 목표 (Phase 1 - 미래 정의 중심)

1. **웹앱 브릿지 인터페이스의 체계적인 카테고리화 및 네이밍 규칙 수립**
2. **딥링크, 딥링크 액션, 자바스크립트 인터페이스 용어 및 사용 기준 정의**
3. **WebView 라이프사이클에 따른 인터페이스 정의 및 관리 방안 마련**
4. **개발 생산성 향상 및 잠재적 장애 요인 제거를 통한 서비스 안정성 강화**

### 제안 내용

#### 인터페이스 카테고리 및 네이밍 규칙

| 카테고리 | 설명 | 네이밍 패턴 |
|----------|------|-------------|
| 시스템/디바이스 정보 및 제어 | 앱 또는 디바이스의 일반적인 정보 조회 및 시스템 기능 제어 | `get`, `set`, `request`, `protect[Feature]` |
| 사용자 인증 및 계정 관리 | 사용자 인증 및 계정 정보 관리 | `[AuthMethod]Complete`, `get[AuthInfo]` |
| 주문 및 커머스 기능 | 주문, 장바구니, OCR 등 커머스 관련 기능 | `update[FeatureInfo]`, `get`, `set` |
| UI/UX 제어 | 웹뷰 내 UI 요소의 표시/숨김, 스타일 변경 | `show[UIElement]`, `close[UIElement]` |
| 로그 및 모니터링 | 웹뷰 내에서 발생하는 로그 전송 | `send` |
| 이벤트 콜백 (앱 → 웹) | 앱의 특정 동작 시 웹뷰로 전달되는 이벤트 | `on[EventName]` |

#### 딥링크/딥링크 액션/자바스크립트 인터페이스 사용 기준

| 개념 | 호출 주체 | 데이터 흐름 방향 | 주요 역할 |
|------|----------|------------------|----------|
| 딥링크 | 웹, 외부 앱 | 웹 → 앱 | 웹에서 앱으로 네이티브 화면 전환 |
| 딥링크 액션 | 웹 (딥링크 포함), 앱 내 처리기 | 웹 → 앱 | 딥링크에 액션 정보를 포함해 앱 동작 제어 |
| 자바스크립트 인터페이스 | 앱 내부 웹뷰의 JS / 앱 Native | 앱 ↔ 웹 (양방향) | 앱과 웹이 양방향 통신 |

#### WebView 라이프사이클 이벤트 정의

| 이벤트 명칭 | 설명 | 호출 주체 |
|-------------|------|----------|
| `onWebViewInit` | 웹뷰 인스턴스가 생성되고 초기화가 완료된 시점 | 앱 |
| `onWebViewLoaded` | HTML 문서 및 모든 JS 리소스 로딩 완료 시점 | 웹뷰 |
| `onWebViewAppear` | 웹뷰가 화면에 나타나 사용자에게 보여지는 시점 | 앱 |
| `onWebViewDisappear` | 웹뷰가 화면에서 사라지거나 백그라운드로 전환되는 시점 | 앱 |
| `onWebViewDestroy` | 웹뷰 인스턴스가 소멸되고 메모리에서 해제되는 시점 | 앱 |

## 4. RFC - 테스트 작성 표준화

### 기본 정보

| 항목 | 내용 |
|------|------|
| 발의자 | 프론트엔드팀 |
| 발의일자 | YYYY-MM-DD |
| 문서 상태 | 작성중 → 논의 진행중 → 완료 |
| 챔피언 | 기술리드/프론트엔드팀 |

### 문제 정의

1. **테스트 전략의 일관성 부족**
   - A 프로젝트: 단위 테스트 중심의 Testing Pyramid 방식
   - B 프로젝트: 통합 테스트 중심의 Testing Trophy 방식
   - C 프로젝트: E2E 테스트에 과도한 의존

2. **테스트 도구 및 환경의 분산**
   - 테스트 러너: Jest, Vitest, Mocha 등 혼재
   - 테스트 라이브러리: Enzyme, React Testing Library 등 혼재
   - E2E 도구: Cypress, Playwright 등 혼재

3. **테스트 품질의 편차**
   - 테스트 작성 경험과 지식 수준에 따라 품질과 커버리지 차이 발생

4. **테스트 현황**
   - 각 팀마다, 각 프로젝트마다 테스트가 제각각으로 구축
   - 테스트 자체가 없거나, 낮은 품질의 테스트가 대부분인 경우 존재

### 최종 목표

**관련 팀이 변화에 효과적으로 대응하고 협력하여 테스트 문화 정착을 통한 프로덕트 신뢰도 향상**

### 세부 목표

1. **테스트 전략 및 도구 표준화**
   - 표준 테스트 전략 정의: Testing Trophy 채택
   - 공통 테스트 스택 선정: Vitest, React Testing Library, Playwright
   - 통합 테스트 환경 제공

2. **테스트 품질 상향 평준화**
   - 테스트 코드 리뷰 강화
   - 테스트 가이드 및 교육 제공
   - 정적 분석 도구 도입: `eslint-plugin-testing-library`

3. **테스트 품질 향상**
   - 최소 가이드라인인 **테스트 커버리지 20%** 달성
   - CI/CD 파이프라인 연동

4. **테스트 작성의 필수화**
   - 조기 결함 발견
   - 요구사항 명확화
   - 품질 예측 가능성 향상

### 제안 내용

#### 테스트 전략 표준화 - Testing Trophy 채택

| 테스트 유형 | 비율 | 설명 |
|-------------|------|------|
| 통합 테스트 | 70% | 컴포넌트 간 상호작용 검증 |
| 단위 테스트 | 20% | 순수 함수 및 복잡한 로직 |
| E2E 테스트 | 10% | 핵심 사용자 플로우 |
| 정적 분석 | - | 모든 테스트의 기반 |
| 접근성 테스트 | Optional | 웹뷰 지면의 경우 |
| 성능 테스트/모니터링 | Optional | 빠르고 쾌적한 UX 제공 목표 |

#### 표준 테스트 도구 스택

```json
{
  "devDependencies": {
    "vitest": "^1.0.0",
    "@vitejs/plugin-react": "^4.0.0",
    "@testing-library/react": "^14.0.0",
    "@testing-library/jest-dom": "^6.0.0",
    "@testing-library/user-event": "^14.0.0",
    "msw": "^2.0.0",
    "playwright": "^1.40.0",
    "@axe-core/playwright": "^4.8.0"
  }
}
```

#### 테스트 작성 원칙

1. **사용자 행동 기반 테스트**: 구현 세부사항이 아닌 사용자 관점에서 테스트
2. **AAA 패턴**: Arrange-Act-Assert 구조 준수
3. **GWT 설명**: Given-When-Then 방식으로 테스트 설명 작성

### 영향 범위

#### 사람 및 팀

- **프론트엔드 개발자 (전체)**: 테스트 전략, 표준 도구, 가이드라인 학습 및 적용
- **프로젝트 관리자 (PM) 및 기획자**: 요구사항 정의 시 테스트 가능성 고려
- **신규 입사자**: 표준화된 테스트 환경으로 빠른 온보딩
- **QA**: 개발자가 작성한 테스트 코드를 통해 Test Case QA 시간 최소화

#### 프로세스

- **개발 워크플로우**: 기능 개발 시 테스트 코드 작성 필수 단계 포함
- **코드 리뷰 (PR)**: 모든 Pull Request에 테스트 코드 포함 필수

### 성공 지표

#### 정량적 지표

- 신규 프로젝트 테스트 커버리지 20% 달성률: 목표 95%
- 프로덕션 크리티컬 버그 발생률: 이전 대비 15% 감소
- PR별 평균 리뷰 시간: 안정적 유지

#### 정성적 지표

- 개발자 만족도 설문: "테스트 코드 작성으로 코드에 대한 자신감이 향상되었는가?" 긍정적 답변 70% 이상

## 5. RFC - UX 라이팅 표준 가이드라인

### 기본 정보

| 항목 | 내용 |
|------|------|
| 발의자 | 프론트엔드팀 |
| 발의일자 | YYYY-MM-DD |
| 문서 상태 | 완료 |
| 챔피언 | 기술리드/프론트엔드팀 |
| 조직 승인 | ✅ 승인 |

### 문제 정의

#### UX 관점

- **조직 전체에서 표준화된 가이드라인 및 원칙 부재**: 서비스 전반의 통일된 Voice & Tone, 용어, 문장 스타일 등에 대한 구체적인 기준 없음
- **체계적인 UX 라이팅 검토 및 관리 프로세스 미비**: 기획/디자인 단계에서 작성된 문구에 대해 UX 라이팅 관점에서의 전문적인 검토나 최종 승인 절차 없음

#### 개발 관점

- **최종 확정되지 않은/검증되지 않은 텍스트의 조기 전달**: 개발 이후 수정이 잦음
- **텍스트 리소스 관리 체계 미흡**: 유사한 문구가 여러 곳에 중복으로 하드코딩

#### 발생 현상 및 영향

- 불필요한 개발 리소스 낭비
- 유지보수 어려움 및 비용 증가
- 배포 안정성 저해 가능성

### 문제 사례

| 문제 유형 | 사례 |
|-----------|------|
| 용어 차이 | 등록 vs 생성 |
| 문체 혼용 | ~~~~다 vs ~~~~요 |
| Placeholder 정책 불일치 | 일관성 없는 placeholder |
| 문법 오류 | 맞춤법 오류 |
| 마침표 사용 여부 | 일관성 없음 |
| 고유명사 표기 | 서비스 고유명사 표기 불일치 등 |
| 띄어쓰기 | 해 주세요/해주세요, 첫 주문/첫주문 등 |

### 목표

UX라이팅 표준 가이드라인을 통해 일관된 용어, 문장 구조, 메시지 패턴을 정립하고 이를 개발 프로세스에 명확히 제공함으로써:
- 개발 과정에서의 텍스트 관련 의사결정 시간 단축
- 재작업 최소화
- 개발 생산성 향상

### 기대 효과

1. 프론트엔드 개발자가 UI에 들어갈 문구를 직접 고민하는 대신, 가이드라인에 따라 **정해진 용어나 메시지 구조를 사용**
2. 명확한 가이드라인을 통해 기획자, 디자이너, 개발자 간의 텍스트 관련 **커뮤니케이션 비용 감소**
3. 일관된 가이드라인에 따라 텍스트를 적용하여 **재작업 빈도 감소**
4. 특정 영역에 대하여 공통화된 텍스트셋을 사용하게 하여 **서비스 내의 통일감 구축**

### 영향 범위

- **사용자향**: 사용자 대상 앱/웹 서비스 전체
- **파트너향**: 파트너/비즈니스 고객 대상 서비스 전체
- **Optional: 내부 어드민**

### 제안 내용

#### Phase 1: 공통 문구 규칙 정의 및 표준화

- 공통적으로 사용되는 용어, 문구 등에 대한 규칙 통일
- UX 라이팅 가이드라인 제작
  - 문구 스타일 가이드라인
  - 용어 표준화
  - 서비스 고유명사 정의

#### Phase 2: UX라이팅 거버넌스 구축

- UX라이팅 관련 추가/수정 프로세스 구축
- PM팀과의 표준 공유
- 텍스트 수정 관련 AI Agent 요청 (반복 작업 감소)

## 6. UX 라이팅 표준 가이드라인 v1.0.0 요약

### Quick Check List

#### 공통 확인 항목

- **띄어쓰기**: 맞춤법 허용 시 **붙여쓰기** 우선
- **마침표**: Title/Label에는 없음, Description에는 있음
- **고유명사**: 서비스 공식 명칭 확인
- **날짜**: 한 자리 수 앞 '0' 제거 (8월 7일)
- **시간**: 12시간제 + 오전/오후 표기
- **금액**: 천 단위 쉼표 사용 (1,000원)

#### 대상별 추가 확인사항

| 대상 | 확인사항 |
|------|----------|
| 유저향 | 친근하고 편안한 어조, 긍정적 표현, 혜택 강조 |
| 파트너향 | 정중하고 전문적인 어조, 적절한 호칭 사용, 비즈니스 용어 |
| 어드민향 | 간결성, 기능 중심, 기술용어 허용 |

### UX 라이팅의 핵심 원칙

1. **🎯 명확성 (Clear)**: 사용자에게 혼란을 주지 않고 메시지를 쉽고 빠르게 이해
2. **⚡ 간결성 (Concise)**: 핵심 내용을 중심으로 짧고 효율적인 문장
3. **💡 유용성 (Useful)**: 사용자가 다음에 어떤 행동을 해야 할지 명확히 안내
4. **😊 친근함 (Friendly)**: 사용자에게 편안하고 친근하게 다가가는 어조
5. **🛡️ 신뢰성 (Trustworthy)**: 정확하고 일관된 정보 제공

### 서비스 고유명사 (최우선 준수 사항)

서비스별로 정의된 공식 명칭을 사용합니다. 고유명사 표기 시 다음 원칙을 따릅니다:

- 공식 명칭과 다른 약칭, 비공식 표현을 사용하지 않습니다.
- 영문/한글 혼용 표기 시 공식 표기를 따릅니다.
- 서비스 내 기능명은 공식 기능명을 사용합니다.

| 해 주세요 | 해주세요 |
| 알려 드려요 | 알려드려요 |
| 첫 주문 | 첫주문 |

#### 무조건 띄어쓰기

|---------------|---------------|

### 문장부호 가이드

#### 마침표 (.)

- **Description에는 마침표를 찍음**: '-니다', '해요'로 끝나는 문장
- **Title, Label에는 마침표를 찍지 않음**

#### 기타 문장부호

| 문장부호 | 사용 규칙 |
|----------|----------|
| 가운뎃점 (·) | 비슷한 개념을 이어서 쓸 때 (장보기·쇼핑) |
| 빗금 (/) | 전체 대비 현재 숫자 표시 (3/10), 반대 개념 (남/여) |
| 쌍점 (:) | 앞말과 붙이고 뒷말과 띄어쓰기 (전송자: 서비스명) |
| 물결표 (~) | 기간/범위 표기 시 양옆 붙여쓰기 (3,000~4,000원) |

### 금액 및 포인트 표기

#### 숫자형 표기 (권장)

- 천 단위마다 쉼표(,) 사용: 1,000원, 10,000원
- 알파벳 O로 표기 금지: ❌ 1,OOO원 → ✅ 1,000원

#### 문장형 표기 (광고/마케팅용)

- 수사와 의존명사는 붙여 씀: 1만원, 1천원, 1백원
- 최소 단위에 숫자 1 사용: ✅ 1만원 (❌ 만원)

### 날짜 및 시간 표기

#### 날짜 표기

- 형식: 'YYYY년 M월 D일' 또는 'YYYY. M. D'
- 한 자리 수일 때 '0' 생략: ✅ 2023년 8월 7일 (❌ 2023년 08월 07일)

#### 시간 표기

- 12시간제 + 오전/오후: ✅ 오전 8:00, 오후 2:30
- 24시간제는 표시 시간에서 지양
- 한 자리 시간 0 생략: ✅ 오전 8:00 (❌ 오전 08:00)

### Button Label 가이드

#### 규칙 체크리스트

- 최대 한줄, 권장 글자 수 12자 이내 (공백 포함)
- 구체적인 동작명 사용
- 1가지 동작만 포함
- 명사형 또는 '-기' 종결
- 특수문자/이모지 제거
- 주문/결제는 '-하기' 필수

#### 대상별 예시

| 대상 | 예시 |
|------|------|
| 유저향 | "주문하기", "장바구니 담기", "주문하기" |
| 파트너향 | "주문 접수", "매출 확인", "상품 관리" |
| 어드민향 | "조회", "등록", "수정", "삭제", "동기화" |
