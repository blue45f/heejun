## 1. 모노레포 구조 설계 (Standard Layout)

모든 코드는 `apps`와 `packages`로 분리하여 관리합니다.

### 1.1 디렉토리 구조

```text
root/
├── apps/                    # 배포 가능한 독립 애플리케이션
│   ├── admin/               # 관리자 대시보드 (React 19)
│   ├── web/                 # 사용자 웹 사이트 (Next.js 15)
│   └── docs/                # 문서 사이트 (Astro / Nextra)
├── packages/                # 재사용 가능한 라이브러리 (Shared)
│   ├── ui/                  # 공통 UI 컴포넌트 (Tailwind v4)
│   ├── config-eslint/       # ESLint / Biome 공통 설정
│   ├── config-typescript/   # TypeScript 공통 설정 (tsconfig)
│   ├── api/                 # OpenAPI 기반 API 클라이언트 및 타입
│   ├── utils/               # 공통 유틸리티 함수
│   └── tokens/              # 디자인 토큰 (색상, 간격, 타이포)
├── tooling/                 # 빌드/개발 도구 설정
│   ├── scripts/             # 공통 스크립트 (코드 생성, 마이그레이션 등)
│   └── github/              # GitHub Actions 워크플로우 템플릿
├── .changeset/              # Changesets 설정
├── pnpm-workspace.yaml      # 워크스페이스 정의 (핵심 설정 파일)
├── .npmrc                   # pnpm 동작 설정
├── package.json             # 루트 패키지 설정
└── pnpm-lock.yaml           # 의존성 잠금 파일
```

### 1.2 `apps` vs `packages` 배치 기준

| 기준 | `apps/` | `packages/` |
| :--- | :--- | :--- |
| **독립 배포 가능 여부** | O (자체 도메인, 서버리스 등) | X (다른 앱에서 import하여 사용) |
| **자체 라우팅 보유** | O (Next.js pages, React Router) | X |
| **환경 변수 직접 소비** | O (.env 파일 직접 사용) | X (주입받아 사용) |
| **npm 퍼블리시 대상** | X (보통 퍼블리시 안 함) | O (선택적으로 퍼블리시) |
| **예시** | web, admin, docs, storybook | ui, utils, api, config, tokens |

> **원칙**: 2개 이상의 앱에서 동일한 코드를 복붙하고 있다면, 즉시 `packages/`로 추출하세요.

## 2. pnpm 워크스페이스 완벽 가이드

pnpm은 하드 링크를 사용하여 중복된 패키지 설치를 방지하고, 엄격한 `node_modules` 구조로 Ghost Dependency를 차단하며, workspace 기능만으로 모노레포를 강력하게 운영할 수 있습니다.

### 2.1 `pnpm-workspace.yaml` 설정

```yaml
# pnpm-workspace.yaml
# 워크스페이스에 포함할 패키지 경로 패턴
packages:
  - "apps/*"       # 모든 애플리케이션
  - "packages/*"   # 모든 공유 패키지
  - "tooling/*"    # 빌드/개발 도구

# pnpm 카탈로그: 워크스페이스 전체에서 동일 버전을 강제함
catalog:
  react: "^19.0.0"
  react-dom: "^19.0.0"
  typescript: "^5.7.0"
  "@tanstack/react-query": "^5.62.0"
  zod: "^3.24.0"
  tailwindcss: "^4.0.0"
  vitest: "^3.0.0"
```

### 2.2 `workspace:` protocol 의존성

내부 패키지 간 의존성은 반드시 `workspace:` 프로토콜을 사용합니다. 이렇게 하면 npm registry가 아닌 로컬 워크스페이스에서 패키지를 해결합니다.

```bash
# 내부 패키지를 의존성으로 연결
pnpm add @my/ui --filter=@my/web --workspace

# 루트에 개발 도구 설치 (-w: workspace root)
pnpm add -Dw @changesets/cli

# 특정 패키지에 외부 의존성 추가
pnpm add zod --filter=@my/api
```

```jsonc
// apps/web/package.json
{
  "dependencies": {
    "@my/ui": "workspace:*",           // 항상 로컬 최신 버전 참조
    "@my/utils": "workspace:^1.0.0",   // 로컬에서 버전 범위 검증
    "react": "catalog:",               // pnpm 카탈로그에서 버전 참조
    "react-dom": "catalog:"
  },
  "devDependencies": {
    "@my/config-typescript": "workspace:*"
  }
}
```

> **`workspace:*`**: 퍼블리시 시 실제 버전 번호로 자동 치환됩니다. 내부 패키지는 항상 `workspace:*`를 사용하세요. 직접 버전을 명시하면 npm registry에서 검색을 시도하여 실패합니다.

### 2.3 `pnpm catalog` (버전 중앙 관리)

`pnpm-workspace.yaml`의 `catalog`에 정의된 버전을 모든 패키지에서 공유합니다. 하나의 파일에서 버전을 관리하므로 패키지 간 버전 불일치를 원천 차단합니다. **pnpm 10에서 catalog는 stable 기능으로 격상**되어 명명된 카탈로그(named catalogs)도 지원합니다.

```yaml
# pnpm-workspace.yaml (pnpm 10)
# 기본 catalog
catalog:
  react: "^19.0.0"
  react-dom: "^19.0.0"
  typescript: "^5.7.0"
  vitest: "^3.0.0"
  zod: "^3.24.0"

# 명명된 catalogs -- 동일 패키지의 다른 버전을 그룹별로 관리
catalogs:
  legacy:
    react: "^18.3.0"
    react-dom: "^18.3.0"
  canary:
    react: "19.2.0-canary"
    react-dom: "19.2.0-canary"
```

```jsonc
// 명명된 catalog 사용: "catalog:<name>"
{
  "dependencies": {
    "react": "catalog:",          // 기본 catalog -> ^19.0.0
    "react-dom": "catalog:legacy" // legacy catalog -> ^18.3.0
  }
}
```

> **Bun 호환성**: Bun workspaces도 `catalog:` 프로토콜을 지원합니다(2025년부터). pnpm-workspace.yaml과 유사한 형식으로 root `package.json`의 `workspaces.catalog`에 선언합니다. 다만 Bun catalog는 명명된 catalogs 지원이 제한적이므로 다중 버전 관리가 필요하면 pnpm 10을 권장합니다.

```jsonc
// 각 패키지의 package.json에서 "catalog:" 키워드로 참조
{
  "dependencies": {
    "react": "catalog:",       // "^19.0.0"으로 해석됨
    "react-dom": "catalog:",
    "zod": "catalog:"
  },
  "devDependencies": {
    "typescript": "catalog:",
    "vitest": "catalog:"
  }
}
```

```bash
# 카탈로그에 새 패키지 추가: pnpm-workspace.yaml에 직접 추가 후
# 각 패키지에서 "catalog:"로 참조

# 카탈로그 버전 업데이트: pnpm-workspace.yaml만 수정하면
# 모든 패키지에 자동 반영됨 (pnpm install 실행 필요)
```

> **장점**: React 19로 업그레이드 시 `pnpm-workspace.yaml` 한 곳만 수정하면 모든 패키지에 적용됩니다.

### 2.4 `pnpm --filter` (선택적 실행)

`--filter` 플래그로 특정 패키지만 골라서 명령을 실행합니다. CI 최적화와 개발 생산성의 핵심입니다.

```bash
# 특정 패키지만 빌드
pnpm --filter @my/web build

# 특정 패키지와 그 의존성까지 포함 (... 접미사)
pnpm --filter @my/web... build

# 특정 패키지에 의존하는 모든 패키지 역방향 (... 접두사)
pnpm --filter ...@my/ui build

# 디렉토리 기반 필터
pnpm --filter './apps/*' build
pnpm --filter './packages/*' build

# 여러 필터 조합
pnpm --filter @my/web --filter @my/admin dev

# main 브랜치 대비 변경된 패키지만 실행
pnpm --filter '...[origin/main]' build

# 변경된 패키지와 의존하는 패키지까지 포함
pnpm --filter '...{packages}[origin/main]...' build

# 특정 패키지 제외
pnpm --filter '!@my/docs' build
```

### 2.5 `pnpm --recursive` / `-r` (일괄 실행)

모든 워크스페이스 패키지에 동일한 명령을 실행합니다. 간단한 스크립트에 적합합니다.

```bash
# 모든 패키지에서 build 스크립트 실행
pnpm -r build

# 모든 패키지에서 lint 실행 (병렬)
pnpm -r --parallel lint

# 모든 패키지에서 typecheck 실행 (스트림 출력)
pnpm -r --stream typecheck

# 의존성 순서를 존중하며 빌드 (workspace-concurrency로 병렬도 조절)
pnpm -r --workspace-concurrency=4 build

# 실패해도 나머지 패키지는 계속 실행
pnpm -r --no-bail test

# 특정 스크립트가 있는 패키지만 실행 (없으면 건너뜀)
pnpm -r --if-present clean
```

### 2.6 Ghost Dependency 방지와 `.npmrc` 설정

pnpm의 엄격한 `node_modules` 구조는 선언되지 않은 패키지 사용을 사전에 차단합니다.

```bash
# Ghost Dependency 감지 예시
# apps/web/src/utils.ts 에서 "lodash"를 사용하지만
# apps/web/package.json에 "lodash"가 선언되어 있지 않을 경우:

$ pnpm build --filter=@my/web
# Error: Cannot find module 'lodash'
# -> apps/web/package.json에 lodash를 명시적으로 추가해야 함

$ pnpm add lodash --filter=@my/web
```

```ini
# .npmrc (엄격 모드 강화)
strict-peer-dependencies=true    # peer dependency 불일치 시 에러
auto-install-peers=true          # peer dependency 자동 설치
shamefully-hoist=false           # 호이스팅 비활성화 (엄격 모드 유지)
prefer-workspace-packages=true   # 워크스페이스 패키지를 우선 해결
link-workspace-packages=true     # 워크스페이스 패키지를 심볼릭 링크로 연결
```

### 2.7 `pnpm deploy` (프로덕션 배포용 격리)

`pnpm deploy`는 특정 워크스페이스 패키지와 그 프로덕션 의존성만 격리된 디렉토리로 복사합니다. Docker 이미지를 최소화하거나 서버리스 배포에 매우 유용합니다.

```bash
# @my/web 앱과 프로덕션 의존성만 격리 추출
pnpm --filter @my/web deploy ./deploy/web

# 결과 디렉토리 구조
# ./deploy/web/
# ├── package.json          # 프로덕션 의존성만 포함
# ├── node_modules/         # 프로덕션 의존성만 설치됨
# ├── dist/                 # 빌드 결과물
# └── ...
```

```dockerfile
# Dockerfile (pnpm deploy 활용 - 최소 이미지)
FROM node:20-slim AS base
RUN corepack enable

# 의존성 설치 단계
FROM base AS deps
WORKDIR /app
COPY pnpm-lock.yaml pnpm-workspace.yaml package.json ./
COPY apps/web/package.json ./apps/web/
COPY packages/ui/package.json ./packages/ui/
COPY packages/utils/package.json ./packages/utils/
RUN pnpm install --frozen-lockfile

# 빌드 단계
FROM deps AS build
COPY . .
RUN pnpm --filter @my/web... build

# 배포용 격리 단계
FROM deps AS deploy
COPY --from=build /app .
RUN pnpm --filter @my/web deploy /app/deploy

# 프로덕션 이미지 (최소 크기)
FROM base AS production
WORKDIR /app
COPY --from=deploy /app/deploy .
EXPOSE 3000
CMD ["node", "dist/server.js"]
```

### 2.9 내부 패키지 `package.json` 설정

```jsonc
// packages/ui/package.json
{
  "name": "@my/ui",
  "version": "0.1.0",
  "private": true,                     // npm에 퍼블리시하지 않을 경우
  "sideEffects": false,                // 트리셰이킹 최적화

  "main": "./dist/index.js",          // CJS 진입점
  "module": "./dist/index.mjs",       // ESM 진입점
  "types": "./dist/index.d.ts",       // TypeScript 타입 진입점

  // 모던 exports 필드 (Node.js 16+)
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.js"
    },
    "./button": {
      "types": "./dist/button.d.ts",
      "import": "./dist/button.mjs",
      "require": "./dist/button.js"
    },
    "./styles.css": "./dist/styles.css"
  },

  "scripts": {
    "build": "tsup src/index.ts --format cjs,esm --dts",
    "dev": "tsup src/index.ts --format cjs,esm --dts --watch",
    "typecheck": "tsc --noEmit",
    "lint": "eslint src/",
    "clean": "rm -rf dist"
  },

  "dependencies": {
    "react": "catalog:",               // pnpm 카탈로그에서 버전 참조
    "react-dom": "catalog:"
  },
  "devDependencies": {
    "@my/config-typescript": "workspace:*",
    "tsup": "^8.3.0"
  }
}
```

### 2.10 소스 코드 직접 참조 (빌드 없이 개발)

개발 시 매번 빌드하지 않고 소스를 직접 참조하려면, Next.js `transpilePackages` 활용:

```typescript
// apps/web/next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  // 내부 패키지를 빌드 없이 소스에서 직접 트랜스파일
  transpilePackages: ["@my/ui", "@my/utils"],
};

export default nextConfig;
```

이 경우 패키지의 `package.json`에서 `main`을 소스 파일로 지정:

```jsonc
// packages/ui/package.json (개발 모드용 설정)
{
  "name": "@my/ui",
  "main": "./src/index.ts",           // 소스 직접 참조
  "types": "./src/index.ts",
  "exports": {
    ".": "./src/index.ts",
    "./*": "./src/*/index.ts"
  }
}
```

## 3. 빌드 오케스트레이션 (선택)

pnpm의 `--filter`, `-r`, `--parallel` 조합만으로도 대부분의 모노레포를 운영할 수 있습니다. Turborepo와 같은 빌드 오케스트레이터는 **대규모 모노레포에서 캐싱과 태스크 의존성 관리가 필요할 때** 도입을 검토합니다.

### 3.1 도구 선택 매트릭스 (pnpm vs Turborepo 2.x vs Nx 20 vs Moon 1.30)

| 기준 | pnpm만으로 충분 | Turborepo 2.x 권장 | Nx 20 권장 | Moonrepo 1.30 권장 |
| :--- | :--- | :--- | :--- | :--- |
| **패키지 수** | 10개 이하 | 20개 이상 | 50개 이상 (엔터프라이즈) | polyglot 다수 |
| **빌드 시간** | 전체 빌드 5분 이내 | 전체 빌드 10분 이상 | 30분 이상 | 빌드 재현성 우선 |
| **태스크 의존성** | 단순 (순차 빌드로 충분) | 복잡 (빌드 → 린트 → 테스트 의존 관계) | 복잡 + affected-graph 활용 | 복잡 + 다언어 toolchain |
| **팀 규모** | 1-5명 | 10명 이상, 다수 팀 | 50명 이상, 엔터프라이즈 | 다양한 언어 팀 |
| **CI 캐싱** | GitHub Actions 캐시로 충분 | Vercel Remote Cache 또는 self-hosted | Nx Cloud (distributed task execution) | Moonbase |
| **언어 범위** | JS/TS 중심 | JS/TS 중심 | JS/TS + 부분 polyglot | polyglot (Rust/Go/Node 혼재) |
| **코드 생성** | 불필요 | 불필요 | Generators 필요 시 | 자체 generator |
| **2026년 추세** | 표준 베이스라인 | 가장 보편적 가속기 | 대기업/Angular 진영 | 떠오르는 polyglot 옵션 |

### 3.2 pnpm 내장 스크립트 실행으로 운영하기

Turborepo 없이도 pnpm의 기능만으로 빌드 파이프라인을 구성할 수 있습니다.

```jsonc
// package.json (루트) - Turborepo 없는 구성
{
  "scripts": {
    // 의존성 순서를 존중하며 순차 빌드
    "build": "pnpm -r --stream build",

    // 병렬로 실행해도 되는 태스크
    "lint": "pnpm -r --parallel lint",
    "typecheck": "pnpm -r --parallel typecheck",
    "test": "pnpm -r --parallel test",

    // 변경된 패키지만 빌드 (CI 최적화)
    "build:affected": "pnpm --filter '...[origin/main]' build",

    // 특정 앱과 의존성만 빌드
    "build:web": "pnpm --filter @my/web... build",

    // 개발 서버 (여러 앱 동시 실행)
    "dev": "pnpm --filter @my/web --filter @my/admin dev"
  }
}
```

> **핵심**: `pnpm -r build`는 워크스페이스 의존성 그래프를 자동으로 분석하여 올바른 빌드 순서를 보장합니다. 대부분의 경우 별도의 빌드 오케스트레이터가 불필요합니다.

### 3.3 Turborepo 2.x 도입 시 (선택적 가속)

대규모 모노레포에서 빌드 캐싱과 정교한 태스크 의존성 관리가 필요한 경우 Turborepo 2.x를 도입합니다. 2.x는 태스크 러너를 재작성하여 캐시 적중률과 워치 모드 성능을 크게 개선했습니다.

```bash
# Turborepo 2.x 설치 (선택적)
pnpm add -Dw turbo@^2.4.0
```

```jsonc
// turbo.json (Turborepo 2.x 신규 스키마)
{
  "$schema": "https://turbo.build/schema.json",

  // 모든 태스크에 영향을 주는 전역 환경 변수
  "globalEnv": ["NODE_ENV", "CI"],

  // 전역 의존성: 이 파일이 바뀌면 모든 캐시 무효화
  "globalDependencies": ["tsconfig.base.json"],

  // 2.x: UI 옵션 -- TUI 또는 stream 출력 선택
  "ui": "tui",

  // 2.x: 원격 캐시 시그니처 검증 활성화 (전송 무결성 보장)
  "remoteCache": {
    "signature": true
  },

  // v2: "pipeline" 대신 "tasks" 사용
  "tasks": {
    "build": {
      "dependsOn": ["^build"],        // 상위 의존성 패키지가 먼저 빌드
      "outputs": ["dist/**", ".next/**", "!.next/cache/**"],
      "env": ["NEXT_PUBLIC_*", "VITE_*"],
      "outputLogs": "new-only"        // 2.x: 새 로그만 표시
    },
    "dev": {
      "dependsOn": ["^build"],
      "cache": false,                  // 개발 서버는 캐싱하지 않음
      "persistent": true,              // 장기 실행 프로세스
      "interactive": true              // 2.x: 인터랙티브 dev 모드 지원
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": ["coverage/**"]
    },
    "lint": {
      "dependsOn": ["^build"],
      "outputs": []
    },
    "typecheck": {
      "dependsOn": ["^build"],
      "outputs": []
    },
    "clean": {
      "cache": false
    },

    // 2.x: 워치 모드 전용 태스크 (turbo watch로 실행)
    "//#watch:format": {
      "cache": false,
      "persistent": true
    }
  }
}
```

> **Turborepo 2.x 신규 기능 정리**
> - `turbo watch`: 파일 변화 감지 후 영향받는 태스크만 자동 재실행 (CI보다 로컬 dev에서 유용)
> - `outputLogs`: 캐시 적중 시 출력을 제어 (`new-only`, `errors-only` 등)
> - `remoteCache.signature`: 캐시 무결성을 위한 HMAC 시그니처 (자체 호스팅 환경 권장)
> - `with` 필드: 동시 실행 의존 태스크 명시 (예: dev 시 backend도 함께 실행)

```jsonc
// Turborepo 사용 시 package.json 스크립트 (turbo로 위임)
{
  "scripts": {
    "build": "turbo run build",
    "test": "turbo run test",
    "lint": "turbo run lint",
    "dev:web": "turbo run dev --filter=@my/web",
    "build:affected": "turbo run build --filter='...[origin/main]'"
  },
  "devDependencies": {
    "turbo": "^2.4.0"
  }
}
```

### 3.4 원격 캐싱 (Turborepo 2.x 사용 시)

**원격 캐시 호스팅 선택지 (2026)**

| **Vercel Remote Cache** | 공식 호스팅, 무료 티어 제공, 설정 즉시 사용 가능 | 소규모~중규모 팀, Vercel 배포 사용 시 |
| **Self-hosted Turborepo Remote Cache** | 오픈소스 서버([`turborepo-remote-cache`](https://github.com/ducktors/turborepo-remote-cache)), S3/GCS/R2 백엔드 | 보안/컴플라이언스 요구, 데이터 외부 반출 금지 |

## 5. CI 최적화: pnpm --filter 기반

모노레포 CI의 핵심은 **"바뀐 것만 테스트하는 것"**입니다. pnpm의 `--filter`만으로도 Turborepo 없이 효율적인 CI를 구성할 수 있습니다.

### 5.1 GitHub Actions 워크플로우 (pnpm 기반)

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

# 동일 PR에서 새 커밋 푸시 시 이전 워크플로우 자동 취소
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  # 1단계: 변경된 패키지 탐지
  detect-changes:
    runs-on: ubuntu-latest
    outputs:
      has-changes: ${{ steps.check.outputs.has_changes }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # 전체 이력 필요 (diff 비교)

      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: "pnpm"

      - run: pnpm install --frozen-lockfile

      # pnpm --filter로 변경된 패키지가 있는지 확인
      - id: check
        run: |
          CHANGED=$(pnpm --filter '...[origin/main]' exec echo changed 2>/dev/null | wc -l)
          if [ "$CHANGED" -gt 0 ]; then
            echo "has_changes=true" >> $GITHUB_OUTPUT
          else
            echo "has_changes=false" >> $GITHUB_OUTPUT
          fi

  # 2단계: 린트 + 타입체크 + 테스트 + 빌드 (변경된 패키지만)
  quality:
    needs: detect-changes
    if: needs.detect-changes.outputs.has-changes == 'true'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: "pnpm"

      # pnpm store 캐싱 (CI 속도 향상)
      - uses: actions/cache@v4
        with:
          path: ~/.pnpm-store
          key: pnpm-${{ hashFiles('pnpm-lock.yaml') }}
          restore-keys: pnpm-

      - run: pnpm install --frozen-lockfile

      # 변경된 패키지만 린트 (pnpm --filter 사용)
      - name: Lint (affected)
        run: pnpm --filter '...[origin/main]' lint

      # 변경된 패키지만 타입체크
      - name: Typecheck (affected)
        run: pnpm --filter '...[origin/main]' typecheck

      # 변경된 패키지만 테스트
      - name: Test (affected)
        run: pnpm --filter '...[origin/main]' test

      # 변경된 패키지와 의존하는 패키지 빌드
      - name: Build (affected)
        run: pnpm --filter '...[origin/main]' build

  # 3단계: 전체 빌드 검증 (main 브랜치 머지 시)
  full-build:
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: "pnpm"
      - run: pnpm install --frozen-lockfile
      - run: pnpm -r build && pnpm -r test && pnpm -r lint && pnpm -r typecheck
```

### 5.2 Turborepo를 추가한 CI (선택적 가속)

대규모 모노레포에서 원격 캐싱으로 CI 시간을 더 단축하고 싶은 경우:

```yaml
# .github/workflows/ci.yml (Turborepo 추가 버전)
env:
  TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
  TURBO_TEAM: ${{ vars.TURBO_TEAM }}

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      # ... checkout, pnpm setup, install 동일 ...

      # Turborepo 사용 시: 원격 캐시 + 태스크 의존성 자동 관리
      - name: Build & Test (affected, with cache)
        run: turbo run build test lint typecheck --filter='...[origin/main]'
```

### 5.3 pnpm --filter 패턴 정리

```bash
# 패키지 이름 기반
pnpm --filter @my/web build              # 특정 패키지
pnpm --filter @my/web... build            # 패키지 + 의존성
pnpm --filter ...@my/ui build             # 패키지에 의존하는 모든 패키지

# 변경 감지 기반 (git diff)
pnpm --filter '...[origin/main]' build    # main 대비 변경된 패키지
pnpm --filter '{apps}[origin/main]' build # apps 디렉토리 내 변경 패키지

# 디렉토리 기반
pnpm --filter './apps/*' build            # apps 하위 전체
pnpm --filter './packages/*' typecheck    # packages 하위 전체

# 제외 패턴
pnpm --filter '!@my/docs' build           # 특정 패키지 제외
pnpm --filter '!./apps/docs' build        # 디렉토리 기반 제외

# 조합
pnpm --filter @my/web --filter @my/admin dev  # 여러 패키지 동시
```

### 5.4 의존성 그래프 시각화

```bash
# pnpm으로 의존성 목록 확인
pnpm ls -r --depth=0                     # 모든 패키지의 직접 의존성
pnpm ls -r --json | jq                   # JSON 형식으로 분석
pnpm why <package-name> --filter @my/web  # 특정 패키지가 왜 설치되었는지

# Turborepo 사용 시 그래프 시각화 (선택)
turbo run build --graph=graph.html       # 인터랙티브 그래프
turbo run build --graph=graph.svg        # SVG 파일 생성
```

## 6. 버전 관리 및 릴리즈

### 6.1 Changesets 기반 버전 관리

[Changesets](https://github.com/changesets/changesets)를 사용하여 패키지 버전과 CHANGELOG를 자동 관리합니다.

```bash
# Changesets 초기 설정
pnpm add -Dw @changesets/cli
pnpm changeset init
```

```jsonc
// .changeset/config.json
{
  "$schema": "https://unpkg.com/@changesets/config@3.0.0/schema.json",
  "changelog": "@changesets/cli/changelog",
  "commit": false,
  "fixed": [],                           // 항상 같은 버전으로 묶을 패키지 그룹
  "linked": [                            // 버전이 함께 올라갈 패키지 그룹
    ["@my/ui", "@my/tokens"]
  ],
  "access": "restricted",                // npm 퍼블리시 접근 제한 (private)
  "baseBranch": "main",
  "updateInternalDependencies": "patch",  // 내부 의존성 자동 업데이트
  "ignore": [
    "@my/web",                            // 앱은 버전 관리에서 제외
    "@my/admin"
  ]
}
```

### 6.4 Independent vs Fixed 버전 전략

| 전략 | 설명 | 적합한 경우 |
| :--- | :--- | :--- |
| **Independent** (기본값) | 각 패키지가 독립적으로 버전 관리 | 패키지 간 결합도가 낮을 때 |
| **Fixed** | 그룹 내 패키지가 항상 같은 버전 | UI 컴포넌트 + 디자인 토큰처럼 항상 함께 릴리즈할 때 |
| **Linked** | 하나가 올라가면 나머지도 함께 올라감 | 밀접하게 연관된 패키지 그룹 |

```jsonc
// .changeset/config.json 예시
{
  // fixed: 항상 같은 버전 (v1.2.0 -> 모두 v1.3.0)
  "fixed": [["@my/ui", "@my/tokens"]],

  // linked: 하나가 major면 나머지도 major
  "linked": [["@my/api", "@my/api-types"]]
}
```

## 7. 모노레포 마이그레이션 가이드

기존 단일 저장소를 모노레포로 전환하는 단계별 가이드입니다.

### 7.1 마이그레이션 단계

```text
Phase 1: 기반 구축 (1-2일)
├── pnpm 전환 및 workspace 설정
├── .npmrc 엄격 모드 설정
└── 루트 package.json 정리

Phase 2: 패키지 분리 (3-5일)
├── 공통 설정 추출 (config-eslint, config-typescript)
├── 공통 유틸리티 추출 (utils)
├── 공통 UI 추출 (ui)
└── API 타입 추출 (api)

Phase 3: CI/CD 전환 (1-2일)
├── GitHub Actions 워크플로우 업데이트
├── pnpm --filter 기반 선택적 실행 적용
└── (선택) Turborepo 도입 및 원격 캐싱 설정

Phase 4: 안정화 (1주일)
├── 전체 빌드/테스트 검증
├── 개발 환경 문서화
└── 팀 온보딩
```

### 7.2 Step-by-Step 실행

```bash
# Step 1: pnpm으로 전환
npm install -g pnpm
pnpm import                  # package-lock.json -> pnpm-lock.yaml 변환
rm package-lock.json

# Step 2: 워크스페이스 초기화
mkdir -p apps/web packages/ui packages/utils packages/config-typescript

# Step 3: 기존 코드를 apps/web으로 이동
# (git mv를 사용하면 히스토리 보존)
git mv src apps/web/src
git mv public apps/web/public
git mv next.config.ts apps/web/
git mv tsconfig.json apps/web/

# Step 4: 공통 코드를 packages로 추출
# UI 컴포넌트 분리
git mv apps/web/src/components/ui packages/ui/src

# 유틸리티 함수 분리
git mv apps/web/src/lib/utils.ts packages/utils/src/

# Step 5: 내부 의존성 연결
cd apps/web
pnpm add @my/ui @my/utils --workspace

# Step 6: import 경로 일괄 수정
# "@/components/ui/button" -> "@my/ui/button"
# "@/lib/utils" -> "@my/utils"
```

### 7.3 Import 경로 자동 변환 스크립트

```typescript
// tooling/scripts/migrate-imports.ts
// 기존 상대 경로를 패키지 경로로 일괄 변환하는 스크립트

import { readFileSync, writeFileSync } from "fs";
import { globSync } from "glob";

// 변환 규칙 정의
const IMPORT_MAP: Record<string, string> = {
  "@/components/ui": "@my/ui",
  "@/lib/utils": "@my/utils",
  "@/types/api": "@my/api",
};

const files = globSync("apps/web/src/**/*.{ts,tsx}");

for (const file of files) {
  let content = readFileSync(file, "utf-8");

  for (const [oldPath, newPath] of Object.entries(IMPORT_MAP)) {
    // import 구문의 경로를 치환
    const regex = new RegExp(`from ["']${oldPath}(/[^"']*)?["']`, "g");
    content = content.replace(regex, (_, sub) => {
      return `from "${newPath}${sub || ""}"`;
    });
  }

  writeFileSync(file, content);
}

console.log(`${files.length}개 파일의 import 경로를 변환했습니다.`);
```

## 9. 주의사항 및 흔한 실수

### 9.1 순환 의존성 (Circular Dependencies)

```text
[잘못된 예]
packages/ui  →  depends on  →  packages/utils
packages/utils  →  depends on  →  packages/ui    (순환!)

[올바른 해결]
packages/ui  →  depends on  →  packages/utils
packages/utils  →  독립적 (의존성 없음)
```

```bash
# 순환 의존성 탐지 (pnpm 기본 명령)
pnpm ls --depth=Infinity --json | jq '.[] | .dependencies'

# pnpm으로 의존성 트리 확인
pnpm ls -r --depth=1

# Turborepo 사용 시 그래프로 시각적 확인 (선택)
turbo run build --graph=graph.html
```

> **해결 원칙**: 순환이 발생하면 공통 부분을 새로운 패키지(`packages/shared`)로 추출합니다.

### 9.2 패키지 경계 위반

```typescript
// [잘못된 예] 패키지 내부 파일을 직접 import
import { helperFn } from "@my/ui/src/lib/internal-helper";  // 내부 구현 직접 참조!

// [올바른 예] 공개된 API만 사용
import { Button } from "@my/ui";
import { Button } from "@my/ui/button";  // exports 필드에 명시된 서브패스
```

ESLint로 경계 위반을 자동 차단:

```javascript
// eslint.config.mjs
{
  rules: {
    "no-restricted-imports": ["error", {
      patterns: [
        {
          group: ["@my/*/src/*"],           // src 디렉토리 직접 접근 차단
          message: "패키지의 공개 API만 사용하세요. exports 필드를 확인해 주세요."
        }
      ]
    }]
  }
}
```

### 9.3 CI 타임아웃 문제

```yaml
# 문제: 모노레포가 커지면서 CI가 30분 이상 소요
# 해결 전략 (pnpm 기반):

# 1. pnpm store 캐싱 (가장 기본적이고 효과적)
- uses: actions/cache@v4
  with:
    path: ~/.pnpm-store
    key: pnpm-${{ hashFiles('pnpm-lock.yaml') }}
    restore-keys: pnpm-

# 2. 변경된 패키지만 실행 (pnpm --filter)
- run: pnpm --filter '...[origin/main]' build test

# 3. 병렬 실행 활용
- run: pnpm -r --parallel lint typecheck

# 4. (선택) Turborepo 원격 캐싱 추가 - 대규모 모노레포에서만 권장
# env:
#   TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
#   TURBO_TEAM: ${{ vars.TURBO_TEAM }}
# - run: turbo run build test --filter='...[origin/main]'
```

### 9.4 빈번한 실수 모음

| 실수 | 증상 | 해결 |
| :--- | :--- | :--- |
| `workspace:*` 대신 버전 직접 명시 | 내부 패키지가 npm registry에서 검색됨 | 내부 패키지는 항상 `workspace:*` 사용 |
| `catalog:` 미사용으로 버전 불일치 | 패키지마다 다른 React 버전 설치 | `pnpm-workspace.yaml`에 `catalog` 정의 후 `catalog:` 참조 |
| `node_modules`를 `.gitignore`에 누락 | 저장소 크기 급증 | 루트 `.gitignore`에 `node_modules` 추가 |
| 루트에서 `pnpm add` 시 `-w` 플래그 누락 | "Running this command will add the dependency to the workspace root" 경고 | `pnpm add -Dw <pkg>` 사용 |
| `transpilePackages` 미설정 | Next.js에서 내부 패키지 import 실패 | `next.config.ts`에 `transpilePackages` 추가 |
| `.npmrc`에 `shamefully-hoist=true` 설정 | Ghost Dependency가 감지되지 않음 | `shamefully-hoist=false`로 엄격 모드 유지 |
| `pnpm deploy` 전에 빌드 누락 | 배포 디렉토리에 빌드 결과물 없음 | `pnpm --filter @my/web... build` 후 `pnpm deploy` 실행 |
