## 이 가이드에 대하여

이 문서는 프론트엔드 팀에 새로 합류하는 개발자가 **최대한 빠르게 자율적으로 기여할 수 있도록** 설계된 실전 온보딩 가이드이다. 단순한 셋업 매뉴얼이 아니라, 대규모 React 코드베이스를 이해하고, AI 도구를 활용해 학습 곡선을 단축하며, 팀의 비동기 협업 문화에 자연스럽게 녹아드는 과정 전체를 다룬다.

**이 가이드의 핵심 원칙:**

- 모든 학습은 실제 코드와 실제 이슈를 통해 이루어진다
- AI 도구는 학습의 보조제이지 대체제가 아니다
- 질문하는 것보다 질문하지 않는 것이 더 비용이 크다
- 문서화되지 않은 지식은 존재하지 않는 지식이다

## 개발 환경 구축

### 필수 런타임 및 패키지 매니저

2025년 기준 프론트엔드 프로젝트의 표준 런타임 환경이다.

```bash
# Node.js 22 LTS 설치 (fnm 사용 권장, nvm보다 빠름)
curl -fsSL https://fnm.vercel.app/install | bash
fnm install 22
fnm default 22
node -v  # v22.x.x 확인

# pnpm 설치 (corepack 활용)
corepack enable
corepack prepare pnpm@latest --activate
pnpm -v  # 9.x.x 확인
```

> **왜 pnpm인가?** npm 대비 디스크 사용량 절감(hard link 기반), 엄격한 의존성 해석(phantom dependency 방지), 그리고 monorepo 지원이 뛰어나다.

## AI 도구를 활용한 온보딩 가속화

### Claude Code로 코드베이스 탐색하기

Claude Code는 터미널에서 직접 코드베이스와 대화하면서 탐색할 수 있는 도구이다. 온보딩 초기에 코드베이스를 빠르게 파악하는 데 매우 유용하다.

**설치 및 기본 사용:**

```bash
# Claude Code 설치
npm install -g @anthropic-ai/claude-code

# 프로젝트 루트에서 실행
cd <project-directory>
claude
```

**온보딩에 유용한 질문 패턴:**

```
# 프로젝트 구조 파악
> 이 프로젝트의 전체 디렉토리 구조를 설명해줘. 각 폴더의 역할이 뭐야?

# 데이터 흐름 추적
> 사용자가 로그인 버튼을 클릭했을 때 실행되는 코드 흐름을 처음부터 끝까지 추적해줘

# 특정 패턴 학습
> 이 프로젝트에서 API 호출을 어떤 패턴으로 하고 있어? 예시 코드를 보여줘

# 컨벤션 파악
> 이 프로젝트의 컴포넌트 작성 컨벤션을 분석해줘. 파일 구조, 네이밍, props 패턴 등

# 의존성 이해
> 이 프로젝트에서 사용하는 주요 라이브러리들과 각각의 용도를 정리해줘

# 테스트 패턴 학습
> 이 프로젝트의 테스트 작성 패턴을 알려줘. 어떤 테스트 프레임워크를 쓰고 있어?
```

**코드 리뷰 보조:**

```
# 내가 작성한 코드에 대한 사전 리뷰
> 이 변경사항을 리뷰해줘. 프로젝트의 기존 패턴과 일치하는지도 확인해줘

# 리팩토링 제안
> 이 컴포넌트를 프로젝트의 기존 패턴에 맞게 리팩토링하려면 어떻게 해야 해?
```

### GitHub Copilot으로 패턴 학습하기

Copilot은 단순한 코드 자동완성 도구가 아니라, 프로젝트의 코딩 패턴을 빠르게 흡수하는 학습 도구이다.

**효과적인 활용법:**

```typescript
// 1. 주석으로 의도를 먼저 작성하면 프로젝트 패턴에 맞는 코드를 제안받을 수 있다
// API에서 사용자 목록을 가져와서 테이블에 표시하는 컴포넌트
// → Copilot이 프로젝트의 기존 API 호출 패턴, 테이블 컴포넌트 사용법을 반영한 코드를 제안

// 2. 기존 파일을 열어둔 상태에서 새 파일을 작성하면 패턴을 더 잘 따른다
// 예: UserList.tsx를 열어둔 채로 ProductList.tsx를 작성

// 3. 테스트 파일에서 특히 유용하다
// 기존 테스트 파일의 패턴을 학습하여 일관된 테스트 코드를 제안
describe("useAuth", () => {
  // Copilot이 기존 테스트 패턴을 따라 제안
});
```

**주의할 점:**

- Copilot이 제안한 코드를 그대로 수락하지 말고, 반드시 이해한 후 사용한다
- 제안된 코드가 프로젝트의 컨벤션과 맞는지 확인한다
- 보안에 민감한 코드(인증, 권한 처리 등)는 Copilot 제안에 의존하지 않는다
- AI가 생성한 코드에는 hallucination이 있을 수 있다. 특히 API 시그니처, 라이브러리 사용법은 공식 문서와 대조한다

## 코드베이스 탐색 전략

### 대규모 React 프로젝트 구조 이해하기

처음 코드베이스를 마주했을 때 모든 파일을 읽으려 하지 말고, 아래 전략을 따른다.

**1단계: 진입점에서 시작하기**

```
src/
├── main.tsx              ← 앱 진입점. 여기서 시작
├── App.tsx               ← 라우팅 구조 파악
├── routes/               ← 페이지별 코드 분리
│   ├── index.tsx
│   └── __root.tsx
```

가장 먼저 `main.tsx` (또는 `index.tsx`)를 읽고, Provider 구조와 전역 설정을 파악한다. 그 다음 `App.tsx`에서 라우팅 구조를 확인하면 전체 앱의 페이지 구성을 한눈에 알 수 있다.

**2단계: 하나의 기능을 수직으로 추적하기**

가장 단순한 페이지 하나를 골라서 UI부터 데이터 소스까지 수직으로 따라간다.

```
페이지 컴포넌트 (routes/users/index.tsx)
  → 사용하는 커스텀 훅 (hooks/useUsers.ts)
    → API 호출 함수 (api/users.ts)
      → API 클라이언트 설정 (lib/apiClient.ts)
        → 타입 정의 (types/user.ts)
```

이 수직 추적을 2~3개 기능에 대해 반복하면, 프로젝트의 아키텍처 패턴이 보이기 시작한다.

**3단계: 공통 모듈 파악하기**

```
src/
├── components/
│   ├── ui/               ← 디자인 시스템 기본 컴포넌트 (Button, Input, Modal...)
│   └── shared/           ← 비즈니스 로직이 포함된 공통 컴포넌트
├── hooks/                ← 커스텀 훅
├── lib/                  ← 유틸리티 함수, 설정
├── stores/               ← 전역 상태 관리 (Zustand, Jotai 등)
└── types/                ← 공통 타입 정의
```

> **팁:** `components/ui/` 폴더를 먼저 훑어보면 프로젝트에서 사용하는 UI 기본 요소들을 빠르게 파악할 수 있다. 이미 만들어진 컴포넌트를 모르고 새로 만드는 실수를 방지한다.

### 읽어야 할 파일 우선순위

온보딩 첫 주에 반드시 읽어야 할 파일 목록 (우선순위 순):

1. **`package.json`** - 사용 중인 라이브러리, 스크립트 명령어
2. **`tsconfig.json`** - path alias, 컴파일 옵션
3. **`vite.config.ts`** - 빌드 설정, proxy 설정
4. **`eslint.config.js`** - 코딩 규칙
5. **`src/main.tsx`** - 앱 진입점
6. **`src/App.tsx`** - 라우팅 구조
7. **`README.md`** - 프로젝트 개요 (있을 경우)
8. **`.env.example`** - 필요한 환경 변수 목록

## 30/60/90일 온보딩 로드맵

### 30일차 (Day 1-30): 기반 구축

이 기간의 목표는 **개발 환경 완성, 코드베이스 기본 이해, 첫 PR 머지**이다.

#### Week 1: 환경 셋업과 탐색

| 일차 | 활동 | 완료 기준 |
|------|------|-----------|
| Day 1 | 개발 환경 셋업, 프로젝트 로컬 실행 | `pnpm dev`로 앱이 브라우저에 정상 표시 |
| Day 2 | 팀 도구 접근 권한 확인, 코드베이스 구조 탐색 | GitHub, 이슈 트래커, Slack 채널 접근 완료 |
| Day 3 | `main.tsx` → `App.tsx` → 주요 라우트 순서로 코드 읽기 | 앱의 주요 페이지 5개 이상 파악 |
| Day 4 | 기존 이슈 중 `good-first-issue` 선택 및 착수 | 이슈 할당 및 브랜치 생성 |
| Day 5 | 첫 PR 제출 | 코드 리뷰 요청 상태 |

#### Week 2: 패턴 학습

| 활동 | 완료 기준 |
|------|-----------|
| 하나의 기능을 UI → Hook → API → Type까지 수직 추적 | 추적 내용을 팀 위키에 문서화 |
| 프로젝트의 상태 관리 패턴 파악 | 어떤 상태 관리 도구를 왜 쓰는지 설명 가능 |
| 첫 PR 리뷰 피드백 반영 및 머지 | 머지 완료 |
| 두 번째 이슈 착수 (약간 더 복잡한 것) | PR 제출 |

#### Week 3-4: 독립성 확보

| 활동 | 완료 기준 |
|------|-----------|
| 새로운 UI 컴포넌트 또는 페이지 작성 | 기존 디자인 시스템 컴포넌트를 활용하여 구현 |
| 단위 테스트 작성 경험 | 최소 1개 컴포넌트에 대한 테스트 작성 |
| 팀원의 PR 1건 리뷰 참여 | 의미 있는 코멘트 1개 이상 |
| 30일 회고 작성 | 배운 것, 어려운 것, 다음 30일 목표 정리 |

**30일차 마일스톤:**
- PR 2건 이상 머지
- 로컬 개발 환경에서 독립적으로 개발 가능
- 프로젝트 아키텍처의 큰 그림을 설명할 수 있음
- 디버깅 도구 기본 사용법 숙지

### 60일차 (Day 31-60): 기여 확대

이 기간의 목표는 **중간 난이도 이슈 독립 처리, 코드 리뷰 참여, 기술 부채 인식**이다.

#### Week 5-6: 복잡한 기능 개발

| 활동 | 완료 기준 |
|------|-----------|
| 여러 컴포넌트에 걸친 기능 개발 | 설계부터 구현까지 독립 수행 |

### 코드 리뷰하는 법 (신규 입사자를 위한 가이드)

온보딩 중이라도 다른 팀원의 PR을 리뷰하는 것은 코드베이스를 배우는 가장 효과적인 방법 중 하나이다.

**리뷰 시 집중할 포인트 (경험 수준별):**

| 수준 | 집중 포인트 | 예시 코멘트 |
|------|-------------|-------------|
| 첫 달 | 이해가 안 되는 부분 질문 | "이 부분에서 왜 `useMemo`를 사용했는지 궁금합니다" |
| 첫 달 | 오타, 네이밍 개선 제안 | "`userData`보다 `userProfile`이 의도를 더 잘 전달하는 것 같습니다" |
| 둘째 달 | 엣지 케이스 지적 | "data가 빈 배열일 때 이 컴포넌트가 어떻게 렌더링되나요?" |
| 둘째 달 | 테스트 커버리지 확인 | "이 조건 분기에 대한 테스트가 있으면 좋겠습니다" |
| 셋째 달 | 아키텍처 수준 피드백 | "이 로직을 커스텀 훅으로 분리하면 재사용성이 높아질 것 같습니다" |

**리뷰 코멘트 작성 원칙:**

```
# 좋은 코멘트의 구조
1. 관찰 (무엇을 보았는가)
2. 영향 (왜 중요한가)
3. 제안 (어떻게 개선할 수 있는가)

# 예시
"이 useEffect에서 의존성 배열에 `userId`가 빠져있는 것 같습니다. (관찰)
userId가 변경되어도 데이터를 다시 가져오지 않을 수 있습니다. (영향)
의존성 배열에 userId를 추가하면 해결될 것 같습니다. (제안)"
```

**피해야 할 코멘트 패턴:**

- "이건 왜 이렇게 했어요?" → "이 부분의 의도가 궁금합니다. X 때문인가요?"
- "이건 틀렸습니다" → "이 부분에서 Y 케이스를 고려하면 Z 문제가 발생할 수 있을 것 같습니다"
- 아무 맥락 없이 "nit:" → 사소한 제안이라도 이유를 간단히 덧붙인다

### 코드 리뷰를 받는 법

- 리뷰 코멘트에 방어적으로 반응하지 않는다. 코드에 대한 피드백이지 사람에 대한 평가가 아니다
- 모든 코멘트에 답변한다. 수용했으면 "반영했습니다", 다른 의견이 있으면 근거와 함께 설명한다
- "Resolve" 버튼은 코멘트를 남긴 사람이 누르도록 한다 (팀 규칙에 따라 다를 수 있음)
- 리뷰 반영 후 re-request review를 한다

### Sentry를 통한 에러 모니터링

Sentry는 프로덕션 환경의 에러를 실시간으로 수집하고 추적하는 도구이다.

**프론트엔드 Sentry 기본 설정:**

```typescript
// src/lib/sentry.ts
import * as Sentry from "@sentry/react";

Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  environment: import.meta.env.MODE,
  integrations: [
    Sentry.browserTracingIntegration(),
    Sentry.replayIntegration({
      maskAllText: true,
      blockAllMedia: true,
    }),
  ],
  tracesSampleRate: 0.1,         // 성능 트레이싱 10% 샘플링
  replaysSessionSampleRate: 0.01, // 일반 세션 리플레이 1%
  replaysOnErrorSampleRate: 1.0,  // 에러 발생 세션은 100% 리플레이
});
```

**Error Boundary 설정:**

```tsx
// src/components/ErrorBoundary.tsx
import * as Sentry from "@sentry/react";

interface FallbackProps {
  error: Error;
  resetError: () => void;
}

function ErrorFallback({ error, resetError }: FallbackProps) {
  return (
    <div role="alert">
      <h2>문제가 발생했습니다</h2>
      <pre>{error.message}</pre>
      <button onClick={resetError}>다시 시도</button>
    </div>
  );
}

export function AppErrorBoundary({ children }: { children: React.ReactNode }) {
  return (
    <Sentry.ErrorBoundary
      fallback={({ error, resetError }) => (
        <ErrorFallback
          error={error as Error}
          resetError={resetError}
        />
      )}
    >
      {children}
    </Sentry.ErrorBoundary>
  );
}
```

**Sentry 대시보드 활용법:**

```
온보딩 중 확인해야 할 Sentry 항목:

1. Issues 페이지

2. Performance 페이지
   - 주요 페이지의 로딩 시간 기준값 파악
   - 느린 트랜잭션 식별

3. 알림 설정
   - 본인이 담당하는 영역의 에러 알림을 Slack으로 연동
```

### 비동기 커뮤니케이션 원칙

현대 개발 팀은 동기적 소통(회의, 즉석 질문)보다 비동기적 소통(문서, 메시지)을 기본으로 한다. 이는 개발자의 집중 시간(deep work)을 보호하기 위함이다.

**메시지 작성 원칙:**

```
나쁜 예:
"잠깐 통화 가능해요?"
"이거 좀 봐주세요"

좋은 예:
"프로필 페이지 이미지 업로드 관련 질문입니다.
- 현재 상황: 이미지 리사이징 후 S3 업로드 시 CORS 에러 발생
- 시도한 것: vite.config.ts에서 proxy 설정 추가,
  S3 bucket CORS 정책 확인 (정상)
- 질문: 프로덕션 환경에서는 이 부분을 어떻게 처리하고 있나요?
  CloudFront를 통해 우회하는 건가요?
- 긴급도: 이번 스프린트 완료 목표이지만 오늘 중 답변이 아니어도 됩니다"
```

핵심은 **상대방이 맥락을 파악하기 위해 추가 질문을 하지 않아도 되도록** 충분한 정보를 한 번에 제공하는 것이다.

**응답 시간 기대치:**

| 채널 | 기대 응답 시간 | 용도 |
|------|----------------|------|
| Slack DM | 4시간 이내 | 일반 질문 |
| Slack 채널 멘션 | 1영업일 이내 | 팀 논의 필요한 사안 |
| PR 리뷰 요청 | 1영업일 이내 | 코드 리뷰 |
| 긴급 (장애) | 즉시 | 프로덕션 장애 시 |

### 문서화 습관

**"문서화된 것만 존재한다"** 라는 원칙을 따른다.

```
문서화해야 할 것:
1. 기술적 의사결정 (ADR - Architecture Decision Record)
   - 무엇을 결정했는가
   - 어떤 대안을 검토했는가
   - 왜 이 선택을 했는가

2. 트러블슈팅 기록
   - 어떤 문제가 발생했는가
   - 원인은 무엇이었는가
   - 어떻게 해결했는가

3. 온보딩 중 발견한 문서 부족 영역
   - 온보딩 중 막혔던 지점을 기록하고
   - 해결 후 그 내용을 문서로 남긴다
   - 이것이 다음 신규 팀원에게 가장 큰 선물이다
```

**ADR 작성 템플릿:**

```markdown
# ADR-001: 상태 관리 도구로 Zustand 선택

## 상태
승인됨 (2025-01-15)

## 맥락
프로젝트의 전역 상태 관리를 위한 도구 선택이 필요하다.
현재 props drilling이 3단계 이상인 컴포넌트가 12개 존재한다.

## 검토한 대안
1. Redux Toolkit - 생태계가 크지만 보일러플레이트가 많다
2. Zustand - 가볍고 TypeScript 지원이 우수하다
3. Jotai - 원자적 상태 관리에 적합하나 학습 곡선이 있다

## 결정
Zustand를 선택한다.

## 근거
- 번들 크기가 작다 (1.1kB gzipped)
- React 외부에서도 상태에 접근 가능하다
- 보일러플레이트 없이 직관적으로 사용할 수 있다
- 팀원 대부분이 사용 경험이 있다

## 결과
- store 패턴은 src/stores/ 디렉토리에 도메인별로 분리한다
- 전역 상태는 최소화하고, 서버 상태는 TanStack Query로 관리한다
```

### 회의 문화

**회의 참석 전 준비:**
- 안건을 미리 읽고 의견을 준비한다
- 시간 내에 결론이 나지 않을 것 같으면 "이 주제는 별도 논의가 필요할 것 같습니다"라고 제안한다
- 회의 후 결정 사항과 액션 아이템을 문서로 남긴다

**데일리 스탠드업 포맷:**

```
1. 어제 한 일 (완료된 것 위주로 간결하게)
2. 오늘 할 일 (가장 중요한 1-2가지)
3. 블로커 (도움이 필요한 부분, 없으면 생략)
```

> **팁:** 스탠드업은 보고가 아니라 동기화이다. 30초 이내로 말하고, 상세 논의가 필요하면 "이 건은 스탠드업 이후 별도로 논의하겠습니다"라고 한다.

### 피드백 문화

**피드백 주기:**
- 구체적 행동에 대해 말한다 (성격이 아니라)
- 가능한 빨리 준다 (일주일 뒤가 아니라 당일에)
- 공개적으로 칭찬하고, 개선 피드백은 1:1로 한다

**피드백 받기:**
- 방어적으로 반응하지 않는다
- "그 부분에 대해 더 구체적으로 말해줄 수 있나요?"라고 질문한다
- 피드백에 동의하지 않더라도 감사를 표한다

## 부록: 자주 겪는 상황별 대응 가이드

### "코드가 이해가 안 돼요"

1. 해당 파일의 git log를 확인한다: `git log --oneline -10 -- <file-path>`
2. 관련 PR을 찾아 변경 이유를 파악한다
3. Claude Code에 해당 코드의 맥락을 질문한다
4. 그래도 모르겠으면 git blame으로 작성자를 찾아 직접 질문한다

### "빌드가 깨졌어요"

```bash
# 1. node_modules 초기화
rm -rf node_modules
pnpm install

# 2. 빌드 캐시 정리
rm -rf dist .vite

# 3. TypeScript 캐시 정리
rm -rf tsconfig.tsbuildinfo

# 4. 그래도 안 되면 Node.js 버전 확인
node -v  # 22.x.x인지 확인
```

### "테스트가 로컬에서만 실패해요"

```bash
# 1. 테스트 캐시 정리
pnpm test -- --clearCache

# 2. 단일 테스트 파일만 실행
pnpm test -- path/to/test.test.ts

# 3. 타임존 이슈 확인
TZ=UTC pnpm test

# 4. 환경 변수 차이 확인
# CI와 로컬의 .env 파일 비교
```

### "PR 리뷰가 안 올라와요"

- Slack에서 리뷰어를 정중하게 리마인드한다
- PR 설명이 충분한지 다시 확인한다 (리뷰어가 맥락 파악에 시간이 오래 걸리면 리뷰가 늦어진다)
- PR 크기가 너무 크지 않은지 확인한다 (300줄 이상이면 분리를 고려한다)
