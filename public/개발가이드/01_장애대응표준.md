## 장애대응의 목표와 원칙

### 목표
- 사용자 영향 최소화와 서비스 신속한 해소
- 근본 원인 분석과 재발 방지(Poka-Yoke) 실행

### 핵심 원칙

| 원칙 | 설명 |
|------|------|
| **공지/전파 우선** | 정보가 완벽하지 않아도 즉시 공유하고 스레드로 수시 업데이트 |
| **롤백 최우선** | 가장 빠른 사용자 영향 해소 수단을 항상 롤백부터 검토 |
| **동원(All-hands) 5분 대기** | 초동 5분 내 필요한 사람들이 모두 모여 역할을 분담. 장애 인입/확인 시간으로부터 **4분 내 해소 목표** |
| **단일 지휘(Commander)** | 의사결정과 우선순위는 Commander가 단일 창구로 책임 |
| **가시성** | 허들/Zoom 논의도 반드시 장애 채널 스레드에 요약 업데이트 |

---

## 대응 시간 권장 가이드

> 시간은 참고값이며, Commander는 매 업데이트에 다음 ETA를 명시합니다.

- **초동 공지/역할 배분**: 5분 이내
- **롤백 결정/개시**: 7분 이내
- **핫픽스(필요 시) 준비/적용**: 10~30분
- **커뮤니케이션 주기**: Critical 5분, Warning ~30분

## 장애 공지 및 전파

### 공지 템플릿

```
**** 장애공지 ****
1. 심각도: Critical/Warning
2. 장애 발생 지점(내부/외부):
3. 장애 조치 채널: #YYYYMMDD-장애내용
4. 고객이 받는 영향: (사용자 관점으로 구체화)
5. 장애 시작 시간: (오전/오후 HH:MM)
6. 장애 원인: (초기 가설 가능, 예상임을 명시)
7. 조치 내용: (착수된 즉시 기입)
8. 장애 종료 시간: -
```

### 템플릿 설명

| 항목 | 설명 |
|------|------|
| **장애 공지 유형** | 장애 공지 / 장애 아님 / 장애 업데이트 / 장애해소 공지 |
| **심각도** | Critical/Warning으로 나뉘며, 대응 단계를 결정하는 기준 |
| **장애 발생 지점** | 내부/외부로 구분 (자사 내부 문제 vs 외부 서비스) |
| **장애 조치 채널** | #YYYYMMDD-장애내용 (장애 건별로 생성되는 채널 링크) |
| **고객이 받는 영향** | 시스템 측면이 아닌, 고객이 받을 수 있는 영향 위주로 작성 |
| **장애 시작 시간** | 장애가 최초로 시작된 시간 |
| **장애 원인** | 대응 중 원인이 확인되면 업데이트 |
| **조치 내용** | 시간별로 유관부서에 공유할 내용 업데이트 |
| **장애 종료 시간** | 장애가 해소되는 시간 |

## 장애 발생시 동원 가이드

| 항목 | 내용 |
|------|------|
| **동원 기준(5분 룰)** | 장애 공지 후 5분 내 참석 가능한 인원이 허들/Zoom + Slack 채널에 집결. 팀채널에 전체 공지, 이후 필요 필수인원에 대해서 유/무선연락을 취해 최대한 빠르게 집결할 수 있도록 한다. 특정 상황에 필수인원이 집결 불가능한 경우, 대행자를 지정한다. |
| **침묵 규칙** | 발언권은 Commander 지시 순서로. 나머지는 이모지/스레드로 신호. 잡음 최소화. |
| **즉시 준비물** | 최근 배포 버전/해시, 마지막 정상 버전, 롤백 경로, 플래그 대시보드 링크, 주요 모니터링 링크 |
| **허들/Zoom 업데이트** | 논의 요지는 5줄 이내로 Slack 스레드에 즉시 요약 업데이트 |

## 역할과 대무자 지정

초동 5분 내 커맨더가 아래 역할을 지정/멘션하고, 미 배정 역할은 커맨더가 임시 수행합니다.

### 장애 커맨더
- 초동 수습과 의사결정 총괄, 공지 주기 설정, 역할 배분
- **지정 우선순위**:
  1. 배포 및 모니터링 담당자
  2. 도메인 FE 온콜
  3. 도메인 FE TL
  4. 공통 FE 시니어
  5. SRE 대행

### 커뮤니케이터
- 커뮤니케이터는 개발자일 필요 없음 (PM 등 여타 직군도 가능)
- 채널 공지/스레드 업데이트, 타조직 전파, 타임라인 기록
- **커뮤니케이션 대상**: BE, SRE, VOC/CS, 기획/PM, QA, 외부 협력사

### 모니터링 담당자
- 대시보드/알람 집중 관찰, 영향/추세 리포트
- 그라파나 링크: (팀 내부 대시보드 URL 설정)
- 센트리 링크: (팀 내부 Sentry 프로젝트 URL 설정)

### 대응 실무자
- FE 빌드/배포, 플래그/실험, CDN/캐시, 라우팅, 긴급 핫픽스 수행

## 심각도와 트리거

### 프론트엔드 관점에서의 심각도

| 심각도 | 설명 |
|--------|------|
| **Critical** | 중앙 기준 충족 또는 FE 지표 급변으로 주요 유저 플로우가 중단/심각 저하 |
| **Warning** | 기능 저하/일부 구간 이슈이나 대안 경로 존재 |

### FE 주요 탐지 신호
- JS 에러율 급증
- onLoad 실패/리소스 4xx/5xx 급증
- SPA 전환 실패율 급증
- Hydration mismatch 급증
- 핵심 페이지 가용성 저하 (예: 홈/상품상세/장바구니/결제 진입률 급락)
- 정적 에셋 배포/서빙 오류 (CDN/오리진 미스매치, 캐시 오염)
- 실험/플래그 롤아웃 후 리텐션/주문 전환 급락

## 대응 프로세스

### 1) 초동 평가 (0~5분)
- Commander 지정, 역할 배분, 공지 게시, 조치 채널 개설
- 영향 크기/범위 파악 (핵심 전환, 트래픽, JS 에러율, 에셋 실패율)

### 2) 롤백 검토 (최우선)
Critical이라 판단되는 경우 (주요 유저 플로우가 중단/심각 저하, 장애 등급표에서 1/2등급이 예상 되는 경우) 협의를 통해 바로 롤백 판단을 할 수 있습니다.

#### 롤백의 방식
- **플래그/실험 회수**: 기능 플래그 OFF, 롤아웃 비율 0%, 실험 중단
- **배포 롤백**: 마지막 정상 아티팩트로 즉시 롤백 (서버 호환성 확인)
- **CDN/캐시**: 이전 index.html 서빙 복귀, 캐시 무효화/범위 퍼지, 강제 캐시 단축
- **라우팅**: 신규 라우팅/에지 규칙 무효화, 이전 규칙 복원
- **데이터/호환**: 스키마/컨트랙트와 관련된 변경이 배포가 되는 경우 BE와 호환성 검토 후 단계적 롤백

### 3) 대체 경로/완화 (롤백 불가 시)
- Feature 토글로 문제 기능 비가시화
- 구버전 경로로 우회
- 부분 비활성화 (읽기 전용 전환 등)

### 4) 핫픽스 (필요 시)
- 커밋 범위 최소화
- 스모크 테스트
- 점진 배포 후 전량 확대

### 5) 확인/검증
- 핵심 유저플로우 스모크 테스트
- 지표 확인: JS 에러율, 로딩 실패율, 전환률/주문수 회복 확인

## 장애 사후 조치 프로세스

### Post Mortem 수행 가이드

**모든 장애에 대해서 장애보고서를 작성하는 것을 원칙으로 합니다.**

단, 장애아님으로 최종 판정 되었더라도 대응 기록을 보관할 필요가 있다고 판단될 경우, 장애 보고서를 작성할 수 있습니다.

### 장애보고서
- 장애 해소 후 이슈 트래킹 시스템(JIRA 등)에 장애보고서를 생성합니다.

### 주요 기입 항목
- 주문유실/매출유실 영향 (가능 시 수치), 사용자 영향 서술, 타임라인 (공지/결정/조치), 근본 원인 (5Whys)
- 재발 방지(Poka-Yoke): 배포/롤아웃 가드, 캐시 전략, 라우팅 가드, 계약 테스트, 프리플라이트 스모크 등
- 액션 아이템: 담당자/기한 포함, 추적 가능 링크 (깃/플래그/대시보드)

## 주문유실수 산정 기준

주문유실수 확인은 해당 도메인 담당 팀에서 산정 가능하다면 담당 팀 산정 우선으로 적용하며, 담당 팀에서 명확한 산정이 어렵다면 인프라/SRE 담당 팀에서 계산합니다.

### 장애 등급 기준

**기준: 서비스의 일평균 주문수를 기반으로 산정**

| 등급 | 기준 |
|------|------|
| **1등급** | 일평균 주문수의 0.5% 이상 유실 |
| **2등급** | 일평균 주문수의 0.05% 이상 유실 |
| **3등급** | 기타 모든 장애 |

## 5Whys 템플릿

- **숫자 5는 상징적인 의미이며**, 꼭 다섯 번일 필요는 없습니다. 문제의 복잡도에 따라 질문 횟수는 더 적거나 많아질 수 있습니다.
- 첫 번째 질문은 항상 장애로 영향을 받은 **고객의 관점에서 시작**해야 합니다.
- 답변은 반드시 **검증 가능하거나 이미 검증된 사실을 기반**으로 해야 합니다.

```
상황: (시간/현상/영향)
1. 왜 이런 상황이 발생했는가?
2. 왜 이런 상황이 발생했는가?
3. 왜 이런 상황이 발생했는가?
4. 왜 이런 상황이 발생했는가?
5. 왜 이런 상황이 발생했는가?
근본 원인:
개선/방지: (Poka‑Yoke 3건 이상)
```

### 5Whys 사례: 대량의 5xx 에러 발생

**상황**: 오후 2시경, 웹 서비스에서 대량의 5xx 에러가 발생하여 트래픽이 급감함.

**5Why 분석**

1. 왜 5xx 에러가 발생했는가?  
   → 웹 서버가 요청을 처리하지 못하고 에러를 반환했기 때문이다.
2. 왜 웹 서버가 요청을 처리하지 못했는가?  
   → 서버의 CPU 사용률이 100%에 도달했기 때문이다.
3. 왜 CPU 사용률이 100%까지 올랐는가?  
   → 특정 API 요청이 급증하면서 서버 부하가 증가했기 때문이다.
4. 왜 특정 API 요청이 급증했는가?  
   → 외부 파트너 시스템에서 비정상적인 반복 호출이 발생했기 때문이다.
5. 왜 외부 파트너 시스템에서 반복 호출이 발생했는가?  
   → 타임아웃 처리 후 재시도 로직이 과도하게 설정되어 있었기 때문이다.

**근본 원인**: 외부 파트너 시스템의 재시도 로직 오류 및 비정상 트래픽 발생.

**개선 방안**
- 외부 시스템 재시도 로직 가이드 제공 및 개선 요청
- 서버 단 트래픽 관리 및 API rate limit 적용
- 서버 모니터링 알림 임계치 재조정

| 장애 심각도 | 장애 등급 | 장애 보고서 작성 기한 | 장애보고서 리뷰 | 작성자 |
|------------|----------|---------------------|----------------|--------|

| Warning | 3등급 | 장애 해소일 기준 **3 영업일** 이내 작성 완료 | 3 영업일 이내 | 장애 발생 팀 |

## 장애 보고서 리뷰어

팀의 담당 Tech Lead가 해당 역할을 수행합니다.

1. 5-whys를 통해 근본적 원인이 제대로 식별 되었는지
2. Poka-Yoke를 적합하게 설계하여 장애 재발 방지가 가능한지 검증
   - 진행 현황 관리, 및 조치 확인 담당과 지원

---

## 장애 보고서 상태

티켓 내 `Review Completed` 상태:
- **장애 리뷰가 진행되고 리뷰에서 도출된 피드백이 장애보고서에 반영이 완료**됨을 의미
- 인프라/SRE 담당 팀에서 작성된 내용을 함께 검토하고 `DONE` 상태로 변경

### 검토사항
1. Root Cause가 정확하게 분석되었는지
2. Root Cause를 기반으로 재발 방지 대책이 적절하게 수립되었는지
3. 장애 재발 시 감지 수단이 마련되었는지

## 장애 후속조치 (Poka-Yoke)

- Poka-Yoke 과제의 추적 관리 용이성을 위해 이슈 트래킹 시스템에서 **장애후속조치 전용 프로젝트**를 사용하는 것을 권장
- 만약 개별 팀의 칸반 보드, 스프린트 등을 통해 티켓을 관리하고 싶은 경우, **Poka-Yoke 티켓과 연결(Linked)된 별도의 클론(Clone) 티켓을 생성해 관리**

### 조치 기간 (Poka-Yoke)

| 기간 | 완료 목표 |
|------|----------|
| **단기** | 1주일 이내 완료 |
| **중기** | 1개월 이내 완료 |
| **장기** | 1분기 이내 완료 |

## 정기 운영 리뷰 (Weekly Operations Review)

- 안정성(Stability), 신뢰성(Reliability), 보안(Security)을 주제로 매주 정기적으로 진행하는 세션

### 장애 발표 기준
- 모든 Critical 장애
- 또는 Warning 장애 중 비즈니스 영향이 1등급 기준 이상인 장애
